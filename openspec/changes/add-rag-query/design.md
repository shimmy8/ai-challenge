## Context

См. `proposal.md` для мотивации и `specs/rag-query/spec.md` для наблюдаемого контракта. Индексация уже живёт в `src/rag/`: один SQLite-файл хранит `structural` и `fixed` chunks, их тексты, provenance и little-endian `f32` embeddings. `IndexStore` пока умеет только публиковать данные и читать cache по хешу. Интерактивный путь проходит через `app.rs` и `AgentPool` к `Agent::ask`; `Agent` одновременно хранит историю и отправляет её обоим chat-провайдерам.

Корпус Дня 21 содержит 662 structural-чанка, поэтому точный поиск в памяти достаточно мал и позволяет обойтись без новой векторной БД. Embedding-конфигурация намеренно отделена от chat-конфигурации и не должна читаться, пока RAG выключен. Локальные `.fox-embeddings.json` и `.fox-index.db` содержат чувствительные данные и не попадают в Git.

## Goals / Non-Goals

**Goals:**

- Добавить один provider-neutral retrieval-путь для OpenAI и Claude без дублирования chat-flow.
- Сохранить исходную семантику истории, памяти, tool calling и invariant-проверки.
- Сделать retrieval и сравнение детерминированными настолько, насколько позволяет внешний LLM.
- Оставить оценку качества понятной и проверяемой без LLM-судьи.

**Non-Goals:**

- ANN-индекс, reranker, hybrid/BM25 search и автоматический выбор chunking-стратегии.
- Автоматическая переиндексация, изменение chunking Дня 21 или миграция основного session store.
- Долговременное сохранение RAG on/off в `.fox-llm.json`.
- Доказательство, что модель действительно использовала каждый переданный фрагмент; список источников означает фактически переданный контекст.
- Полноценная семантическая метрика качества или статистически значимый benchmark.

## Decisions

### 1. Retrieval остаётся отдельным слоем внутри `src/rag/`

Новый модуль retrieval загружает совместимые structural-чанки и vectors через расширенный read-only API `IndexStore`, получает embedding вопроса через существующий `EmbeddingProvider` и возвращает provider-neutral `RetrievedChunk`. Оркестрация интерактивного режима остаётся в `app.rs`, а `Agent` не открывает файлы и не знает о SQLite.

Так сохраняются границы ответственности: RAG-хранилище и embedding-сеть находятся в `src/rag/`, CLI управляет режимом, Agent отвечает за conversation state и chat-provider flow. Альтернатива — встроить retrieval в `Agent::ask` — сильнее связывает Agent с локальными файлами и заставляет тесты агента поднимать индекс.

### 2. Первый поиск — exact cosine scan по structural-чанкам

При каждом RAG-вопросе `IndexStore` одним запросом читает metadata, content и vector совместимых structural-чанков. Retrieval проверяет размеры и конечность значений, вычисляет cosine similarity и сортирует по `(similarity DESC, chunk_id ASC)`. После top-5 применяется лимит 6000 Unicode-символов: результаты добавляются целиком по рангу, как минимум лучший непустой чанк должен помещаться, иначе возвращается конфигурационная ошибка.

Для текущих 662 чанков exact scan прост, воспроизводим и не добавляет dependency. Альтернативы sqlite-vss/FAISS откладываются до измеряемой проблемы latency или размера корпуса. `fixed` не участвует, потому что сравнение Дня 21 рекомендует structural как более точную смысловую основу.

### 3. Совместимость определяется descriptor вопроса и строками chunks

Запрос использует `.fox-embeddings.json` и существующую factory. SQL выбирает только строки `strategy = 'structural'`, `model = descriptor.model` и `dimensions = descriptor.dimensions`. Отсутствие совпадений отличает пустой/несовместимый индекс от нерелевантного вопроса и вызывает безопасную ошибку с предложением переиндексировать корпус.

Endpoint и provider не сохранены на каждой строке индекса, поэтому v1 может строго проверить только model и dimensions. Добавлять миграцию схемы ради endpoint identity сейчас нецелесообразно; это ограничение будет явно описано в отчёте.

### 4. Agent получает оригинал и эфемерный request content раздельно

В Agent добавляется единая внутренняя точка запроса, принимающая исходный user input и необязательный ephemeral content для текущего сообщения. Подготовка контекста, ветвление, tool loop, token metrics, invariant validation и сохранение ответа остаются общими. В `history` и `persisted_history` добавляется исходный вопрос; непосредственно перед provider-вызовом строится временная копия истории, где только последнее user-сообщение заменено RAG-обёрткой. Результаты tool calls продолжают добавляться в рабочую временную request history, а успешный финальный ответ сохраняется обычным образом.

Это не даёт служебному контексту попасть в SQLite, summary или последующие turns. Отдельный второй Agent для RAG отвергнут: он дублировал бы memory/settings и нарушал бы непрерывность диалога.

### 5. RAG prompt использует жёсткий текстовый envelope

Builder создаёт стабильный блок: правила работы с недоверенными источниками, исходный вопрос и пронумерованные секции `[1]..[N]` с source/title/section и content. Delimiters фиксированы, metadata экранируется от управляющих delimiters, а тексты никогда не интерпретируются как инструкции приложения. Модели предлагается ссылаться на `[N]` и честно сообщать, если контекста недостаточно.

CLI после ответа печатает собственный список тех же `[N]`, поэтому provenance остаётся наблюдаемым даже при плохом форматировании ответа моделью. Мы не называем эти фрагменты доказанно использованными моделью — только переданными ей.

### 6. RAG mode — процессное состояние CLI

`app.rs` хранит `rag_enabled: bool`, начальное значение `false`. `/rag on|off|status` обрабатываются до обычной отправки и не вызывают providers. `/new` очищает conversation state, но не меняет выбранный режим; перезапуск процесса возвращает off. Status bar получает короткий индикатор RAG, а `/help` описывает команды.

Так режим легко сравнивать внутри одного запуска, но он не усложняет schema `.fox-llm.json`. Отдельные команды `/ask-rag` и `/ask-plain` отвергнуты как менее удобные для продолжительного диалога.

### 7. Сравнение выполняет отдельный startup mode `rag-eval`

Парсер startup mode получает команду вида:

```text
fox-llm rag-eval --questions reports/day22/control-questions.json \
  --output reports/day22/comparison.json
```

Для каждого вопроса runner создаёт два независимых одноразовых Agent с одинаковыми chat settings и без memory/profile/history/MCP: plain и RAG. RAG retrieval выполняется до своего chat-запроса. Результат накапливается в памяти и атомарно публикуется только после всех 20 успешных chat-запросов и 10 query-embedding запросов.

Контрольная запись содержит `id`, `question`, `expectation`, `required_fact_fragments` и `expected_sources`. Fact coverage — регистронезависимое совпадение нормализованных фрагментов в ответе; source recall — точное совпадение относительных путей среди retrieved chunks. Эти эвристики дешёвы и прозрачны, но итоговый README дополнительно содержит ручную оценку смысла.

### 8. Артефакты оценки безопасны и отделены от тестовых фикстур

`reports/day22/control-questions.json` и итоговый README коммитятся. `comparison.json` содержит вопросы, ответы, provenance, timings и token counts, поскольку это требуемый результат эксперимента, но не содержит vectors, hashes, endpoint config или credentials. В unit tests используются fake embedding/chat providers и временная SQLite-база; реальные локальные конфиги не читаются.

## Risks / Trade-offs

- [Exact scan станет медленным на большом корпусе] -> Замерять retrieval latency в evaluation; переходить к ANN только после появления порога и профиля нагрузки.
- [Очень короткие structural-чанки занимают позиции top-5] -> Зафиксировать наблюдение в отчёте; merge/min-size относится к следующему изменению, чтобы не смешивать retrieval со сменой индексации.
- [Одинаковые model и dimensions не гарантируют один embedding space у разных endpoint] -> Документировать ограничение и в будущем сохранить provider/endpoint fingerprint в индексе.
- [Prompt injection внутри корпуса] -> Жёстко маркировать контекст как недоверенные данные, сохранять приоритет системных/invariant-инструкций и тестировать вредоносный чанк.
- [Keyword coverage даёт ложные успехи и провалы] -> Публиковать сами эвристики, ответы и ручной разбор; не выдавать метрику за семантическую оценку.
- [20 chat-запросов стоят денег и зависят от сети] -> Запускать evaluation только явно, показывать безопасный прогресс и token usage, а unit tests выполнять на fakes.
- [Ошибка после части запросов теряет дорогой прогресс] -> Не публиковать частичный официальный отчёт ради атомарности; progress сообщает завершённые пары, а повторный запуск остаётся явным решением пользователя.

## Migration Plan

1. Расширить `IndexStore` только read API; существующая схема индекса остаётся совместимой.
2. Добавить retrieval и Agent ephemeral-input API с fake-based regression tests.
3. Подключить `/rag` при сохранённом default off, затем добавить `rag-eval`.
4. Создать контрольный набор, выполнить индексирование при необходимости и один полный evaluation run.
5. Заполнить отчёт Дня 22 и выполнить fmt, Clippy и весь test suite.

Rollback состоит в удалении новых команд и retrieval-вызова; индекс и session database не требуют отката или миграции.
