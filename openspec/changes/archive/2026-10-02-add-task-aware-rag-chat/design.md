## Context

См. `proposal.md` — Why. Интерактивный путь уже разделяет retrieval и generation: `app.rs` вызывает enhanced retrieval до `Agent::ask_rag`, а агент сохраняет исходный вопрос, временно заменяя только последнюю реплику копии request history на RAG-envelope. Generation получает обычную историю и `ActiveMemory`; query rewrite сейчас получает только текущий вопрос. Grounded-ответ проходит parser, проверку metadata и дословных цитат до изменения истории.

Рабочая память задачи уже хранится независимо от сессии. `TaskTodo::from_description` помещает исходное описание первым фактом, последующие допустимые `TaskUpdate.f` дополняют факты, а `Task.title` задаёт краткую цель. Поэтому требуемую память можно получить без изменения SQLite-схемы или TOON-формата.

## Goals / Non-Goals

**Goals:**

- Разрешать анафоры и короткие follow-up-вопросы до embedding-поиска.
- Сохранять жёсткое разделение исходного вопроса, retrieval hints, найденных документов и инструкций.
- Ограничить стоимость и объём контекстного rewrite детерминированными окнами.
- Повторно использовать существующую task memory без миграции пользовательских данных.
- Получить воспроизводимое доказательство на двух последовательных сценариях, а не набор независимых вопросов.

**Non-Goals:**

- Веб-интерфейс, удалённая vector database или новый embedding-провайдер.
- Автоматическое включение RAG при запуске; `/rag on`, `/rag off` и default-off сохраняются.
- Семантический поиск по всей истории или embedding-память диалога.
- Автоматическое создание долговременных фактов, профиля или новой задачи из обычных сообщений.
- Изменение изолированного single-turn `rag-eval` Дней 22–24.

## Decisions

### 1. Формировать отдельный ограниченный `RetrievalContext`

Перед `retrieve_enhanced` интерактивный цикл формирует неизменяемый снимок:

```text
RetrievalContext
+-- recent_user_messages: не более 4, суммарно <= 2000 символов
+-- task_title: активная задача либо отсутствует
+-- task_facts: исходное описание и сохранённые факты, <= 2000 символов
```

Реплики выбираются из `persisted_history` до добавления текущего вопроса, только с ролью `user`, от новых к старым; в prompt они возвращаются в хронологическом порядке. Реплика включается целиком либо не включается, поэтому границы сообщений остаются проверяемыми. Task budget заполняется названием, затем фактами в сохранённом порядке; переполнение отбрасывает целиком более поздние факты.

Снимок передаётся только в query rewrite. Исходный вопрос отдельно используется для original embedding, сохраняется в истории и остаётся последней пользовательской репликой generation history.

Альтернативы:

- Передавать всю историю — лучше разрешает дальние ссылки, но неограниченно растит стоимость и повышает риск prompt injection.
- Строить embeddings истории — требует отдельного индекса жизненного цикла сессии и несоразмерно текущему заданию.
- Оставить rewrite изолированным — не решает основную проблему multi-turn retrieval.

### 2. Использовать существующие task title и facts как task state

`Task.title` и первый факт, созданный из исходного описания, задают цель. Допустимые `TaskUpdate.f` фиксируют уточнения, ограничения и определения терминов. Retrieval читает их как данные, но не меняет задачу. Новый факт начинает влиять только на следующий ход после обычной проверки и атомарного сохранения task delta.

Это сохраняет существующую SQLite- и TOON-совместимость. Отдельные поля `goal`, `constraints` и `terms` не вводятся: они улучшили бы типизацию, но потребовали бы миграции формата, нового delta-контракта для обеих моделей и существенно расширили бы День 25. Смысл каждого факта остаётся человекочитаемым и проверяемым в `/task show` и `/memory`.

### 3. Query rewrite остаётся изолированным действием без инструментов

Rewrite получает фиксированную системную инструкцию и один структурированный prompt с тремя явно разделёнными секциями: текущий вопрос, недавние пользовательские реплики и состояние задачи. Две последние секции маркируются как недоверенные справочные данные. Профиль, long-term facts, mode-инструкции, ответы ассистента, summary, step results и tool definitions не передаются.

Проверка защищённых элементов применяется к текущему вопросу, как и раньше. Требовать все идентификаторы из четырёх прошлых реплик было бы чрезмерно: старое обсуждение может содержать уже отвергнутые варианты и сделало бы корректный rewrite невозможным.

### 4. Один формат видимого завершения RAG-хода

Успешный grounded-ответ продолжает использовать строгую TOON-атрибуцию и существующий render проверенных источников. Константа локального `no_relevant_context` дополняется секцией `Источники` с явным отсутствием результатов. Ошибки конфигурации, провайдера или контракта не считаются завершённым ответом и по-прежнему не сохраняются как реплика.

Такое различие не выдаёт отброшенные чанки за источники и одновременно выполняет пользовательское ожидание «всегда выводить источники» для каждого сохранённого RAG-ответа.

### 5. Добавить отдельный последовательный `rag-chat-eval`

Новый startup-режим принимает пути `--scenarios` и `--output`. Fixture содержит ровно два сценария, initial task и 10–15 turns. Runner создаёт для каждого сценария изолированного агента и временное SQLite-хранилище, затем на каждом ходе использует те же функции сборки retrieval context, enhanced retrieval, grounded generation, применения task delta и сериализации истории, что интерактивный путь.

Проверки делятся на детерминированные:

- ожидаемый outcome;
- наличие обязательных source paths среди проверенных citations;
- отсутствие источников для `no_relevant_context`;
- обязательные фрагменты видимого ответа;
- сохранение фрагментов task title и facts после хода;
- наличие секции `Источники` в каждой сохранённой паре сообщений.

Отчёт сначала пишется во временный файл рядом с destination, затем атомарно переименовывается. Он содержит ответы и безопасные source metadata, но не prompt, содержимое чанков, vectors или credentials. `rag-eval` остаётся отдельным кодовым путём и получает `RetrievalContext::default()` либо прежний изолированный API без контекста.

Альтернатива — только два ручных терминальных прогона — проще, но не даёт повторяемой проверки длины, изоляции, источников и состояния после каждого хода.

### 6. Тестировать сборку контекста отдельно от live evaluation

Юнит-тесты используют scripted request clients и временные базы: окно из четырёх user messages, бюджеты Unicode, отсутствие assistant/profile/MCP-данных, prompt-injection delimiters, сохранение исходной истории, восстановление task facts и rollback при ошибке. Интеграционные тесты прогоняют короткие детерминированные fixtures через fake embedding/chat adapters. Два полных live-сценария сохраняются в `reports/day25/` как результат задания, но сетевой прогон не становится обязательным условием обычного `cargo test`.

## Risks / Trade-offs

- [Модель неверно разрешит ссылку даже с контекстом] → Fixtures включают поздние follow-up-вопросы и проверяют обязательные источники; исходный и rewritten запросы по-прежнему ищутся совместно.
- [Старая реплика вытеснена окном из четырёх сообщений] → Долгоживущая цель и подтверждённые ограничения закрепляются в task facts; несохранённые детали намеренно считаются краткосрочными.
- [История или task fact содержит prompt injection] → Жёсткие delimiters, маркировка как data, отсутствие tools и тест с повелительным текстом.
- [Task facts смешивают разные типы сведений] → Это осознанная совместимость без миграции; отчёт проверяет конкретные фрагменты, а будущий change MAY типизировать task brief отдельно.
- [Live-сценарии недетерминированы и дороги] → Структурные контракты покрываются fake adapters, live runner сохраняет token usage/diagnostics и никогда не скрывает провал отдельного хода.
- [Контекстный rewrite увеличивает токены] → Фиксированные бюджеты 2000 + 2000 Unicode-символов и не более четырёх реплик.

## Migration Plan

1. Добавить `RetrievalContext` и покрыть его детерминированное формирование тестами, не подключая к CLI.
2. Расширить интерактивный enhanced retrieval и обновить no-context rendering.
3. Добавить regression-тесты совместимости: без истории/задачи, RAG off, `/new`, восстановленная задача и существующий `rag-eval`.
4. Добавить `rag-chat-eval`, fixtures и sanitized report schema.
5. Выполнить два live-сценария, сохранить результаты и отчёт Дня 25.

Rollback состоит в отключении передачи `RetrievalContext` и удалении нового startup-режима; SQLite и сохранённые задачи не требуют обратной миграции.
