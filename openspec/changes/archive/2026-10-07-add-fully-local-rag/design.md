## Context

См. `proposal.md` — Why. Текущий RAG уже реализует полный grounded flow: выбранный chat provider делает query rewrite, embedding adapter получает vectors вопроса, SQLite retrieval локально вычисляет similarity и reranking, после чего тот же chat provider генерирует ответ и при необходимости выполняет repair. `Provider::Ollama` проходит через общий request client, поэтому архитектурно подключение локальной LLM не требует отдельной RAG-ветки.

Индекс Недели 6 находится в `.fox-index.db` и построен на `text-embedding-3-small` размерности 1536. Интерактивная сессия сохраняет provider, model и историю вопросов/ответов, включая rendered sources и citations. При `--dump-metrics` отдельный JSONL-лог сохраняет `session_id`, outcome, elapsed time и request/session token counts, но эти метрики не входят в запись самой сессии.

## Goals / Non-Goals

**Goals:**

- Подтвердить в реальном CLI, что Ollama выполняет query rewrite, generation и repair в существующем RAG.
- Сохранить `.fox-index.db`, embedding configuration, retrieval algorithm и пользовательские команды без изменений.
- Сравнить локальную и необязательную облачную модель на одном наборе вопросов через обычные сохранённые сессии.
- Получить показатели качества из истории, а speed/token metrics — из связанного metrics log.
- Честно разделить локальные стадии и внешний embedding request в отчёте.

**Non-Goals:**

- Менять embeddings, corpus, chunking или SQLite-схему.
- Добавлять новый evaluation runner, export command или session schema.
- Создавать параллельный индекс или полностью offline RAG.
- Читать либо публиковать сессии, которые пользователь не выбрал для эксперимента.
- Доказывать статистическую устойчивость модели большим числом повторов.

## Decisions

### 1. Индекс и embedding-пространство остаются неизменными

День 28 использует `.fox-index.db`, созданный для Недели 6, и совместимую конфигурацию `text-embedding-3-small`. Query embedding должен находиться в том же vector space, поэтому его продолжает создавать существующий endpoint из `.fox-embeddings.json`. Индекс не открывается для записи и не переиздаётся.

Локальная embedding-модель отклонена для этого change: даже при том же числе dimensions её vectors не совместимы с сохранёнными vectors OpenAI и потребовали бы нового индекса.

### 2. Существующий `/rag on` остаётся единственной точкой входа

Пользователь выбирает Ollama обычным provider flow, включает `/rag on` и задаёт вопросы. Query rewrite получает текущие `AgentSettings`, а generation и repair проходят через тот же provider-neutral request client. Новый RAG mode не нужен.

Перед живым экспериментом focused recording-client regressions подтверждают, что rewrite, grounded generation и repair получают Ollama settings и не переключаются на cloud. Производственный код меняется только при обнаружении фактической несовместимости.

### 3. «Локальный retrieval» означает поиск по локальному индексу

После получения query vectors приложение локально читает SQLite, вычисляет cosine similarity, объединяет original/rewrite candidates, применяет threshold, reranking, top-K и context budget. Индекс и полные чанки не отправляются внешнему search service.

Embedding вопроса является отдельным этапом и при текущей конфигурации может использовать внешний endpoint. Поэтому отчёт говорит «локальный SQLite retrieval» и «локальная генерация Ollama», но не «полностью offline RAG».

### 4. Контрольный набор задаётся вручную в чистой сессии

Пользователь запускает `cargo run -- --dump-metrics`, выбирает Ollama, создаёт чистую сессию, включает `/rag on` и задаёт вопросы прошлой недели в заранее зафиксированном порядке. Это проверяет тот же путь, которым пользуется человек, включая историю для query rewrite, CLI rendering и сохранение сессии.

Для cloud comparison создаётся вторая чистая сессия с теми же вопросами и порядком. Профиль, активная задача, дополнительные mode-инструкции и посторонняя история не используются, чтобы не вносить разные скрытые условия. Если cloud provider не настроен, локальная сессия остаётся самостоятельным результатом.

`rag-eval` отклонён как избыточный: вопросы уже существуют, а пользователь готов воспроизвести их в реальном интерфейсе. Отдельный runner дал бы ещё один путь, который нужно поддерживать, вместо проверки конечного пользовательского сценария.

### 5. Сессия и metrics log анализируются совместно

После прогона пользователь передаёт точный session id или title. Анализ ограничивается этой сессией и извлекает из неё provider/model, пары вопрос-ответ и rendered sources/citations. Из `fox-metrics.log` выбираются только записи с тем же `session_id`; они сопоставляются с ответами в хронологическом порядке.

Metrics log не содержит текста вопроса, а сессия не содержит per-turn latency. Поэтому только совпадение session id, числа успешных ходов и порядка позволяет связать записи. При неоднозначности показатель помечается как недоступный — данные не угадываются.

Для облачной модели применяется тот же подход с другим session id. Сами `.fox-sessions.db` и `fox-metrics.log` остаются локальными и не копируются в отчёт.

### 6. Оценка использует весь набор как проверку стабильности

Качество оценивается по ожидаемым фактам контрольных вопросов, релевантности источников, дословным цитатам и корректным отказам. Скорость берётся из `elapsed_ms` и token counts. Стабильность означает долю успешных ходов, provider/contract errors, пропуски источников и latency outliers на полном наборе.

Если нужна оценка вариативности текста, в конце каждой сессии повторяются два или три заранее выбранных сложных вопроса. Полностью повторять весь набор несколько раз не требуется. Ручная оценка ясности и полноты маркируется как qualitative и не отменяет проверяемые ошибки.

### 7. Отчёт содержит только безопасные производные данные

В `reports/day28/README.md` попадают команды, environment, session identifiers без содержимого других сессий, агрегированные metrics, контрольные ответы или короткие безопасные фрагменты, источники и выводы. Запрещено добавлять базы данных, полный metrics log, локальные конфигурации, credentials, vectors, content hashes, полные retrieval chunks и служебные prompts.

## Risks / Trade-offs

- [Сессия не хранит per-turn latency] → запускать CLI с `--dump-metrics` и связывать entries только по точному `session_id` и порядку.
- [Формулировка «полностью локально» может пониматься как offline] → явно описать внешний query-embedding и вынести локальные embeddings с переиндексацией в отдельное улучшение.
- [Provider-specific rewrite меняет retrieval context] → считать сравнение end-to-end и использовать одинаковые вопросы, порядок и исходное состояние.
- [Один прогон слабо измеряет вариативность] → оценивать operational stability на всём наборе и при необходимости повторить 2–3 сложных вопроса.
- [Cold start увеличивает первый local latency] → не скрывать первый ход и отметить влияние загрузки модели.
- [В базе есть посторонние личные диалоги] → читать только явно названные session ids и не включать локальное хранилище в отчёт.

## Migration Plan

1. Добавить focused regressions для Ollama в RAG rewrite, generation и repair paths; исправить production code только при фактическом провале.
2. Зафиксировать порядок контрольных вопросов и запустить чистую Ollama-сессию через `cargo run -- --dump-metrics` и `/rag on`.
3. При наличии настроенной облачной модели повторить вопросы в отдельной чистой сессии.
4. После явного указания session ids проанализировать только выбранные histories и связанные metrics entries.
5. Оформить безопасные таблицы и выводы в `reports/day28/`, затем выполнить standard quality gates.

Миграция и rollback не требуются: формат конфигурации, индекс, команды и схемы данных не меняются.
