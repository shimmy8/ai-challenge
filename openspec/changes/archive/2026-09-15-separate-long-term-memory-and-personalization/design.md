## Context

Сейчас `ActiveMemory` содержит задачу и `Profile`, таблица `profiles` хранит `name + instructions`, а `Agent::request_settings()` помещает профиль в секцию «долговременного профиля». Краткосрочные summary и sticky facts живут в сессии, рабочая память — в `tasks`; отдельного API для явного сохранения долговременных фактов нет. Существующий профиль уже связан с сессией и применяется при всех стратегиях сжатия.

Изменение пересекает модель данных, SQLite, команды CLI, сборку prompt, payload обоих провайдеров, документацию Дней 11–12 и тесты. Требования определены в delta specs `agent-memory` и `personalization-profile`.

## Goals / Non-Goals

**Goals:**

- Добавить факты как контекстные данные, не меняя существующие механизмы сессии, задачи и профиля.
- Сохранить совместимость существующих профилей и сессий.
- Сделать сохранение факта в долговременную память явным и проверяемым.
- Подтвердить персонализацию на уровне сформированного provider payload и воспроизводимого эксперимента.

**Non-Goals:**

- Автоматически извлекать долговременную память или предпочтения из диалога.
- Добавлять embeddings, семантический поиск, ранжирование или синхронизацию между устройствами.
- Поддерживать несколько одновременно активных профилей или пользователей.
- Преобразовывать существующие sticky facts в долговременные записи.
- Оценивать качество ответа модели автоматическим семантическим тестом.

## Decisions

### 1. Память и персонализация разделяются по роли в prompt

Профиль остаётся доверенной пользовательской инструкцией и располагается после базового режима ответа. Задача, долговременные записи, summary и sticky facts маркируются как контекстные данные, а не команды.

Порядок секций:

```text
[инструкции режима]
[инструкции профиля персонализации]
[рабочая память задачи как данные]
[долговременные факты как данные]
[summary или sticky facts сессии как данные]
[история сообщений]
```

Альтернатива — хранить всё одним текстовым prompt — отклонена, потому что она снова смешивает инструкции и сведения и затрудняет тестирование источника контекста.

### 2. Долговременная память хранится отдельными фактами

Добавляется таблица:

```sql
CREATE TABLE memory_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    content TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Каждая строка является фактом без дополнительной классификации. Факты глобальны для локального пользователя и доступны во всех сессиях. В первой версии весь ограниченный по длине список включается в prompt: семантический выбор был бы отдельной функцией и скрывал бы, какие сведения реально применены.

Альтернатива — сохранять факты JSON-массивом в профиле — отклонена, поскольку связывает знания о пользователе или проекте с форматом ответа и не позволяет независимо адресовать факт. Типы `decision` и `knowledge` также отклонены для этого инкремента: различие между ними субъективно и усложняет простую команду сохранения.

### 3. Запись и удаление выполняются отдельными явными командами

Детерминированная форма сохранения:

```text
/remember <текст>
/forget <id>
```

`/remember` без аргументов открывает интерактивный многострочный ввод. Семантика команды фиксирована: она всегда создаёт только долговременный факт. Команда не добавляет сообщение в историю, не меняет summary или sticky facts и не меняет активную задачу, TODO, фазу либо профиль. `/forget` показывает целевой факт и удаляет его только после подтверждения. Краткосрочная память продолжает заполняться обычным диалогом, а рабочая — явными командами `/task`; универсальная команда для переноса между слоями не добавляется.

Альтернатива `/memory add` отклонена, потому что существующая `/memory` заявлена и используется как read-only диагностическая команда.

### 4. Профиль получает структурированный ввод без несовместимой миграции схемы

Новый интерактивный `/profile new` отдельно запрашивает стиль, формат и ограничения, после чего сериализует их в канонический текст с заголовками. Таблица `profiles` и поле `Profile.instructions` сохраняются: ранее созданный произвольный текст остаётся корректной инструкцией и не требует эвристического разбора.

Это предпочтительнее добавления трёх обязательных колонок: старые значения невозможно надёжно разложить по категориям, а модели всё равно требуется итоговый текст инструкций. Отдельная чистая функция формирования текста обеспечит детерминированные unit-тесты.

### 5. Активная память содержит снимок долговременных записей

`ActiveMemory` расширяется коллекцией `long_term_facts`, которую `SessionStore` загружает при запуске и обновляет после `/remember` или `/forget`. `AgentPool::set_memory` передаёт одинаковый снимок всем агентам, поэтому параллельные ответы получают один контекст. Факты не связываются с конкретной сессией: они являются текущим глобальным контекстом и их исправления должны действовать на последующие запросы, включая продолжение старой сессии.

Альтернатива сохранять список идентификаторов в каждой сессии отклонена: она превращает глобальную память в исторический snapshot и требует отдельной политики обновления устаревших фактов.

### 6. Provider payload строится тестируемыми чистыми функциями

Формирование JSON для OpenAI и Claude выделяется из HTTP-отправки. Тесты проверяют, что итоговые поля `instructions` и `system` содержат профиль при повторных запросах, но долговременные факты остаются в маркированной секции данных. Реальные ответы не проверяются unit-тестом, поскольку формулировки модели недетерминированы; различия поведения фиксируются ручным сценарием в отчёте Дня 12.

### 7. Предыдущие учебные артефакты остаются неизменными

Архив change, specs и отчёты Дня 11 не редактируются: новая функциональность оформляется отдельным инкрементом. README получает только описание новых пользовательских команд. Отчёт Дня 12 использует два контрастных профиля и один контрольный запрос, сравнивая стиль, формат и ограничения. Если платный API-вызов не выполняется, отчёт сохраняет команды и критерии без вымышленных ответов.

## Risks / Trade-offs

- [Все долговременные факты увеличивают каждый запрос] -> ограничить длину одного факта, показывать полный список через `/memory`, а retrieval оставить отдельным будущим изменением.
- [Текст памяти может выглядеть как prompt injection] -> явно маркировать всю секцию как недоверенные данные, экранировать её границы и держать ниже инструкций профиля.
- [Удаление факта необратимо] -> показывать id и текст факта и требовать явного подтверждения.
- [Старые профили не имеют видимой структуры] -> применять их без изменений; структурированный формат обязателен только для новых профилей.
- [Глобальная память меняет контекст продолженной старой сессии] -> документировать её как актуальное состояние пользователя, а не исторический snapshot.
- [Профиль конфликтует с режимом ответа] -> сохранять детерминированный порядок секций и показывать обе через `/memory`; базовые инструкции режима идут первыми, профиль уточняет формат.

## Migration Plan

1. При открытии БД создать `memory_entries` без `kind`, не изменяя таблицы `profiles`, `tasks` и существующие ссылки сессий.
2. Считать отсутствие фактов валидной пустой долговременной памятью.
3. Переименовать пользовательские подписи prompt и `/memory`, не меняя команды или идентификаторы профилей.
4. После обновления существующие профили продолжают загружаться из `instructions`; новые сохраняются туда же в структурированном текстовом формате.
5. Rollback безопасен для существующих данных: старая версия игнорирует новую таблицу. Созданные факты снова станут доступны после возврата к новой версии.
