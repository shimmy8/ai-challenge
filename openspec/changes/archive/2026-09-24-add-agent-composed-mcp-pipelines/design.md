## Context

Сейчас `Agent::ask_inner` передаёт модели определения разрешённых MCP-инструментов и выполняет до трёх top-level tool calls. `McpRuntime` повторно проверяет имя по снимку allowlist и отправляет один `tools/call`, а `Agent` отвечает за инварианты, подтверждение и сохранение только пользовательской истории. Формат `RequestOptions` уже одинаков для OpenAI и Claude, поэтому новый механизм должен оставаться provider-neutral.

Входные схемы инструментов доступны в `ToolDefinition`, но клиент пока проверяет только то, что arguments является JSON-объектом. Локальный MCP-сервер уже запускается отдельным режимом и весь его код по правилам репозитория должен оставаться в `src/mcp/`.

## Goals / Non-Goals

**Goals:**

- дать модели один структурированный способ объявить линейный план из разрешённых инструментов;
- выполнить каждый шаг как настоящий MCP `tools/call`, сохранив существующие allowlist, инварианты и подтверждения;
- обеспечить типобезопасную передачу JSON-результатов через `$ref` и понятный trace;
- предоставить полностью тестируемый GitHub-report pipeline из атомарных инструментов;
- оставить текущие одиночные tool calls и оба провайдера совместимыми.

**Non-Goals:**

- произвольные DAG, ветвления, циклы, параллельные шаги и автоматические retry всего пайплайна;
- генерация или выполнение моделью Rust, shell-команд, URL либо произвольного HTTP;
- rollback уже выполненных внешних действий;
- private GitHub repositories, traffic, security metrics, GraphQL и обязательная GitHub-аутентификация;
- планировщик фоновых или периодических пайплайнов.

## Decisions

### 1. Агент вызывает встроенный `fox_execute_pipeline`

Клиент добавляет provider-neutral определение `fox_execute_pipeline` к основному запросу, только если существует хотя бы один разрешённый MCP-инструмент. Arguments этого synthetic tool call содержат `PipelinePlan { name, steps }`; сам `fox_execute_pipeline` не отправляется MCP-серверу.

`Agent` распознаёт зарезервированное имя, валидирует весь план и затем вызывает каждый атомарный шаг через существующий `SharedToolExecutor`. После завершения он возвращает модели один `ToolResult` с call id исходного `fox_execute_pipeline` и полным trace. Поэтому провайдер видит один top-level structured call, а MCP-сервер получает несколько настоящих `tools/call`.

Альтернативы:

- прямое свободное чередование модельных tool calls ограничено тремя вызовами и делает передачу данных зависимой от повторного рассуждения модели;
- серверный `run_pipeline` формально скрывает композицию за одним MCP-вызовом и связывает общий оркестратор с конкретным сервером;
- разбор JSON из текста нарушает существующую гарантию, что текст не запускает инструменты.

### 2. Первая версия поддерживает только линейный план

`PipelineStep` содержит `id`, `tool` и `arguments`. Шаги выполняются в порядке массива. Единственная ссылка имеет точную объектную форму `{"$ref":"<step-id>.output"}` и может встречаться рекурсивно внутри arguments. Она заменяется полным JSON `content` успешного результата предыдущего шага. Частичные JSON Pointer и строковая интерполяция не поддерживаются в первой версии.

Линейная модель исключает циклы по построению, позволяет отклонять forward references одним проходом и достаточно выразительна для GitHub-отчёта. DAG и параллелизм отложены, потому что потребуют явной семантики зависимостей, конкурентных подтверждений и детерминированного порядка trace.

### 3. Валидация делится на статическую и пошаговую

До первого внешнего вызова статическая проверка подтверждает:

- от 1 до 8 шагов;
- уникальные непустые id;
- каждый `tool` найден среди текущих `ToolDefinition` и не равен зарезервированному `fox_execute_pipeline`;
- каждый `$ref` указывает на уже объявленный id;
- исходные arguments являются объектом.

Перед каждым шагом клиент разрешает ссылки, проверяет итоговый объект по `input_schema` целевого инструмента, запускает проверку инвариантов и при необходимости confirmation. Для JSON Schema используется отдельная библиотека `jsonschema`, чтобы не реализовывать неполный собственный валидатор поверх схем MCP/schemars.

Альтернатива — полагаться только на серверную валидацию — не подходит, поскольку изменяющий вызов должен быть проверен и показан пользователю до отправки.

### 4. Ошибка останавливает цепочку без rollback

Trace хранит общий status и для каждого шага: `pending`, `running`, `succeeded`, `failed`, `cancelled` или `skipped`, resolved arguments, безопасный output/error и признак изменяющего действия. После первой ошибки, отказа подтверждения или invariant refusal оставшиеся шаги становятся `skipped`.

Trace существует только внутри текущего `ask_inner`. В модель возвращается один результат synthetic tool call; в `history` и `persisted_history` промежуточные сообщения не добавляются. Флаг уже выполненного внешнего действия агрегируется по шагам и сохраняет текущую семантику ошибки финального synthesis.

### 5. Лимиты разделяются по уровням

Существующий счётчик остаётся лимитом трёх top-level structured calls модели. Вызов `fox_execute_pipeline` увеличивает его на один независимо от числа внутренних шагов. Валидатор отдельно ограничивает план восемью MCP-шагами. Каждый шаг использует MCP timeout: обычные инструменты ограничены 15 секундами, а `github_project_activity` получает 120 секунд на ограниченный backoff, пагинацию и сбор нескольких источников в больших репозиториях. Один и тот же выбор тайм-аута применяется агентом и MCP-клиентом; GitHub-клиент дополнительно использует более короткие request timeouts и общий ограниченный бюджет запросов.

Это позволяет полезному пайплайну иметь пять шагов, не разрешая модели бесконечную цепочку.

### 6. GitHub-сценарий состоит из пяти атомарных инструментов

Локальный MCP-сервер объявляет:

1. `github_repository_metadata` — repository metadata и languages;
2. `github_project_activity` — commits/contributors, issues, PR, Actions и releases за период;
3. `calculate_github_metrics` — детерминированные derived metrics и warnings;
4. `render_github_report` — Markdown без дополнительного LLM-вызова;
5. `save_report_to_file` — доменно-независимая запись произвольного текстового отчёта в файл.

GitHub HTTP-код и DTO размещаются в `src/mcp/github.rs`, а рендеринг и безопасная запись — в `src/mcp/report.rs`; `server.rs` только регистрирует handlers. `reqwest::Client` переиспользуется, отправляет обязательный `User-Agent` и следует REST version header. Пагинация идёт до конца временного диапазона либо безопасного лимита в 20 страниц и имеет общий бюджет запросов, увеличенный для аутентифицированного клиента. Каждый источник получает отдельный признак полноты; если большой репозиторий не помещается в лимит, зависимые метрики сопровождаются warning. Если asynchronous contributor statistics остаётся pending, клиент ограниченно пагинирует commits периода и считает уникальных авторов как fallback без возврата их идентификаторов наружу.

Первая версия продолжает работать без токена. Необязательный `GITHUB_TOKEN` загружается только процессом MCP-сервера из существующего локального `.env-mcp`, устанавливается как sensitive Bearer header общего `reqwest::Client` и не включается в DTO, trace, логи или ошибки. Ответы `403` с исчерпанным rate limit, `404` и сетевые ошибки преобразуются в безопасные MCP errors без вывода response headers или локальной среды. Для `202` статистические endpoints повторяются с ограниченным backoff; если отдельный источник остаётся pending, activity возвращает частичный результат с `unavailable` и warning, чтобы необязательная метрика не блокировала весь отчёт.

### 7. Сохранение отчёта отделено от GitHub и формата документа

`save_report_to_file` принимает `filename`, произвольный UTF-8 `content` и необязательный `overwrite`, но не интерпретирует предметную область или формат отчёта. Инструмент принимает только непустое leaf filename без абсолютного prefix, `/`, `\\`, `.` и `..`, отклоняет существующий symlink и записывает файл в текущий рабочий каталог MCP-сервера. Он объявляется non-read-only, поэтому подтверждение выполняется после подстановки фактического содержимого и имени.

По умолчанию существующий файл не изменяется. Для замены агент должен повторить вызов с `overwrite: true`; изменившиеся аргументы проходят отдельное подтверждение по общему правилу. Это позволяет использовать один инструмент для GitHub-, calendar-, session- и других отчётов, оставляя окончательное размещение файла пользователю.

Альтернативы: жёсткий каталог `reports/day19/` связывает общий инструмент с учебным сценарием, а произвольный относительный или абсолютный путь увеличивает область записи и сложность безопасного preview.

## Risks / Trade-offs

- [Большой trace может раздуть следующий модельный запрос] → ограничить восемью шагами и максимальным размером каждого output; GitHub tools возвращают агрегированные данные, а не полные bodies.
- [Модель может составить синтаксически верный, но бессмысленный порядок] → строгие схемы входов, fail-closed исполнение и явные ошибки в trace; семантическое качество остаётся ответственностью агента.
- [GitHub rate limit без токена низкий] → ограниченный request budget, понятная ошибка/предупреждение и отсутствие скрытых повторов; токен остаётся вне первой версии.
- [GitHub statistics иногда долго отвечает `202`] → ограниченный backoff внутри timeout, затем частичный activity result с `unavailable` и явным warning для зависимой метрики.
- [Изменяющий шаг после предыдущего write может провалиться] → не обещать транзакционность, фиксировать все completed writes и не выполнять автоматический rollback.
- [Synthetic tool name может совпасть с серверным] → зарезервировать префикс `fox_` и скрывать одноимённый server tool как конфликт конфигурации.
- [Добавление JSON Schema validator увеличивает зависимости и время сборки] → использовать библиотеку только на клиентской границе и компилировать схемы один раз на план.
- [Общий saver может заменить важный файл рабочего каталога] → запретить пути и symlink, по умолчанию запрещать overwrite и требовать отдельное подтверждение вызова с `overwrite: true`.

## Migration Plan

1. Добавить provider-neutral pipeline types и валидатор без включения synthetic tool.
2. Подключить `fox_execute_pipeline` к основным запросам и сохранить старый direct-call путь.
3. Добавить атомарные GitHub-инструменты и общий `save_report_to_file` в локальный сервер; новые инструменты останутся выключенными, пока пользователь не выберет их через `/mcp`.
4. Добавить регрессионные и end-to-end тесты на mock executor/HTTP fixtures.
5. Обновить документацию Дня 19 и пример запуска.

Rollback состоит в удалении synthetic definition и pipeline branch из агента; сохранённая конфигурация и одиночные MCP-инструменты остаются совместимыми, постоянная схема данных не меняется.
