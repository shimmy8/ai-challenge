## Context

См. мотивацию в `proposal.md`. Сейчас `Provider` содержит только OpenAI и Claude; выбор провайдера, проверка ключа, список моделей, сериализация сессий и HTTP-dispatch используют исчерпывающие `match`. `AgentSettings` всегда требует строковый API-ключ, а `providers.rs` отправляет OpenAI в жёстко заданный `/v1/responses`. При этом `RequestOptions`, `ApiAnswer` и цикл MCP уже provider-neutral, поэтому новый локальный transport можно добавить без изменения устройства агента, памяти и сессий.

Ollama предоставляет локальный OpenAI-compatible endpoint на `http://127.0.0.1:11434/v1`; Responses API с function tools доступен начиная с Ollama 0.13.3. Проект уже использует `reqwest` и JSON-модель Responses API, поэтому отдельный Ollama SDK не нужен.

## Goals / Non-Goals

**Goals:**

- Сделать Ollama полноценным третьим generation-провайдером во всех путях, использующих `AgentSettings` и общий request client.
- Переиспользовать существующий Responses payload, разбор текста, token usage и structured tool calls.
- Явно представить отсутствие credentials в модели конфигурации вместо фиктивного ключа.
- Сохранить загрузку старых конфигураций и сессий.
- Дать пользователю различимые диагностические сообщения для остановленного сервера, старой версии и отсутствующей модели.

**Non-Goals:**

- Устанавливать или обновлять Ollama из `fox-llm`, автоматически запускать daemon либо автоматически скачивать модель.
- Добавлять Ollama Cloud, удалённые endpoints или настройку произвольного base URL.
- Добавлять мультимодальные сообщения: текущий доменный `Message` остаётся текстовым.
- Переводить embedding/RAG-индексацию на Ollama; меняется только generation-провайдер, используемый агентом и query rewrite.
- Гарантировать одинаковое качество tool calling у всех установленных локальных моделей.

## Decisions

### 1. Ollama остаётся отдельным доменным провайдером

В `Provider` добавляется `Ollama`, а связанные `Display`, `all`, конфигурационная и session-сериализация расширяются новым стабильным значением `ollama`. Это сохраняет корректный статус CLI, метрики и происхождение сессии; Ollama не выдаётся за OpenAI только потому, что использует совместимый протокол.

Альтернатива — направлять Ollama через `Provider::Openai` с другим URL. Она отклонена: потребовался бы фиктивный ключ, статус и сохранённые сессии вводили бы пользователя в заблуждение, а OpenAI-specific фильтры моделей применялись бы к локальным именам.

### 2. Используется OpenAI-compatible Responses API Ollama

OpenAI transport разделяется на общий Responses-compatible путь и небольшие provider-specific настройки: URL, необходимость Bearer authorization и текст диагностического контекста. Ollama отправляет существующий payload в `http://127.0.0.1:11434/v1/responses` без заголовка авторизации. Общий разбор Responses сохраняет call IDs и текущий формат `function_call` / `function_call_output`, поэтому цикл MCP не получает второй параллельный протокол.

Альтернатива — нативный `/api/chat`. Она отклонена для первого варианта: пришлось бы поддерживать отдельные payload/response типы, синтезировать call IDs и отдельно сопоставлять tool results с именами функций. Если совместимость Responses окажется недостаточной, нативный адаптер можно добавить позднее, не меняя публичную capability.

### 3. Credentials становятся опциональными по свойству провайдера

`AgentSettings.api_key` представляется как `Option<String>`, а `Provider` получает явное свойство необходимости авторизации. Создание settings требует непустой ключ для OpenAI/Claude и допускает `None` только для Ollama. CLI использует то же свойство, чтобы полностью пропустить auth flow локального провайдера. HTTP-слой добавляет auth header только для провайдера, которому он требуется.

Альтернатива — хранить пустую строку или значение `ollama` как фиктивный ключ. Она отклонена, поскольку стирает различие между отсутствующей и ненужной авторизацией и повышает риск случайно отправить фиктивные credentials.

### 4. Список моделей читается через совместимый `/v1/models`

Ollama получает список локально доступных моделей через `GET /v1/models`, чей `data[].id` совместим с существующим базовым parser. Для Ollama принимается любое непустое имя; OpenAI сохраняет фильтрацию моделей, совместимых с Responses API, а Claude — текущие правила. Пустой список преобразуется в Ollama-specific подсказку установить модель.

Альтернатива — нативный `/api/tags`. Он предоставляет больше метаданных, но они не используются CLI, а второй формат ответа потребовал бы отдельного parser без пользовательской пользы.

### 5. Старые конфигурации нормализуются по полному реестру провайдеров

После десериализации `Config::load` добавляет отсутствующие provider entries с их defaults, не меняя существующие записи и порядок уже сохранённых значений. Legacy-миграция сразу создаёт OpenAI, Claude и Ollama. Модель Ollama по умолчанию — `qwen3.5:4b`; ключ отсутствует. Та же нормализация применяется к конфигам современного формата, созданным до этого изменения.

Это предпочтительнее специальной проверки только Ollama: реестр defaults станет единым и будущие провайдеры не потребуют новой ветки миграции.

### 6. Ошибки классифицируются на границе Ollama transport

Ошибка соединения с loopback получает сообщение о необходимости запустить Ollama. `404` или несовместимая форма ответа от `/v1/responses` получает подсказку обновить Ollama до версии с Responses API. Ответ о неизвестной модели получает подсказку выполнить `ollama pull <model>` или выбрать установленную модель. Остальные HTTP-ошибки проходят через общий безопасный formatter с ограничением размера body.

Автоматический fallback на OpenAI/Claude запрещён: он нарушил бы ожидание локального выполнения и мог бы вывести данные за пределы компьютера.

### 7. Provider-neutral пути остаются едиными

Память, режимы, стратегии сжатия, RAG query rewrite, метрики и изолированный MCP `ai.generate_text` продолжают строить `AgentSettings` и вызывать общий request client. Их отдельные алгоритмы не ветвятся по Ollama. Специальные изменения ограничиваются конфигурацией, transport/model discovery, CLI authorization и сериализацией идентичности провайдера.

Тестовый контур расширяет существующие пары OpenAI/Claude третьим провайдером там, где проверяется provider-neutral поведение; protocol-specific тесты проверяют Ollama URL, отсутствие auth, модельный parser и диагностическую классификацию.

## Risks / Trade-offs

- [Локальная модель может не поддерживать function calling, хотя сервер принимает tools] → не скрывать ошибку и рекомендовать совместимую модель; регрессионные тесты проверяют протокол, а не качество конкретной модели.
- [Responses API отсутствует в старой Ollama] → распознавать несовместимый endpoint и показывать минимальную поддерживаемую версию вместо общей сетевой ошибки.
- [Большой контекст может вызвать memory pressure на Mac с 16 ГБ] → не увеличивать существующие лимиты контекста автоматически; модель получает только контекст, сформированный текущей стратегией агента.
- [Нормализация конфига добавит enum-значение, неизвестное старой версии `fox-llm`] → перед изменением сохранять исходный config через существующий безопасный write flow; rollback требует удалить запись Ollama и выбрать OpenAI/Claude либо восстановить предыдущий файл.
- [Совместимый API Ollama может отличаться в деталях ошибок или usage] → считать usage необязательным как сейчас, держать парсеры толерантными к отсутствующим полям и закрепить поддерживаемые формы фикстурами.
- [Loopback HTTP не использует TLS] → endpoint жёстко ограничен `127.0.0.1`; произвольные удалённые URL в рамках изменения не поддерживаются.

## Migration Plan

1. Расширить enum и сериализацию провайдера, затем добавить нормализацию старых конфигураций и тесты миграции.
2. Сделать credentials опциональными и сохранить строгую проверку ключей облачных провайдеров.
3. Добавить Responses-compatible Ollama transport, список моделей и диагностические ошибки.
4. Подключить Ollama к CLI, reconfigure-путям, сессиям, метрикам и provider-neutral тестовым матрицам.
5. Запустить форматирование, Clippy и весь набор тестов; затем вручную проверить CLI и HTTP с установленными Ollama 0.13.3+ и `qwen3.5:4b`.

Для отката до предыдущей версии бинарника пользователь должен сначала переключить сохранённый `last_provider` на OpenAI или Claude и удалить запись `ollama` из локального config либо восстановить резервную копию конфигурации. SQLite-схема не меняется; сохранённые Ollama-сессии остаются данными, но старая версия не сможет распознать их provider до повторного обновления.
