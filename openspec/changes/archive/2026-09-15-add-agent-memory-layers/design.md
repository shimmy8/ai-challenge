## Context

`fox-llm` уже хранит полную историю сессии, summary, sticky facts и состояние веток в одной локальной SQLite-базе. `Agent` собирает сообщения и дополнительные инструкции, `SessionStore` отвечает за схему и восстановление, а интерактивные команды обрабатываются в `app.rs` и `cli.rs`. Существующие `summary` и `facts` имеют жизненный цикл сессии и поэтому остаются частью краткосрочной памяти, даже если помогают удерживать старые сведения в контекстном окне.

Изменение пересекает модель агента, prompt composition, SQLite, CLI и восстановление сессий, поэтому требует отдельной модели памяти и миграции без нарушения совместимости старых баз.

## Goals / Non-Goals

**Goals:**

- Сделать область жизни и источник данных каждого слоя памяти наблюдаемыми.
- Сохранить существующие стратегии управления контекстом без изменения их смысла.
- Обеспечить повторное использование профилей и задач между сессиями.
- Исключить неявное сохранение или автоматическое продвижение задачи по pipeline.
- Оставить `main.rs` только точкой сборки модулей и запуска.

**Non-Goals:**

- Автоматическая классификация сообщений по слоям памяти.
- Семантический поиск, embeddings и выбор части долговременных записей.
- Одновременное применение нескольких профилей или нескольких задач к одному запросу.
- Автоматическое исполнение всего pipeline одним запросом.
- Синхронизация памяти между устройствами или пользователями.

## Decisions

### 1. Слои различаются областью жизни, а не физическим файлом

Все данные остаются в `.fox-sessions.db`, но хранятся в разных сущностях:

- краткосрочная память — существующие `sessions`, `session_context`, ветки и checkpoints;
- долговременная память — новая таблица `profiles`;
- рабочая память — новая таблица `tasks`.

В `sessions` добавляются nullable-ссылки `profile_id` и `task_id`. Старые строки получают `NULL`, поэтому текущие сессии продолжают загружаться. Отдельная база на каждый слой была отклонена: она усложнила бы транзакционное сохранение и резервное копирование, не добавляя полезной изоляции для локального CLI.

Предлагаемая схема:

```sql
CREATE TABLE profiles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    instructions TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    todo TEXT NOT NULL,
    phase TEXT NOT NULL DEFAULT 'planning',
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Значения `tasks.phase` проверяются при чтении и записи как enum `TaskPhase`; повреждённое или неизвестное значение приводит к информативной ошибке вместо молчаливого сброса состояния.

### 2. Модель памяти находится в отдельном модуле

Новый `memory.rs` содержит `Profile`, `Task`, `TaskPhase` и агрегат активной памяти. SQLite-запросы остаются в `sessions.rs`, а `agent.rs` получает уже выбранные профиль и задачу и не знает, как они были загружены. Это сохраняет текущие границы ответственности и не раздувает `main.rs`.

### 3. Профиль и задача выбираются явно

`/profile` открывает меню: текущий профиль, выбор сохранённого, создание нового и отключение. `/task` открывает меню: текущая задача, продолжение существующей, создание новой, изменение TODO и переход к следующей фазе. Дополнительно поддерживаются детерминированные формы подкоманд для тестов и повторяемых сценариев, например `/task next` и `/task todo`.

Создание профиля или задачи записывается в БД сразу после подтверждения, а не после следующего ответа модели. Обычный текст диалога никогда автоматически не становится профилем, TODO или фазой.

### 4. Одна сессия использует не более одного профиля и одной задачи

Профиль и задача являются nullable-ссылками сессии. Если пользователь меняет профиль или задачу после первого сохранённого сообщения, CLI начинает новую сессию, сохраняя старую. Это предотвращает историю, разные части которой были сформированы несовместимыми профилями или задачами, и делает `profile_id`/`task_id` однозначным аудитом влияния памяти.

Задача существует независимо от сессии, поэтому её можно продолжить в новом диалоге. При загрузке старой сессии задача восстанавливается по ссылке, но используются её актуальные TODO и фаза: задача является единственным источником истины для рабочей памяти.

### 5. Prompt собирается из типизированных секций

Для основного запроса настройки формируются в следующем порядке:

```text
[инструкции выбранного режима ответа]

[инструкции долговременного профиля]

[рабочая память: id, название, phase, TODO]
[правила текущей фазы и запрет автоматического перехода]

[summary или sticky facts текущей сессии]
[последние сообщения текущей сессии]
```

Профиль намеренно является инструкцией пользователя и подмешивается в системный prompt. Состояние задачи, summary и facts маркируются как данные контекста, а не команды. Профиль и задача добавляются независимо от выбранной стратегии сжатия.

`planning` направляет агента на уточнение плана и TODO, `execution` — на выполнение согласованного TODO, `validation` — на проверку результата. Агенту разрешено текстом предложить `/task next`, но изменение состояния возможно только в CLI после подтверждения. Для `done` фазовая инструкция сообщает, что задача завершена и следующей фазы нет.

### 6. Переход реализуется детерминированной машиной состояний

Допустим только следующий переход:

```text
planning --> execution --> validation --> done
```

LLM не вызывает переход и не определяет сохранённое значение фазы. `/task next` показывает обе фазы, запрашивает подтверждение и затем выполняет одну SQLite-транзакцию. Такой подход выбран вместо разбора ответа модели: он наблюдаем, тестируем и не зависит от формулировок или провайдера.

### 7. Просмотр памяти отделён от редактирования

`/memory` показывает идентификатор и объём краткосрочной памяти, активный профиль с инструкциями и активную задачу с фазой и TODO. Команда ничего не изменяет. Редактирование выполняется только через `/profile` и `/task`, что позволяет явно установить слой назначения.

Статус-бар получает компактные имена активного профиля и задачи; подробный текст доступен через `/memory`, чтобы не переполнять интерактивную строку.

### 8. Фаза задачи отображается отдельной строкой над статус-баром

Когда выбрана задача, CLI рисует над существующим статус-баром отдельную строку `Этап задачи: <phase>`. Цвет задаётся централизованным отображением `TaskPhase`, чтобы текст в UI и машина состояний не могли разойтись:

```text
planning    -> blue
execution   -> yellow
validation  -> magenta
done        -> green
```

Без активной задачи дополнительная строка отсутствует. Функции показа и очистки статуса должны учитывать одну или две служебные строки, чтобы индикатор не попадал в scrollback и не затирал пользовательский prompt. После подтверждённого `/task next`, выбора задачи и восстановления сессии следующий цикл отрисовки использует актуальную фазу из рабочей памяти.

Отдельная строка выбрана вместо цветного фрагмента внутри общего статус-бара: фаза остаётся заметной при длинных именах модели, профиля или задачи и напрямую выполняет требование показывать этап над статусом.

## Risks / Trade-offs

- [Инструкции профиля могут конфликтовать с режимом ответа] → разделять секции, документировать порядок и показывать обе через `/memory`; в первой версии инструкции профиля добавляются после режима и уточняют его.
- [TODO может устареть относительно диалога] → агент может предложить обновление, но CLI сохраняет его только после явного подтверждения пользователя.
- [Переключение памяти неожиданно начинает новую сессию] → до переключения показывать понятное сообщение, автоматически сохранять текущую сессию и не удалять её.
- [Дополнительная строка может некорректно очищаться в узком терминале] → ограничивать её шириной терминала и тестировать симметричную отрисовку/очистку состояний с задачей и без неё.
- [Длинный профиль или TODO увеличит каждый запрос] → валидировать непустой ввод и ввести небольшие документированные лимиты длины; точные значения выбрать рядом с существующими ограничениями CLI при реализации.
- [Удаление профиля или задачи оставит ссылки из истории] → для первой версии не удалять сущности из `/profile` и `/task`; управление удалением остаётся вне scope.
- [Sticky facts дублируют сведения задачи или профиля] → считать их только производной памятью сессии и явно задавать рабочей памяти более высокий приоритет в prompt.

## Migration Plan

1. При открытии существующей БД создать `profiles` и `tasks` и добавить nullable-поля связей к `sessions`.
2. Считать `NULL` отсутствием активного профиля или задачи; не преобразовывать автоматически старые sticky facts.
3. После успешного ответа сохранять ссылки вместе с текущим snapshot сессии, а изменения профилей, TODO и фаз записывать немедленно отдельными транзакциями.
4. При ошибке миграции прекратить запуск с контекстной ошибкой, оставив исходные данные SQLite для повторной попытки.

Rollback к старой версии безопасен на уровне данных: старая версия игнорирует новые таблицы и поля. Созданные профили и задачи останутся в БД и снова станут доступны после возврата к новой версии.
