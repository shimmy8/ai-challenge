## Purpose

Обеспечить воспроизводимую подготовку локального Markdown-корпуса для RAG: обнаружение документов, сравнимое разбиение двумя стратегиями, генерацию embeddings и сохранение проверяемого индекса с происхождением каждого чанка.

## ADDED Requirements

### Requirement: CLI запускает отдельный режим индексации
Система SHALL предоставлять неинтерактивный startup-режим `index`, который принимает повторяемые локальные источники, стратегию `fixed`, `structural` или `all`, путь к выходному индексу и необязательный `--comparison-output`. При отсутствии источников система SHALL рекурсивно индексировать Markdown-файлы из `reports/` и `openspec/specs/`; при отсутствии стратегии система SHALL выполнять обе стратегии. Путь к embedding-конфигурации SHALL быть фиксирован как `.fox-embeddings.json` в корне проекта и SHALL не переопределяться параметром CLI.

#### Scenario: Индексация корпуса по умолчанию
- **WHEN** пользователь запускает `fox-llm index` из корня проекта без дополнительных источников и параметров стратегии
- **THEN** система обнаруживает `.md`-файлы в `reports/` и `openspec/specs/`, выполняет `fixed` и `structural` и записывает результат в `.fox-index.db`

#### Scenario: Явно заданные источники
- **WHEN** пользователь передаёт один или несколько файлов или каталогов через `--source`
- **THEN** система индексирует поддерживаемые Markdown-файлы только из этих источников в детерминированном порядке

#### Scenario: Корпус пуст или недоступен
- **WHEN** ни один читаемый Markdown-документ не найден либо указанный источник недоступен
- **THEN** команда завершается с понятной ошибкой и не публикует частично сформированный запуск индексации

#### Scenario: Альтернативного пути к embedding-конфигурации нет
- **WHEN** пользователь запускает индексацию
- **THEN** система загружает `.fox-embeddings.json` из корня проекта и отклоняет неизвестные аргументы, пытающиеся указать другой файл конфигурации

### Requirement: Fixed chunking сохраняет контролируемое перекрытие
Стратегия `fixed` SHALL делить нормализованный текст по числу Unicode-символов с настраиваемыми положительными `chunk_size` и `chunk_overlap`, причём overlap SHALL быть меньше размера чанка. Граница SHALL по возможности переноситься на конец абзаца или строки без создания пустых чанков; значения по умолчанию SHALL составлять 1200 и 200 символов соответственно.

#### Scenario: Длинный документ разбивается с overlap
- **WHEN** документ превышает настроенный `chunk_size`
- **THEN** система создаёт упорядоченные непустые чанки, соседние чанки разделяют не более настроенного overlap, а ни один обычный чанк не превышает `chunk_size`

#### Scenario: Недопустимые параметры chunking
- **WHEN** `chunk_size` равен нулю либо `chunk_overlap` не меньше `chunk_size`
- **THEN** команда отклоняет параметры до чтения embedding API и изменения опубликованного индекса

### Requirement: Structural chunking следует структуре Markdown
Стратегия `structural` SHALL делить документ по Markdown-заголовкам, сохранять иерархический путь заголовков как секцию и использовать тот же максимальный размер и overlap для дополнительного разбиения раздела, который не помещается в один чанк. Текст до первого заголовка SHALL относиться к секции документа.

#### Scenario: Разделы Markdown становятся отдельными чанками
- **WHEN** документ содержит несколько заголовков и каждый соответствующий раздел не превышает максимальный размер
- **THEN** текст разных разделов не смешивается в одном чанке, а каждый чанк содержит путь своей секции

#### Scenario: Большой раздел получает дочерние чанки
- **WHEN** один Markdown-раздел превышает максимальный размер
- **THEN** система дополнительно делит только этот раздел с настроенным overlap и сохраняет одинаковый путь секции у получившихся чанков

### Requirement: Каждый чанк имеет воспроизводимые метаданные
Система SHALL сохранять для каждого чанка как минимум `chunk_id`, относительный `source`, `title`, `section`, стратегию, порядковый номер и текст. `title` SHALL браться из первого заголовка первого уровня либо из имени файла, `section` SHALL содержать ближайший путь заголовков либо обозначение уровня документа, а `chunk_id` SHALL быть уникальным и стабильным для одинакового источника, стратегии, параметров и содержимого.

#### Scenario: Повторное разбиение неизменного корпуса
- **WHEN** один и тот же корпус дважды разбивается с одинаковой стратегией и параметрами
- **THEN** оба запуска создают одинаковую последовательность `chunk_id` и метаданных

#### Scenario: Одинаковый текст встречается в разных источниках
- **WHEN** два документа содержат одинаковый фрагмент текста
- **THEN** их чанки имеют разные `chunk_id` и сохраняют собственные `source`, `title` и `section`

### Requirement: Embedding provider настраивается независимо от агента
Система SHALL отделять генерацию embeddings от загрузки, chunking, хранилища и chat-провайдеров агента. `.fox-embeddings.json` SHALL задавать provider, endpoint, model, dimensions, batch size и credentials; индексатор SHALL использовать только этот файл и SHALL не получать embedding-настройки или credentials из `.fox-llm.json`. Provider factory SHALL выбирать embedding adapter по полю provider, а первая реализация SHALL поддерживать OpenAI-compatible endpoint с OpenAI `text-embedding-3-small` как конфигурацией по умолчанию.

#### Scenario: Конфигурация OpenAI по умолчанию
- **WHEN** `.fox-embeddings.json` задаёт OpenAI-compatible provider, endpoint OpenAI, `text-embedding-3-small`, размерность 1536 и действующий API key
- **THEN** индексатор создаёт adapter только для embedding pipeline и не меняет выбранный provider или модель интерактивного агента

#### Scenario: Переключение на локальный совместимый endpoint
- **WHEN** `.fox-embeddings.json` указывает локальный OpenAI-compatible endpoint, его модель, размерность и при необходимости credentials
- **THEN** индексатор использует локальный endpoint без изменения `.fox-llm.json`, Agent, chat-provider flow или MCP runtime

#### Scenario: Конфигурация отсутствует или некорректна
- **WHEN** `.fox-embeddings.json` отсутствует, содержит неизвестный provider, пустую модель, некорректный endpoint, нулевую размерность или нулевой batch size
- **THEN** команда `index` завершается до сетевого запроса и изменения опубликованного индекса с сообщением, указывающим на `fox-embeddings.example.json`

#### Scenario: Ошибка embedding-конфигурации изолирована от агента
- **WHEN** `.fox-embeddings.json` отсутствует или повреждён, а пользователь запускает обычный интерактивный режим либо MCP-сервер
- **THEN** система не читает embedding-конфигурацию и сохраняет прежний агентский или MCP-flow

### Requirement: Embeddings создаются пакетно через выбранный adapter
Выбранный embedding adapter SHALL отправлять новые чанки пакетами настроенного размера, возвращать vectors в исходном порядке и сообщать model, фактическую dimensions и usage tokens. Модель и фактическая размерность SHALL сохраняться с каждым вектором.

#### Scenario: Успешная пакетная генерация
- **WHEN** для новых чанков настроенный endpoint и credentials доступны, а API возвращает по одному вектору на каждый вход
- **THEN** система сопоставляет ответы исходному порядку чанков и сохраняет модель, размерность, вектор и сообщённое API потребление токенов

#### Scenario: Обязательные credentials отсутствуют
- **WHEN** индексация требует новых embeddings, но выбранный provider требует API key, а поле credentials пусто
- **THEN** команда завершается до сетевого запроса с инструктивной ошибкой и не повреждает ранее опубликованный индекс

#### Scenario: Некорректный ответ embedding API
- **WHEN** API возвращает ошибку, неожиданное число векторов либо непоследовательные размерности
- **THEN** запуск считается неуспешным и его частичные данные не становятся текущим индексом

### Requirement: SQLite-индекс сохраняет данные атомарно и переиспользует embeddings
Система SHALL хранить документы, чанки, метаданные, embedding-векторы и сведения о запусках в отдельной SQLite-базе. Вектор SHALL храниться в переносимом формате вместе с размерностью. Перед запросом к провайдеру система SHALL искать совместимый embedding по хешу нормализованного текста, модели и размерности; успешный запуск SHALL атомарно заменять данные выбранной стратегии, не удаляя результат другой стратегии.

#### Scenario: Повторная индексация неизменного корпуса
- **WHEN** совместимые embeddings для всех чанков уже присутствуют в индексе
- **THEN** система не отправляет эти тексты провайдеру, помечает embeddings как переиспользованные и публикует новый успешный запуск

#### Scenario: Изменился один документ
- **WHEN** повторная индексация меняет только часть чанков корпуса
- **THEN** система запрашивает embeddings только для новых хешей и переиспользует остальные совместимые векторы

#### Scenario: Сбой не уничтожает предыдущий индекс
- **WHEN** чтение, chunking, embedding или запись завершается ошибкой
- **THEN** последний успешный набор чанков каждой стратегии остаётся доступным без частичной замены

### Requirement: Система формирует сравнение стратегий
При запуске обеих стратегий система SHALL вывести и сохранить машинно-читаемое сравнение, содержащее для каждой стратегии количество документов и чанков, минимальный, максимальный, средний и медианный размер чанка, долю чанков с определённой секцией, число новых и переиспользованных embeddings, токены API и длительность. При наличии `--comparison-output` система SHALL атомарно записать тот же JSON в указанный путь после успешной публикации индекса.

#### Scenario: Сравнение полного корпуса
- **WHEN** запуск `all` успешно завершает обе стратегии
- **THEN** система выводит симметричные метрики `fixed` и `structural` и сохраняет их в записи запуска, пригодной для отчёта дня 21

#### Scenario: Все embeddings взяты из кеша
- **WHEN** запуск не отправляет новых текстов embedding API
- **THEN** число API tokens этого запуска равно нулю, а число переиспользованных embeddings отражает обработанные чанки

#### Scenario: Экспорт сравнения
- **WHEN** запуск `all` с `--comparison-output reports/day21/chunking-comparison.json` успешно завершён
- **THEN** указанный файл атомарно содержит полный JSON сравнения без embedding-векторов, credentials и текстов чанков

### Requirement: Команда сообщает безопасный прогресс индексации
Команда `index` SHALL по умолчанию выводить в `stderr` русскоязычные статусы основных этапов: обнаружение документов, chunking каждой выбранной стратегии, проверку кеша, начало и завершение каждой embedding-партии, публикацию SQLite и запись comparison export. До сетевого ожидания система SHALL вывести номер партии и количество отправляемых текстов, а после ответа — накопительный прогресс, API tokens и длительность. Итоговое сравнение SHALL оставаться в `stdout`. Progress-вывод SHALL быть построчным, пригодным для обычного терминала и CI, и SHALL не требовать отдельного CLI-флага.

Каждый embedding-запрос SHALL иметь timeout 60 секунд. Timeout SHALL завершать запуск понятной безопасной ошибкой и SHALL не публиковать частичный индекс.

#### Scenario: Пользователь видит активность долгого запуска
- **WHEN** индексатор обнаруживает документы, разбивает их, проверяет кеш и отправляет новые тексты embedding provider
- **THEN** `stderr` содержит последовательные статусы этапов и строки до и после каждой партии, включая `batch N/M`, число текстов, накопительный прогресс, токены и длительность

#### Scenario: Полное попадание в кеш
- **WHEN** все embeddings выбранной стратегии найдены в SQLite
- **THEN** progress-вывод сообщает число cache hits и ноль новых embeddings, не выводит фиктивную embedding-партию и продолжает к публикации

#### Scenario: Embedding endpoint не отвечает
- **WHEN** embedding-запрос не завершается за 60 секунд
- **THEN** команда завершается с безопасной ошибкой timeout, а предыдущий опубликованный индекс остаётся доступным

#### Scenario: Progress не раскрывает данные корпуса и credentials
- **WHEN** команда выводит успешный прогресс либо ошибку любого этапа
- **THEN** `stderr` не содержит API key, заголовок `Authorization`, полный embedding config, тексты чанков или их content hashes; допускаются только безопасный endpoint origin, model, агрегированные количества, длительности и локальные выходные пути

### Requirement: Индексация не раскрывает секреты
Система MUST создавать `.fox-embeddings.json` с правами `0600` на Unix и MUST не записывать его credentials в SQLite-индекс, JSON-сравнение, отчёт, stdout, stderr или сообщения ошибок. Репозиторий SHALL исключать `.fox-embeddings.json` из Git, SHALL содержать безопасный `fox-embeddings.example.json` без рабочего секрета и SHALL запрещать агентам читать, индексировать, анализировать, цитировать или выводить локальную embedding-конфигурацию. Диагностический вывод SHALL содержать только пути документов, агрегированные метрики и безопасные сведения об ошибках провайдера без заголовков авторизации и полного тела запроса.

#### Scenario: Провайдер отклоняет запрос
- **WHEN** embedding API возвращает ошибку авторизации или другую HTTP-ошибку
- **THEN** пользователь получает безопасное описание ошибки без API key, заголовка `Authorization` и содержимого всех отправленных чанков

#### Scenario: Репозиторий содержит только безопасный пример
- **WHEN** разработчик проверяет правила репозитория и example-конфигурацию
- **THEN** `.fox-embeddings.json` исключён из Git, `fox-embeddings.example.json` не содержит рабочего credential, а `AGENTS.md` явно разрешает агентам использовать только example
