## Context

Текущий `src/rag/retrieval.rs` строит embedding одного вопроса, вычисляет cosine similarity для всех опубликованных `structural`-чанков и передаёт первые пять в бюджете 6000 символов. `src/app.rs` выполняет retrieval до вызова `AgentPool`, а `src/rag/evaluation.rs` использует тот же путь для сравнения. Chat providers уже скрыты за `RequestClient`, а embedding provider имеет отдельный интерфейс.

Существующий индекс и его SQLite-схема не меняются. Исходный вопрос должен оставаться единственным user message в истории и сессии. Полные тексты кандидатов, vectors, credentials и служебные rewrite-инструкции не должны попадать в отчёты или диагностический вывод.

## Goals / Non-Goals

**Goals:**

- отделить baseline retrieval от enhanced pipeline, чтобы оба режима можно было воспроизводимо сравнить;
- повысить recall до фильтрации и точность итогового top-5;
- сделать фильтр и reranker детерминированными, объяснимыми и тестируемыми без сетевого вызова;
- учесть дополнительную цену query rewrite в метриках enhanced-режима.

**Non-Goals:**

- отдельная reranker- или cross-encoder-модель;
- BM25, полнотекстовый индекс или изменение chunking/SQLite-схемы;
- повторное сравнение plain без RAG;
- автоматический подбор весов или порога по контрольным ответам.

## Decisions

### 1. Query rewrite использует текущие chat provider и model

Новый provider-neutral `QueryRewriter` будет вызываться через существующий `RequestClient` с одним изолированным message и клоном `AgentSettings`, в котором temperature равна 0, а `instructions` полностью заменены отдельной служебной rewrite-инструкцией. Активные пользовательские mode-инструкции не наследуются; запрос отправляется без tool definitions. Для rewrite не создаётся полноценный `Agent`: это исключает подмешивание history, memory, profile, invariants, compression и tools. Интерфейс позволит подставить fake rewriter в тестах.

Модель получает исходный вопрос как отделённые недоверенные данные и должна вернуть одну строку поискового запроса без ответа на вопрос. Результат нормализуется по whitespace, ограничивается 512 Unicode-символами и отклоняется, если после нормализации он пуст. Из исходного вопроса извлекаются защищённые элементы: числовые токены, токены с цифрами, `_` или `-`, а также содержимое парных кавычек и backticks. После Unicode-aware case folding каждый защищённый элемент должен дословно присутствовать в rewrite; при потере элемента rewrite отклоняется с безопасной ошибкой. Такая консервативная проверка покрывает формально выделенные точные термины, а сохранение остальных имён обеспечивается инструкцией и параллельным поиском по исходному вопросу. Ошибка rewrite завершает enhanced RAG без fallback, чтобы не маскировать изменение эксперимента.

Альтернативы: эвристическое удаление стоп-слов не даёт качественного semantic rewrite; отдельная rewrite-модель требует новой конфигурации и credentials.

### 2. Оба query embedding вычисляются одним batch

Enhanced retrieval передаёт embedding provider массив `[исходный вопрос, rewritten query]`, валидирует два вектора и за один проход по structural-чанкам вычисляет `original_similarity` и `rewritten_similarity`. `semantic_score` равен максимуму из двух. Чанки сортируются по `semantic_score` по убыванию и `chunk_id` по возрастанию, после чего обрезаются до `candidate_k`.

Такое объединение не создаёт дублей и не требует двух загрузок индекса. Альтернатива с двумя независимыми top-20 и последующим union может создать до 40 кандидатов и делает смысл `candidate_k` менее однозначным.

### 3. Фильтр предшествует эвристическому reranking

После выбора candidate pool удаляются чанки с `semantic_score < min_similarity`. Enhanced retrieval возвращает типизированный исход: `Retrieved` с непустым финальным набором либо `NoRelevantContext` с безопасным trace и пустым набором. Во втором случае generation не вызывается. Интерактивный режим показывает понятное сообщение и завершает текущий вопрос, а evaluation фиксирует штатный исход и продолжает остальные режимы и вопросы; инфраструктурной ошибкой он не считается.

Для оставшихся кандидатов вычисляются:

- `content_coverage`: доля значимых токенов исходного и rewritten-запросов, встреченных в content;
- `metadata_coverage`: та же доля для объединённых `title` и `section`;
- `rerank_score = 0.70 * semantic_score + 0.20 * content_coverage + 0.10 * metadata_coverage`.

Токенизация приводит Unicode-текст к нижнему регистру, сохраняет буквы, цифры, `_` и `-`, удаляет дубли и небольшой фиксированный список русских и английских стоп-слов. Короткие буквенные токены отбрасываются, но числа и технические идентификаторы с `_` или `-` сохраняются. После расчёта кандидаты сортируются по `rerank_score` по убыванию и `chunk_id` по возрастанию.

Альтернатива только с threshold не может поднять кандидата с точными терминами; LLM-reranker увеличивает число сетевых вызовов и снижает воспроизводимость.

### 4. Baseline сохраняет алгоритм Дня 22

Baseline retrieval получает embedding только исходного вопроса, сортирует все чанки по cosine similarity и берёт top-`final_k` до применения прежнего бюджета контекста. Значение по умолчанию остаётся равным пяти, поэтому default-вызов воспроизводит алгоритм Дня 22. Baseline не вызывает rewriter, не применяет threshold и не пересчитывает ранг. Одинаковый `final_k` в обоих режимах не позволяет изменению размера финальной выдачи искажать сравнение алгоритмов.

Interactive `/rag on` использует enhanced pipeline. Baseline остаётся внутренним режимом сравнения, а не новой пользовательской `/rag`-командой.

### 5. Retrieval возвращает результат и trace

Вместо одного `Vec<RetrievedChunk>` enhanced path возвращает структуру, содержащую final chunks и безопасный trace: rewritten query, применённые параметры, candidate counts, rewrite usage/duration и metadata кандидатов до/после фильтрации. Candidate trace содержит только provenance и scores, но не content, vectors и hashes.

`RetrievedChunk.similarity` сохраняется как максимальная similarity для обратной совместимости CLI-вывода; добавляются поля двух similarities и `rerank_score`. `build_rag_prompt` по-прежнему получает только final chunks.

### 6. Параметры валидируются до сетевых вызовов

`RetrievalConfig` содержит `candidate_k`, `final_k`, `min_similarity` и `context_chars`. Значения по умолчанию: 20, 5, 0.40 и 6000. Валидация требует положительные K и budget, `candidate_k >= final_k` и конечный threshold в `[-1, 1]`. `rag-eval` принимает `--candidate-k`, `--final-k` и `--min-similarity`; интерактивный режим использует defaults. Валидация выполняется до query rewrite и любого embedding-запроса.

### 7. Day 23 evaluation сравнивает только два RAG-режима

Для каждого из тех же 10 вопросов сначала выполняется baseline retrieval и свежий generation-agent, затем query rewrite, enhanced retrieval и, только при наличии контекста, другой свежий generation-agent. Plain-запрос не выполняется. JSON хранит исходы `baseline_rag` и `enhanced_rag` на уровне каждого вопроса и в агрегатах, а также top-level retrieval settings. `NoRelevantContext` сериализуется как статус с пустыми sources, отсутствующим generation-ответом, нулевым fact coverage и фактическими затратами выполненных rewrite/embedding-этапов; агрегат отдельно считает такие исходы.

Токены и время rewrite хранятся отдельно и включаются в enhanced total. Атомарная запись отчёта и fail-closed поведение при сетевой, provider- или serialization-ошибке сохраняются; `NoRelevantContext` не запускает этот путь ошибки.

## Risks / Trade-offs

- [Порог 0.40 зависит от embedding model и корпуса] → параметр делается явным, записывается в отчёт и может быть изменён в evaluation CLI; default не выдаётся за универсальный.
- [LLM rewrite может потерять значимый термин] → retrieval всегда включает исходный query и использует максимум двух similarities.
- [Строгая проверка защищённых элементов может отклонить полезный перефразированный rewrite] → проверяются только элементы, для которых требуется точное воспроизведение; остальные имена защищаются инструкцией и исходным query.
- [Query rewrite добавляет chat latency и tokens] → вызов короткий, изолированный, с temperature 0; затраты измеряются отдельно.
- [Простой token overlap не понимает русскую морфологию и синонимы] → semantic score остаётся доминирующим, а lexical-часть лишь поднимает точные термины.
- [Эвристические веса могут переобучиться на 10 вопросах] → веса фиксируются до запуска и не подбираются автоматически по expected answers.
- [Фильтр может удалить единственный полезный чанк] → отчёт сохраняет candidate metadata до и после threshold, чтобы регрессия была видна.

## Migration Plan

1. Выделить baseline retrieval без изменения его алгоритма и закрепить текущие тесты.
2. Добавить изолированный rewriter, enhanced retrieval, trace и новые тесты.
3. Перевести interactive `/rag on` на enhanced path и обновить evaluation до baseline/enhanced-схемы.
4. Запустить сравнение на том же контрольном наборе и зафиксировать результат в `reports/day23/`.

Откат не требует миграции данных: достаточно вернуть interactive-вызов к baseline retrieval и прежнюю схему evaluation-отчёта; SQLite-индекс и сессии остаются совместимыми.
