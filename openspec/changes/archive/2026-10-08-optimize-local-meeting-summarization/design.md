## Context

См. `proposal.md` для мотивации. В `fox-llm` уже есть Ollama через локальный Responses API, единые типы ответа с token usage, разбор startup-режимов и примеры автономных `rag-eval`/`rag-chat-eval`. Текущая `qwen3.5:4b` имеет 4,2 млрд параметров и квантование `Q4_K_M`; интерактивная конфигурация управляет температурой, но `context_messages` ограничивает сообщения истории и не является token context window модели. Общий Responses payload не передаёт `num_ctx` или `num_predict`.

Ollama позволяет фиксировать `num_ctx` и `num_predict` в `Modelfile`, а локальный `/api/ps` сообщает фактически загруженный context length, размер, `size_vram` и quantization. Это позволяет провести эксперимент без изменения общего API облачных провайдеров и без копирования весов: профили будут лёгкими aliases одной базовой модели.

## Goals / Non-Goals

**Goals:**

- Выполнять полностью локальный, однопроходный и воспроизводимый benchmark без состояния интерактивной сессии.
- Разделить baseline, compact и balanced параметры и доказуемо зафиксировать фактически загруженные настройки Ollama.
- Автоматически оценивать структурную и фактическую корректность относительно синтетического эталона.
- Получить sanitized JSON, из которого можно независимо построить отчёт Дня 29.

**Non-Goals:**

- Не менять квантование, веса или семейство модели и не сравнивать облачных провайдеров.
- Не использовать RAG, MCP tools, профили персонализации, долговременную память или сохранённые сессии.
- Не превращать экспериментальные `num_ctx` и `num_predict` в пользовательские настройки всех провайдеров.
- Не измерять температуру корпуса или энергопотребление, если платформа не предоставляет надёжный показатель без привилегий.

## Decisions

### 1. Отдельный startup-режим `summarize-eval`

Новый режим принимает dataset, каталог профилей и output path, выполняет сценарии последовательно и не открывает интерактивный CLI. Он повторяет архитектурный подход существующих eval-команд, но находится в отдельном модуле суммаризации и не зависит от RAG.

Альтернатива — ручной прогон через интерактивный CLI. Она проще, но плохо воспроизводится, смешивает историю и системный контекст приложения и затрудняет сопоставление результатов с эталоном.

### 2. Параметры контекста и длины задаются Ollama aliases

В `reports/day29/profiles/` хранятся три `Modelfile`, каждый с `FROM qwen3.5:4b` и собственными `num_ctx`/`num_predict`. Temperature и benchmark prompt задаются конфигурацией запуска. Подготовительная команда создаёт aliases, не дублируя общие blobs весов. Перед benchmark выполняется preflight: aliases существуют, используют ожидаемое семейство и `Q4_K_M`.

Альтернатива — добавить поля в общий `ProviderConfig` и Responses payload. Она расширяет пользовательский API до подтверждения совместимости параметров у всех провайдеров и смешивает эксперимент с постоянной конфигурацией, поэтому отвергнута.

### 3. Профили фиксированы в версионируемой конфигурации

Начальные значения:

| Профиль | temperature | num_ctx | num_predict | prompt |
| --- | ---: | ---: | ---: | --- |
| baseline | 1.0 | 4096 | 1024 | общий |
| compact | 0.0 | 4096 | 256 | специализированный |
| balanced | 0.2 | 8192 | 512 | специализированный |

Конфигурация хранит также имя alias и пометку ожидаемого quantization. Итоговый оптимизированный профиль выбирается по качеству, затем по медиане времени и памяти при статистически равном качестве; название `balanced` не предрешает победителя.

Альтернатива — полный grid search. Для локальной модели он создаёт слишком много длительных генераций и тепловую нагрузку, а три интерпретируемых профиля дают достаточную причинную картину для учебного эксперимента.

### 4. Dataset содержит девять синтетических протоколов и эталоны

По три сценария относятся к short, medium и long. В каждом эталоне факты имеют стабильные ID; это позволяет сравнивать смысл через ID и нормализованные поля, не требуя дословного совпадения свободного summary. Протоколы включают позднюю отмену, замену ответственного, перенос срока, незакрытый вопрос и отсутствующие значения.

Альтернатива — реальные записи встреч. Они повышают риск раскрытия личной информации и не дают однозначного эталона.

### 5. Контракт ответа сочетает свободный summary и проверяемые сущности

`summary` ограничен пятью предложениями. Остальные поля используют объекты со стабильными ID из входного benchmark-маркера, текстом и нормализованными nullable полями. Парсер принимает только один JSON-объект; Markdown fences и внешний текст считаются нарушением контракта. Сырой ответ сохраняется только внутри sanitized результата для диагностики.

Альтернатива — оценивать свободный Markdown. Это проще для модели, но делает сравнение субъективным и не позволяет надёжно считать hallucination и stale decisions.

### 6. Отчёт различает качество, производительность и доступность метрик

Для каждого случая хранятся исход, отдельные проверки, elapsed, tokens и throughput. Агрегаты строятся по профилю и length tier. Первый запрос каждого alias отмечается cold; последующие — warm. После запроса runner читает `/api/ps` и связывает runtime metadata с точным alias. Недоступные значения остаются `null` с причиной.

Операционная память из `/api/ps` — наблюдение Ollama, а не полная память всей системы. Это ограничение явно отражается в отчёте; внешние привилегированные профилировщики не запускаются автоматически.

### 7. Новый модуль изолирован от MCP и RAG

Код benchmark размещается в `src/summarization/` и экспортируется через его `mod.rs`; startup-dispatch остаётся в `app.rs`, а `main.rs` содержит только декларацию модуля. Модуль переиспользует provider-neutral запрос и общие типы ответа, но не создаёт сессии и не изменяет пользовательскую конфигурацию.

### 8. Progress-логи идут в stderr и содержат только allowlist полей

Runner выводит события `start`, `preflight`, `case_start`, `case_done`, `aggregate` и `report_written`. В них разрешены только порядковый номер, общее число запусков, безопасные ID сценария/профиля, cold/warm, pass/fail, elapsed, token counts и путь итогового отчёта. Идентификаторы очищаются от управляющих символов; transcript, raw answer, benchmark prompt, HTTP body и локальная конфигурация не логируются.

Альтернатива — печатать полные запросы и ответы для диагностики. Она упрощает ручной разбор, но противоречит безопасной наблюдаемости и создаёт риск публикации содержимого при записи терминала.

## Risks / Trade-offs

- [Modelfile alias отсутствует или создан с другими параметрами] → Добавить явную подготовительную команду и preflight по `/api/show` и `/api/ps`; не продолжать со скрытым fallback.
- [Контекст 4096 обрежет часть medium/long входов до вызова или на стороне модели] → Сохранять фактический input token count и context length; считать потерю фактов частью результата профиля, но отклонять случаи, где prompt плюс обязательный output физически не помещаются в заявленный профиль.
- [Семантически верный текст не совпадает дословно с эталоном] → Проверять стабильные fact IDs и нормализованные structured fields; свободный summary оценивать только по ограничению длины и отсутствию запрещённых утверждений.
- [Порядок прогонов и нагрев искажают время] → Чередовать профили по сценариям, явно маркировать cold/warm и приводить медиану и диапазон, а не только среднее.
- [Один запрос может завершиться ошибкой или невалидным JSON] → Сохранять диагностируемый провал и продолжать независимые случаи; фатальными считать только ошибки dataset, preflight и невозможность атомарно записать результат.
- [Пиковая системная RAM не совпадает с `size_vram`] → Называть показатель именно loaded model memory и не выдавать его за полное потребление процесса или системы.
- [Ошибка провайдера может содержать фрагмент HTTP-ответа] → Пропускать сообщения progress-логов через очистку управляющих символов и ограничение длины; подробная sanitized диагностика остаётся только в JSON-результате.

## Migration Plan

1. Добавить новый startup-режим и benchmark fixtures без изменения существующей конфигурации.
2. Создать Ollama aliases из версионируемых `Modelfile` перед реальным прогоном и проверить их metadata.
3. Выполнить benchmark, сохранить sanitized JSON и подготовить `reports/day29/README.md`.
4. При откате удалить aliases стандартной командой Ollama и удалить новый startup-режим/артефакты; существующие модели, конфигурация и сессии не изменяются.
