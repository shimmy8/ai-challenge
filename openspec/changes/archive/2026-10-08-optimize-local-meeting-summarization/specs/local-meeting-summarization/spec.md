## Purpose

Обеспечить воспроизводимую оптимизацию локальной Ollama-модели для преобразования русскоязычных протоколов встреч в краткое, фактически точное и машинно-проверяемое актуальное резюме.

## ADDED Requirements

### Requirement: Benchmark dataset is deterministic and safe
Система SHALL принимать машинно-читаемый набор синтетических протоколов с уникальными идентификаторами, категориями длины `short`, `medium` или `long` и эталонными решениями, задачами, открытыми вопросами и рисками. Система MUST валидировать весь набор до первого запроса к модели и MUST NOT требовать реальных личных диалогов, credentials или содержимого локальных env-файлов.

#### Scenario: Valid benchmark dataset
- **WHEN** набор содержит валидные уникальные сценарии всех трёх категорий длины и полный эталон для каждого сценария
- **THEN** система принимает набор и выполняет каждый сценарий независимо

#### Scenario: Invalid dataset is rejected before generation
- **WHEN** набор содержит повторяющийся ID, неизвестную категорию, пустой протокол или некорректный эталон
- **THEN** система завершает запуск с понятной русской ошибкой до первого запроса к Ollama и не создаёт частичный успешный отчёт

### Requirement: Summary output follows a strict factual contract
Для каждого протокола система SHALL запрашивать ровно один JSON-объект с полями `summary`, `decisions`, `action_items`, `open_questions` и `risks`. Итог SHALL отражать только актуальные явно подтверждённые сведения: более позднее подтверждённое изменение заменяет прежнее, отменённые решения не считаются актуальными, а отсутствующие владелец или срок представлены как `null` и не выдумываются.

#### Scenario: Later decision supersedes an earlier decision
- **WHEN** протокол содержит предварительное или подтверждённое решение, которое позднее явно отменено или заменено
- **THEN** итог содержит актуальную версию и не выдаёт отменённую версию за действующее решение

#### Scenario: Action item has missing details
- **WHEN** протокол фиксирует задачу без владельца или срока
- **THEN** соответствующее отсутствующее поле равно `null`, а модель не подставляет предполагаемое значение

#### Scenario: Output contains prose outside JSON
- **WHEN** модель добавляет Markdown, пояснение или иной текст вне единственного JSON-объекта
- **THEN** результат сценария помечается как нарушивший контракт и сохраняется как диагностируемый провал

### Requirement: Evaluation profiles isolate tuning variables
Система SHALL сравнивать профили `baseline`, `compact` и `balanced` на одной локальной модели `qwen3.5:4b` с одним уровнем квантования `Q4_K_M`. Профили SHALL фиксировать prompt, `temperature`, `num_ctx` и `num_predict`; изменение весов, размера модели, RAG, MCP, профиля пользователя, долговременной памяти или истории диалога в рамках сравнения MUST NOT допускаться.

#### Scenario: Profiles use the same quantized model
- **WHEN** запускается сравнительный benchmark
- **THEN** каждый профиль использует `qwen3.5:4b` с `Q4_K_M`, а отчёт фиксирует идентичность модели и различающиеся настройки генерации

#### Scenario: Profile model is missing or incompatible
- **WHEN** требуемый локальный профиль не установлен, Ollama недоступна или обнаружено несовместимое квантование
- **THEN** система возвращает понятную русскую ошибку и не подменяет профиль облачным провайдером или другой моделью

#### Scenario: Scenario execution is isolated
- **WHEN** система переходит к следующему протоколу или профилю
- **THEN** новая генерация не получает сообщения, summary, память, tool results или состояние предыдущего запуска

### Requirement: Quality scoring is reproducible
Система SHALL проверять каждый ответ относительно эталона и сохранять отдельные результаты для JSON-валидности, полноты решений и задач, точности владельцев и сроков, обработки отмен, отсутствия неподтверждённых фактов и соблюдения ограничения summary не более пяти предложений. Агрегаты SHALL вычисляться отдельно для каждого профиля и категории длины, чтобы потеря длинного контекста не скрывалась общей средней.

#### Scenario: Fully correct summary
- **WHEN** ответ валиден, содержит все актуальные эталонные сведения, не содержит отменённых или придуманных фактов и соблюдает ограничение длины
- **THEN** сценарий помечается полностью пройденным и увеличивает успешный агрегат своего профиля и категории длины

#### Scenario: Valid JSON contains a factual error
- **WHEN** синтаксически валидный ответ теряет обязательное решение, назначает неверного владельца или возвращает отменённое решение
- **THEN** соответствующие проверки и весь сценарий помечаются проваленными без подмены успехом JSON-парсинга

### Requirement: Performance and resource observations are comparable
Система SHALL для каждого запроса сохранять длительность, доступные input/output token counts и вычисляемую скорость output tokens per second. Система SHALL получать от локальной Ollama доступные metadata загруженной модели, включая фактическую длину контекста, размер модели, использование VRAM или unified memory и уровень квантования, и SHALL отделять первый холодный запуск профиля от прогретых повторов.

#### Scenario: Ollama exposes complete runtime metadata
- **WHEN** после генерации Ollama сообщает токены и metadata загруженной модели
- **THEN** отчёт содержит длительность, токены, throughput, context length, model size, loaded memory size и quantization для соответствующего профиля

#### Scenario: Optional resource metric is unavailable
- **WHEN** Ollama или платформа не сообщает отдельный показатель ресурса
- **THEN** отчёт сохраняет `null` и явную причину недоступности вместо нулевого или выдуманного значения

### Requirement: Results are sanitized and written atomically
Система SHALL атомарно сохранять машинно-читаемый результат и SHALL поддерживать итоговый Markdown-отчёт в `reports/day29/`. Артефакты MUST содержать конфигурации профилей, безопасные синтетические входы, проверки и агрегаты, но MUST NOT содержать API keys, authorization headers, содержимое локальных env-файлов, персональные диалоги или полный внутренний системный prompt приложения.

#### Scenario: Successful evaluation
- **WHEN** все запланированные сценарии обработаны, включая диагностируемые ошибки отдельных ответов
- **THEN** система атомарно публикует полный sanitized JSON с результатами и агрегатами, пригодный для подготовки отчёта

#### Scenario: Evaluation is interrupted
- **WHEN** процесс завершается до формирования полного результата
- **THEN** прежний успешный отчёт не повреждается и неполный временный файл не считается новым результатом

### Requirement: Execution progress is observable and safe
Команда SHALL писать в stderr последовательные progress-логи для старта, preflight каждого профиля, начала и завершения каждой пары сценарий/профиль, cold/warm состояния, краткого исхода проверок, агрегирования и атомарной публикации отчёта. Логи MUST использовать безопасные идентификаторы и числовые метрики и MUST NOT выводить текст протокола, сырой ответ, prompt, authorization data или содержимое локальных конфигураций с credentials.

#### Scenario: Successful run reports progress
- **WHEN** benchmark проходит preflight и обрабатывает сценарии
- **THEN** пользователь видит текущий порядковый номер из общего числа, безопасные ID сценария и профиля, cold/warm состояние, длительность, токены и pass/fail без содержимого входа или ответа

#### Scenario: Failure is logged safely
- **WHEN** preflight или отдельная генерация завершается ошибкой
- **THEN** stderr содержит этап, безопасный ID и очищенное краткое сообщение об ошибке без секретов и без полного HTTP payload
