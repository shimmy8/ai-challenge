## Context

См. мотивацию в `proposal.md`. Сейчас `mcp.rs` открывает короткое соединение только для handshake и `tools/list`, сохраняет у инструмента имя и описание и содержит локальный `echo`. `Agent::ask_inner` выполняет один текстовый запрос через `RequestClient`, затем проверяет итоговый черновик по инвариантам и сохраняет только строковые `Message`. OpenAI Responses API и Claude Messages API имеют разные wire-форматы tool definitions, calls и results, поэтому provider-specific данные нельзя добавлять в сохранённую модель истории.

Интерактивный клиент создаёт один агент, хотя `AgentPool` сохраняет возможность нескольких агентов. Любое подтверждение должно выполняться через внедряемый интерфейс, а не прямой ввод внутри сетевого или provider-модуля. CalDAV Яндекса использует WebDAV discovery, XML и iCalendar, а для личного аккаунта требует отдельный пароль приложения.

## Goals / Non-Goals

**Goals:**

- Добавить provider-neutral цикл structured tool calling с адаптерами OpenAI и Claude.
- Сохранить текущую строковую историю сессии и стратегии сжатия без миграции SQLite.
- Выполнять изменяющее состояние действие только после проверки инвариантов, валидации и точного пользовательского подтверждения.
- Создавать одно личное событие в явно выбранном календаре и достоверно сообщать исход.
- Сделать protocol/provider/CalDAV части тестируемыми без настоящей модели и аккаунта Яндекса.

**Non-Goals:**

- Постоянное MCP-соединение между пользовательскими запросами и поддержка нескольких MCP-серверов.
- Приглашения участников, проверка занятости, повторяющиеся события, напоминания, изменение или удаление событий.
- OAuth Яндекса, Яндекс 360 service applications и хранение секретов приложением.
- Параллельные подтверждения от нескольких агентов; интерактивный режим продолжает использовать один агент.
- Сохранение или повторное воспроизведение provider-specific tool trace после завершения запроса.

## Decisions

### Ввести provider-neutral модель одного модельного хода

`RequestClient` будет принимать request options с необязательными tool definitions и возвращать ход, содержащий текстовые части, structured tool calls и usage. Общие типы будут хранить стабильный `call_id`, имя и JSON-аргументы; `providers.rs` преобразует их в wire-формат OpenAI Responses или Claude Messages и обратно. Tool results передаются следующему ходу отдельным request-scoped transcript.

Инструменты включаются только для основного ответа. Суммаризация, подготовка контекста и invariant verifier вызывают тот же клиент с пустым списком инструментов, чтобы модель не могла инициировать внешнее действие во вспомогательном запросе.

Альтернатива — просить модель печатать JSON в тексте — отвергнута: это не нативный tool calling, допускает ложные срабатывания и не соответствует критерию задания.

### Хранить tool trace только до завершения текущего запроса

Перед первым модельным ходом агент создаёт ephemeral transcript из обычной истории. В него добавляются provider-normalized tool calls и results, пока модель не вернёт финальный текст. В `history` и `persisted_history` записываются только исходное пользовательское сообщение и проверенный итоговый ответ, поэтому SQLite и алгоритмы сжатия не меняют формат.

Цикл поддерживает не более трёх последовательных вызовов. Несколько вызовов, возвращённых одним модельным ходом, обрабатываются последовательно и учитываются в общем лимите; каждый изменяющий состояние вызов подтверждается отдельно.

Альтернатива — расширить `Message` всеми форматами провайдеров — потребовала бы миграции хранилища и связала бы сессии с конкретным API.

### Создать request-scoped MCP runtime

Для пользовательского запроса runtime устанавливает одно Streamable HTTP соединение, выполняет `tools/list`, сохраняет полные определения со входной схемой и annotations, фильтрует их по текущему allowlist и использует то же соединение для `tools/call`. Перед каждым вызовом имя повторно сверяется с этим снимком. После финального ответа либо ошибки сессия закрывается.

Если allowlist пуст, основной запрос работает без подключения. Если включённые инструменты есть, но настроенный сервер недоступен, запрос завершается понятной ошибкой вместо молчаливого продолжения без заявленных возможностей.

### Отделить разрешение действия от его выполнения

Агент зависит от интерфейсов `ToolExecutor` и `ToolApproval`. MCP runtime реализует выполнение, CLI-реализация approval строит детерминированный preview из уже разобранных и валидированных аргументов. В тестах обе зависимости заменяются scripted doubles. Для tool definition с `readOnlyHint=true` подтверждение не требуется; для отсутствующей annotation и для календарного инструмента применяется безопасное значение «требуется подтверждение».

Одобрение привязывается к каноническому имени и сериализованным аргументам. Любое изменение создаёт новую заявку. Отказ преобразуется в tool result `cancelled_by_user`, который позволяет модели корректно завершить ответ без выполнения.

### Проверять предлагаемое действие до побочного эффекта

При активных глобальных инвариантах агент выполняет отдельную проверку пользовательского запроса и канонического описания tool call до показа confirmation. Нарушение формирует существующий шаблонный отказ и не запускает инструмент. После всех tool results итоговый текст проходит текущую draft-проверку.

Успешное внешнее действие необратимо относительно rollback внутреннего `AgentRequestState`. Поэтому подтверждённый успешный tool result фиксируется отдельно от черновика. Если последующий вызов модели или verifier падает, CLI печатает детерминированное сообщение с безопасным summary выполненного действия и отдельно сообщает, что итоговый ответ не сформирован. Автоматический повтор записи не выполняется.

### Использовать CalDAV с паролем приложения для личного аккаунта

Сервер читает `YANDEX_CALDAV_USERNAME`, `YANDEX_CALDAV_PASSWORD` и необязательное `YANDEX_CALDAV_CALENDAR` только из окружения. `reqwest` выполняет Basic authentication к `https://caldav.yandex.ru`; значения секретов не входят в структуры ошибок, tool results или debug output.

Discovery последовательно получает principal, calendar-home-set и writable calendar collections. Если найден один доступный календарь, он выбирается автоматически. При нескольких календарях значение `YANDEX_CALDAV_CALENDAR` должно однозначно совпасть с display name; иначе вызов завершается до записи и перечисляет только безопасные названия.

OAuth отвергнут для текущего объёма: официальный пользовательский сценарий Яндекса для сторонних CalDAV-клиентов основан на отдельном пароле приложения, а service applications относятся к организациям Яндекс 360.

### Формировать валидное и идемпотентное iCalendar-событие

Аргументы инструмента десериализуются строгим типом. `start_at` и `end_at` принимаются как RFC 3339 со смещением, нормализуются и проверяются на `end > start`; для CalDAV они сериализуются в UTC. iCalendar writer экранирует текстовые поля и использует CRLF. Один UUID создаётся до PUT и применяется одновременно как `UID` и имя ресурса `<uuid>.ics`; повтор при определённой транспортной ошибке использует тот же URL и условный запрос, а неопределённый исход не запускает создание с новым UUID.

Для WebDAV XML используется отдельный парсер, для дат и часовых поясов — типизированная библиотека времени, для UID — генератор UUID. Endpoint инкапсулируется настройкой клиента, чтобы тесты направляли запросы в локальный mock.

### Передавать модели достоверный временной контекст

Каждый основной запрос получает отдельную системную секцию с текущими абсолютными датой/временем и зоной `Europe/Moscow`. Инструкция календарного инструмента требует абсолютные RFC 3339 значения и запрещает вызов при неизвестном времени начала либо длительности. Preview форматирует те же разобранные значения, которые будут переданы исполнителю.

Фиксированная зона выбрана для согласованного учебного сценария и текущего окружения пользователя. Поддержка настраиваемой зоны может быть отдельным изменением.

### Проверять слои независимо и одним end-to-end сценарием

Provider payload/parser tests покрывают OpenAI и Claude. Scripted provider проверяет последовательность «tool call → tool result → final text», лимит и отсутствие инструментов во вспомогательных запросах. Fake executor и approval покрывают allowlist, отказ и invariant preflight. Локальный mock WebDAV/CalDAV проверяет discovery, выбор календаря, Basic auth без утечки, PUT и тело iCalendar. Интеграционный MCP-тест вызывает инструмент через настоящий локальный transport, но направляет CalDAV в mock.

Ручная проверка запускает MCP-сервер с пользовательскими env vars, включает `create_calendar_event` через `/mcp`, отправляет полностью определённую фразу, подтверждает preview и визуально проверяет событие в веб-интерфейсе Яндекс Календаря.

## Risks / Trade-offs

- [CalDAV discovery Яндекса может отличаться для аккаунтов и нескольких календарей] → Проверять реальные XML-ответы только вручную без записи секретов, использовать стандартные свойства CalDAV и выдавать диагностическую ошибку без выбора «первого» календаря.
- [Модель может неверно интерпретировать относительную дату] → Передавать точный runtime context и показывать абсолютные значения до обязательного подтверждения.
- [Сеть может оборваться после успешного PUT] → Сохранять UID в рамках вызова, не повторять с новым UID и честно сообщать неопределённый исход.
- [После успешной записи может упасть финальный модельный ход] → Немедленно сохранять безопасный outcome и показывать пользователю детерминированное подтверждение внешнего действия отдельно от ошибки синтеза.
- [Provider APIs используют разные структуры tool calls] → Изолировать wire-типы в provider adapters и проверить зафиксированными JSON fixtures.
- [Пароль приложения обладает правом записи в календарь] → Не сохранять его в конфигурации, не логировать заголовки и рекомендовать отдельный отзывной пароль только для `fox-llm`.
- [Интерактивное подтверждение несовместимо с несколькими параллельными агентами] → В текущем CLI оставить один агент; многопользовательское approval scheduling вынести в отдельное изменение.

## Migration Plan

1. Добавить новые внутренние типы с пустым набором инструментов по умолчанию, сохранив обычные запросы без MCP без изменения поведения.
2. Расширить MCP descriptors/runtime и подключить tool loop только при непустом allowlist.
3. Добавить календарный инструмент и CalDAV adapter; без переменных окружения существующий `echo` и `/mcp` продолжают работать, а календарный вызов возвращает безопасную ошибку настройки.
4. Обновить документацию и выполнить ручную проверку на отдельном тестовом событии после автоматических тестов.
5. Для отката отключить `create_calendar_event` через `/mcp` либо удалить MCP endpoint из локальной конфигурации; схема `.fox-llm.json` и SQLite не требуют обратной миграции.
