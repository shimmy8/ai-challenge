## Context

См. мотивацию в `proposal.md`. Существующий индексатор сохраняет Markdown-чанки из `reports/` и `openspec/specs/` в `.fox-index.db`; enhanced retrieval не ограничивает поиск по подмножеству источников. `Agent::ask_rag` формирует grounded-ответ из переданных чанков, но намеренно отправляет запрос без MCP tools. Интерактивный агент подключается к нескольким MCP-серверам через общий router, а локальный `workspace` server сейчас объявляет только изменяющий состояние `save_report`.

Репозиторий уже содержит `.codegraph/`, однако CodeGraph является внешним локальным бинарником и не должен становиться обязательным условием для ответов по документации. Текущая реализация project help переиспользует историю основного агента для query rewrite и generation, поэтому предыдущий вопрос способен сместить следующий независимый ответ. Кроме того, внешний `workspace` MCP приходится запускать и регистрировать вручную. Все новые серверные handlers и процессы должны находиться в `src/mcp/`. Локальные secret-файлы запрещено читать, индексировать или включать в диагностику.

## Goals / Non-Goals

**Goals:**

- Переиспользовать существующие индекс, retrieval, grounded-контракт и MCP router.
- Давать `/help` контролируемый проектный контекст с явным происхождением данных.
- Изолировать каждый проектный вопрос от истории, summary и памяти основного агента.
- Автоматически предоставлять help-субагенту минимальный workspace MCP без ручной регистрации.
- Изолировать сбой документации, Git или CodeGraph и сохранять полезный частичный ответ.
- Сохранять внутреннюю проверку происхождения фактов, не перегружая пользовательский ответ источниками, цитатами и техническими идентификаторами.
- Ограничить дочерние процессы фиксированным workspace, временем и объёмом вывода.

**Non-Goals:**

- Индексация исходного кода embeddings или замена CodeGraph собственным анализатором.
- Индексация `openspec/changes/`, отчётов для `/help` или создание новой папки `docs/`.
- Добавление списка файлов, Git diff, автоматической переиндексации CodeGraph или фонового watcher.
- Изменение поведения `/help` без аргументов, обычного tool-calling или `/rag on|off`.
- Предоставление help-субагенту пользовательских MCP-серверов, `save_report` или иных изменяющих состояние инструментов.

## Decisions

### 1. Сохранить один SQLite-индекс и фильтровать project retrieval

Стандартный discovery добавит корневой `README.md` к существующим `reports/` и `openspec/specs/`. Retrieval configuration получит allowlist источников или эквивалентный predicate, применяемый до формирования кандидатов `/help`: точное совпадение `README.md` либо префикс `openspec/specs/`.

Это не дублирует embeddings и сохраняет текущую команду `index`. Отдельный `.fox-project-index.db` отклонён из-за двух баз, повторной индексации и риска рассинхронизации. Фильтрация только после top-k отклонена: нерелевантные отчёты могли бы вытеснить разрешённые проектные документы до фильтра.

### 2. Запускать внутренний help-only MCP вместе с приложением

Интерактивный startup создаёт отдельный loopback listener на `127.0.0.1:0`, получает назначенный ОС порт, запускает MCP handler в управляемой Tokio-задаче и подключает к нему выделенный клиентский runtime. Этот endpoint объявляет только `git_current_branch` и `codegraph_explore`: существующий `save_report` и пользовательские MCP-маршруты в него не входят. Внутренний сервер не записывается в `.fox-llm.json`, не отображается как пользовательская регистрация и завершается владельцем runtime при выходе из приложения.

Реальный HTTP MCP на случайном loopback-порту выбран вместо фиксированного порта и прямого вызова Rust-функций: это сохраняет требуемую MCP-границу, исключает конфликт портов и убирает ручную подготовку демо. Переиспользование общего `WorkspaceServer` без фильтра отклонено, потому что открыло бы субагенту `save_report`.

### 3. Создавать новый изолированный субагент для каждого вопроса

Каждый `/help <вопрос>` создаёт временный `Agent` с текущими provider/model settings, но с пустыми history, persisted history, summary, profile, task и long-term memory. Query rewrite получает пустой `RetrievalContext`, поэтому предыдущие реплики не влияют даже на отбор документов. После retrieval субагент получает только очищенный вопрос, разрешённые RAG-фрагменты и `SharedToolExecutor` внутреннего help-only MCP.

Субагент может самостоятельно вызывать доступные workspace tools в пределах обычных лимитов tool loop. Успешные результаты нормализуются в именованные источники `mcp://workspace/git_current_branch` и `mcp://workspace/codegraph_explore` и участвуют в grounded-проверке итогового ответа. После завершения временное состояние удаляется; основной агент локально сохраняет только очищенный вопрос и проверенный итоговый ответ.

Изоляция через новый `Agent` выбрана вместо очистки и восстановления существующего: она исключает утечки состояния при ошибках и делает независимость последовательных вопросов проверяемой. Предварительный детерминированный вызов tools координатором отклонён, поскольку пользователь требует прямого доступа субагента к специализированному MCP.

### 4. CodeGraph является workspace MCP tool

Новые project-inspection handlers располагаются в `src/mcp/workspace.rs` и регистрируются существующим `WorkspaceServer`. `codegraph_explore` запускает процесс как argv (`codegraph`, `explore`, `<question>`) с `current_dir` равным canonical workspace; shell не используется. Перед запуском проверяются непустой ограниченный вопрос и `.codegraph/` в корне.

Процесс выполняется с отдельным тайм-аутом. Stdout и stderr считываются с жёстким пределом; при тайм-ауте процесс завершается и дожидается reap. Результат содержит только статус и безопасный ограниченный текст. Секретные пути не передаются процессу как вход и не включаются в ошибки.

Прямое встраивание CLI в `app.rs` отклонено, потому что нарушило бы требование MCP и смешало UI с проектными процессами. Отдельный тип сервера отклонён: оба инструмента естественно принадлежат уже существующему workspace server.

### 5. Git-ветка получается тем же безопасным процессным слоем

`git_current_branch` выполняет Git с фиксированными аргументами относительно workspace и различает named branch, detached HEAD и ошибку «не репозиторий». Инструмент не принимает пользовательские аргументы и объявляется read-only. Использование команды Git выбрано вместо новой Rust-зависимости: Git уже является условием проекта, а операция мала и хорошо ограничивается.

### 6. `/help` имеет два явных режима

Точное `/help` остаётся синхронной локальной справкой и после списка печатает отдельную строку `Задайте вопрос о проекте: /help <вопрос>`. Префикс `/help ` с непустым остатком запускает асинхронный help-поток независимо от `rag_enabled`. В историю агента передаётся очищенный вопрос, поэтому технический синтаксис команды и MCP trace не сохраняются как диалог.

Проектный вопрос не использует текущую историю ни для query rewrite, ни для generation. Успешный ответ сохраняется в истории основного агента только после завершения изолированного потока; последующий `/help` всё равно начинает с пустого состояния. Project help не изменяет профиль, задачу, долговременную память или фазу задачи.

### 7. Частичные ошибки становятся метаданными контекста

Документационный retrieval и каждый MCP-вызов имеют независимый outcome. Успешный источник включается в generation; ошибка преобразуется в короткое безопасное ограничение, которое отражается пользователю, но не цитируется как факт проекта. Если после сбора нет ни одного содержательного источника, generation не запускается.

Это предпочтительнее fail-fast, потому что отсутствие CodeGraph не делает README бесполезным. Молчаливый fallback отклонён: пользователь должен понимать, что ответ построен без части ожидаемого контекста.

### 8. Разделить внутренний grounding и пользовательский ответ

Help-субагент использует специальный двухслойный контракт. Внутренний evidence envelope связывает утверждения с разрешёнными RAG-чанками и результатами help-only MCP и проходит существующие проверки происхождения и точности цитат. После успешной проверки renderer возвращает пользователю только содержательный текст ответа и именно его записывает в историю основного агента.

Разделы `Источники` и `Цитаты`, provenance metadata, `chunk_id`, `mcp://` URI, дословные evidence quotes и tool trace не включаются в пользовательский вывод. Короткое предупреждение о неполном или недоступном контексте остаётся допустимым, поскольку описывает качество ответа, а не раскрывает служебную атрибуцию.

Полный отказ от grounding отклонён: отсутствие видимых цитат не должно разрешать модели выдавать неподтверждённые сведения. Показ существующего RAG-формата отклонён как слишком технический для справочного workflow.

## Risks / Trade-offs

- **[Общий индекс был построен до добавления README]** → `/help` сообщает о необходимости повторить `fox-llm index`; README не читается напрямую в обход индекса.
- **[CodeGraph output велик или содержит нерелевантный код]** → лимит вывода, фиксированный query и общий grounded-контракт ограничивают влияние; документация остаётся отдельным источником.
- **[Внутренняя атрибуция случайно попадает в UI или историю]** → отдельный renderer принимает только проверенный текст ответа, а тесты запрещают заголовки источников, citations metadata, `chunk_id`, MCP URI и tool trace.
- **[Фильтрация уменьшает число кандидатов]** → фильтр применяется до ранжирования, а отсутствие релевантных документов допускает ответ по CodeGraph.
- **[Дочерний процесс зависает]** → timeout обязательно завершает и reap-ит процесс; тест покрывает отсутствие фонового процесса.
- **[Внутренний MCP не смог запуститься]** → обычный CLI и документационный retrieval продолжают работать, а пользователю показывается безопасное ограничение контекста.
- **[Субагент выполняет лишние tool calls]** → ему доступны только два read-only инструмента, сохраняются существующие лимиты вызовов, тайм-ауты и пределы результата.
- **[Фоновая задача MCP переживает приложение]** → единый владелец runtime хранит cancellation/shutdown handle и дожидается завершения сервера.
- **[Уточняющий `/help` больше не видит предыдущий вопрос]** → это намеренное свойство изоляции; пользователь формулирует каждый проектный вопрос самодостаточно.

## Migration Plan

1. Добавить фильтрацию retrieval и `README.md` в default discovery без изменения схемы SQLite.
2. Добавить и протестировать read-only workspace tools; существующий внешний `save_report` и его имя сохранить.
3. Добавить help-only вариант сервера, его автоматический startup/shutdown и выделенный MCP runtime.
4. Перевести `/help <вопрос>` на изолированный субагент с пустым retrieval context и прямым доступом только к help-only tools.
5. Обновить README и повторно выполнить `fox-llm index`, чтобы существующая база получила README-чанки.

Rollback выполняется возвратом к прежнему бинарнику: формат конфигурации и SQLite не меняется, внутренний endpoint не оставляет конфигурационных записей, а лишние README-чанки безопасно игнорируются старым retrieval.
