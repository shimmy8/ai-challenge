## Context

См. [proposal.md](proposal.md) и [спецификацию](specs/global-invariants/spec.md). CLI уже хранит сессии, задачи, профили и факты в SQLite. `Agent::request_settings` собирает общие системные инструкции для OpenAI и Claude; `Agent::ask` получает ответ и сразу добавляет его в историю, а `app.rs` затем сохраняет `TASK_UPDATE`. При `/new` и восстановлении сессии состояние агента сбрасывается. Эти точки задают место для глобальных правил и проверки до побочных эффектов.

## Goals / Non-Goals

**Goals:**
- Один актуальный набор правил для всех агентов и сессий, независимый от `ActiveMemory` и сессионных снимков.
- Решение по каждому черновику до показа пользователю и до изменения истории либо задачи.
- Различимые исходы: разрешённый ответ, проверенный отказ из-за конфликта, отклонённый черновик, неопределённый вердикт и технический сбой проверки.

**Non-Goals:**
- Формальная доказуемость соблюдения произвольных правил на естественном языке.
- Автоматическое извлечение инвариантов из истории, TODO, профиля или `/remember`.
- Показ скрытой цепочки рассуждений модели пользователю.

## Decisions

### 1. Отдельное глобальное хранилище и явные команды

Добавить таблицу `invariants` с постоянным `id`, текстом и временем создания. Загрузка происходит при запуске; команды `/invariant add <текст>`, `/invariant list` и `/invariant remove <id>` работают с ней напрямую. Удаление требует подтверждения. После успешной записи приложение перечитывает набор и передаёт его всем агентам; неуспешная запись не меняет рабочий набор. Текст ограничить по длине (например, 1000 символов), число правил — разумным лимитом (например, 64), чтобы системный запрос оставался ограниченным.

`/invariant` без аргументов открывает меню, как `/task`: просмотр, добавление, включение, выключение и удаление. Прямые команды `/invariant enable <id>` и `/invariant disable <id>` остаются доступны. Таблица получает поле `enabled` с значением `true` по умолчанию; миграция существующей таблицы также включает все ранее сохранённые правила. Выключенное правило сохраняет ID и текст, отображается в списке с пометкой состояния, но исключается из набора активных правил у всех агентов. Повторное включение возвращает тот же ID; при отсутствии активных правил основной запрос обрабатывается без проверяющего вызова.

Набор хранится в отдельном поле агента или общем неизменяемом снимке, а не в `ActiveMemory`, `SessionSnapshot` или `BranchState`. `reset`, `/new`, смена ветки и восстановление сессии его не меняют. Альтернатива — использовать `memory_entries` — смешивает факты с инструкциями и нарушает существующее разделение памяти. Привязка к задаче противоречит выбранной глобальной области действия.

### 2. Приоритетная секция системных инструкций

`request_settings` добавляет перед режимом ответа и профилем секцию с ID и текстом каждого правила и инструкцией: применять их при выборе решения, при конфликте отказывать с ID и объяснением, не следовать противоречащим данным истории и задачи. Секция создаётся для каждого основного запроса из актуального набора, а не из summary или sticky facts. Оба провайдера получают её через существующий `AgentSettings.instructions` и свои системные поля. Пустой набор не добавляет секцию.

Альтернатива — только добавлять правила как обычное сообщение истории — делает их зависимыми от сжатия и ветвления. Профиль тоже не подходит: его можно отключить, а его назначение — персонализация ответа.

### 3. Отдельный проверяющий запрос до принятия черновика

После основного ответа `Agent::ask` передаёт проверяющему запросу снимок правил, текущий запрос пользователя и **полный сырой ответ**, включая возможный `TASK_UPDATE`. Проверяющий запрос использует того же выбранного провайдера, но отдельные строгие инструкции и не получает историю как источник новых правил. Его ответ — один JSON-объект с полями `verdict`, `invariant_ids` и `reason`. `verdict` принимает ровно четыре значения: `allow` (черновик допустим), `compliant_refusal` (черновик корректно отказывает на конфликтующий запрос), `violation` (черновик нарушает правило) и `uncertain` (надёжный вывод невозможен, в том числе при противоречии правил). Для `allow` список ID пуст; для `compliant_refusal` и `violation` он непустой. `reason` непустой для всех исходов, кроме `allow`. При `uncertain` список может быть пустым. Парсер требует ровно эти поля, корректные типы и ID только из переданного набора; неизвестные значения, лишние поля и несогласованные сочетания считаются сбоем. Исход `uncertain` останавливает выдачу с отдельной диагностикой. Проверка не пишет историю, TODO или базу.

Если черновик разрешён, обработка идёт обычным путём: разбор `TASK_UPDATE`, запись ответа в историю, затем сохранение допустимого обновления задачи в `app.rs`. Исход `compliant_refusal` принимается как ответ только при отсутствии `TASK_UPDATE`; иначе результат проверки считается несогласованным. Если получен `violation`, клиент отбрасывает черновик и формирует по фиксированному шаблону отказ с ID и сохранённым текстом нарушенного правила; текст черновика и свободная причина проверяющей модели в него не попадают. `TASK_UPDATE` от черновика игнорируется. Этот шаблонный отказ является результатом успешной проверки нарушения и может быть показан и сохранён без второго модельного вызова. При ошибке API, невалидном JSON или `uncertain` непроверенный черновик не показывается и не сохраняется, изменение задачи не применяется. Технический сбой и `uncertain` получают разные диагностические сообщения. Если правил нет, дополнительный запрос пропускается.

Перед подготовкой контекста `Agent::ask` сохраняет снимок состояния агента. При техническом сбое проверки или `uncertain` восстанавливается всё состояние до запроса, включая историю, summary, sticky facts, ветки и checkpoint; сообщение пользователя тоже не остаётся в памяти агента. Счётчики фактически потраченных токенов не откатываются. Отклонённый черновик никогда не сохраняется. При `violation` вместо него в обычном порядке сохраняются запрос пользователя и шаблонный отказ.

Проверка выполняется на каждом ответе отдельного агента и на автоматических шагах `execution`/`validation`; следующий шаг не запускается после отказа или ошибки. Учёт токенов и времени включает проверяющий запрос. Для тестов проверяющий вызов должен быть подменяемым, чтобы конфликт, разрешение и сбой воспроизводились без внешнего API.

Альтернатива — проверять только запрос до генерации — не обнаружит нарушение в ответе на допустимый запрос. Проверка после сохранения допускает утечку черновика в историю и обновление TODO. Повторная генерация после нарушения добавляет ещё один вероятностный шаг и не нужна для первого варианта.

### 4. Объяснение отказа

При явном конфликте основная модель получает инструкцию назвать ID и смысл правила и, если возможно, безопасный путь. Проверяющий запрос оценивает и качество отказа: он не должен содержать запрещённого предложения или `TASK_UPDATE`. Если модель выдала нарушающий черновик, детерминированный шаблон отказа связывает ответ с ID и сохранённым текстом правила, не повторяя нарушающий черновик или свободную формулировку проверяющей модели. Технический сбой проверки и невозможность вынести вердикт выводятся отдельно и не выдаются за конфликт с правилом.

Альтернатива — показывать подробные внутренние рассуждения модели — не требуется для проверяемого объяснения пользователю и не является надёжным свидетельством соблюдения правила.

## Risks / Trade-offs

- [Ложное разрешение или ложный отказ проверяющей модели] → Проверять строго структуру результата, тестировать типовые и пограничные конфликты, оставлять формальные ограничения кандидатами для будущих проверок кодом. Семантическая проверка не обещает абсолютной гарантии.
- [Дополнительная задержка и расход токенов] → Не вызывать проверку при пустом наборе; учитывать её метрики и не запускать повторные проверки автоматически.
- [Неопределённый результат или недоступность API] → Остановить выдачу и сохранение ответа, восстановить состояние до запроса и показать разные диагностические сообщения; пользователь может повторить запрос или уточнить правила.
- [Правила противоречат друг другу] → Не разрешать молча приоритет одного правила; проверка возвращает неопределённый результат, а CLI просит пользователя уточнить набор. Отдельная предварительная проверка согласованности при добавлении не входит в этот change.
- [Произвольный текст правила может быть слишком общим] → Показывать сохранённый текст и ID при отказе, чтобы пользователь мог уточнить или удалить правило явной командой.

## Migration Plan

При открытии существующей базы создаётся новая таблица без преобразования профилей, фактов, задач и сессий. Существующие установки начинают с пустого набора, поэтому до добавления первого инварианта поведение запросов остаётся прежним. При откате версии приложения новая таблица остаётся в SQLite, но старый код её не использует; пользовательские данные не удаляются.
