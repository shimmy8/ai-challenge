## Purpose

Позволяет разработчику ставить цель на уровне проекта, после чего изолированный ассистент самостоятельно исследует несколько файлов, безопасно изменяет подтверждённые файлы и сообщает воспроизводимый результат.

## ADDED Requirements

### Requirement: Project command accepts a goal instead of file-level instructions
Команда `/project <цель>` SHALL принимать непустую цель на естественном языке и запускать один project workflow. Система MUST отклонять пустую цель до обращения к provider или MCP и MUST сохранять обычное поведение `/help` и основного диалога.

#### Scenario: Goal-level request starts project work
- **WHEN** пользователь вводит `/project Найди все места использования ToolExecutor`
- **THEN** система запускает project workflow с текстом цели без служебного префикса `/project`

#### Scenario: Empty project goal is rejected
- **WHEN** пользователь вводит `/project` либо только пробелы после команды
- **THEN** система показывает русскоязычную подсказку о синтаксисе и не вызывает provider или MCP

### Requirement: Every project goal uses a fresh isolated subagent
Система SHALL создавать новый временный субагент для каждого project workflow. Субагент MUST получать настройки текущего provider и активные глобальные инварианты, но MUST NOT получать историю, summary, профиль, активную задачу, долговременную память, RAG-контекст или пользовательский MCP registry основного агента. Субагент SHALL иметь доступ только к внутреннему project-only MCP и MUST NOT получать встроенный pipeline planner.

#### Scenario: Consecutive project goals are independent
- **WHEN** пользователь последовательно запускает две разные команды `/project`
- **THEN** второй субагент не получает цель, tool results или модельный контекст первого запуска

#### Scenario: Main-agent context is not exposed
- **WHEN** история основного агента содержит приватный текст, профиль и активную задачу
- **THEN** первый запрос project-субагента не содержит эти данные и объявляет только project-only tools

#### Scenario: Global invariant applies to a project write
- **WHEN** project-субагент предлагает изменение, конфликтующее с активным глобальным инвариантом
- **THEN** система отклоняет действие до пользовательского подтверждения по существующим правилам проверки инвариантов

### Requirement: The assistant researches project files before answering
Для содержательной цели project-субагент MUST самостоятельно вызвать хотя бы один read-only project tool до итогового ответа. При наличии `.codegraph/` запросы о символах, их использованиях, вызовах и зависимостях MUST начинаться с `codegraph_explore`; literal `search_files` SHALL использоваться только как fallback при отсутствии/ошибке CodeGraph либо для явно текстового поиска. После discovery субагент SHALL прочитать релевантные исходные файлы перед выводом. Для изменения файла субагент MUST сначала прочитать целевой файл либо подтвердить через список файлов, что новая цель отсутствует, и SHALL исследовать хотя бы один источник фактов, на котором основано изменение.

#### Scenario: API usage is found across files
- **WHEN** workspace содержит `.codegraph/`, минимум два исходных файла определяют или используют искомое API и пользователь просит найти все его использования
- **THEN** субагент сначала вызывает `codegraph_explore`, читает релевантные исходные файлы и итоговый ответ перечисляет фактические относительные пути и номера строк без широкого поиска по документации и без изменения workspace

#### Scenario: CodeGraph is unavailable for symbol lookup
- **WHEN** workspace не содержит `.codegraph/` либо `codegraph_explore` завершается ошибкой
- **THEN** субагент использует bounded `search_files` как fallback и читает минимум один найденный файл перед выводом

#### Scenario: Documentation update is grounded in code
- **WHEN** пользователь просит обновить документацию на основе текущего кода
- **THEN** субагент читает документацию и минимум один релевантный файл кода до предложения записи

#### Scenario: Model attempts to answer without research
- **WHEN** первый ответ модели не содержит project tool call для содержательной цели
- **THEN** workflow не представляет его как проверенный результат работы с проектом и сообщает, что исследование файлов не выполнено

### Requirement: File changes are explicit and reproducible
Project workflow SHALL поддерживать создание нового UTF-8 файла и полную замену существующего UTF-8 файла без удаления файлов. Замена существующего файла MUST ссылаться на SHA-256 версии, ранее прочитанной в том же workflow, а создание MUST явно требовать отсутствия цели. Повторный запуск той же цели над уже согласованным состоянием SHALL либо завершаться без вызова записи, либо возвращать успешный результат `changed=false` без изменения байтов файла.

#### Scenario: Existing documentation is updated
- **WHEN** субагент прочитал текущую версию Markdown-файла, пользователь подтвердил предложенный diff и SHA-256 остаётся актуальным
- **THEN** система атомарно записывает ровно подтверждённое UTF-8 содержимое и возвращает старый и новый hash, число записанных байтов, diff и `changed=true`

#### Scenario: A new project file is generated
- **WHEN** пользователь просит создать новый файл, цель отсутствует и пользователь подтверждает diff создания
- **THEN** система создаёт один обычный файл внутри workspace и возвращает его относительный путь, hash, размер, diff и `changed=true`

#### Scenario: Source changed after it was read
- **WHEN** содержимое существующего файла изменилось после чтения и перед подтверждённой записью
- **THEN** система отклоняет запись как stale, не заменяет новую версию и предлагает субагенту перечитать файл

#### Scenario: Repeated goal is already satisfied
- **WHEN** повторный project workflow вычисляет то же итоговое содержимое, которое уже хранится в цели
- **THEN** байты и metadata файла не меняются, а итоговый ответ явно сообщает об отсутствии изменений

### Requirement: Project result reports evidence and actual changes
После успешного workflow система SHALL показать итоговый ответ с фактически прочитанными или изменёнными относительными путями. Пути, только найденные discovery-инструментом, MUST быть отделены от действительно прочитанных и MUST NOT обозначаться как «Проверено». Если была запись, ответ MUST отличать подтверждённые записанные изменения от предложенных или отменённых и SHALL включать либо ограниченный unified diff, либо точную команду получения Git diff. Технические tool calls и полное содержимое tool results MUST NOT сохраняться как сообщения диалога; MAY сохраняться только очищенная цель и итоговый ответ.

Policy denial для запрещённого пути SHALL считаться проверенным безопасным исходом, а не отсутствием исследования. Итог MUST использовать детерминированный текст отказа, MUST NOT подтверждать существование запрошенного пути, повторять его имя или включать provider-generated описание и SHALL явно сообщать, что workspace не изменён.

#### Scenario: Read-only goal completes
- **WHEN** project workflow только искал и читал файлы
- **THEN** итог перечисляет использованные файлы и явно сообщает, что workspace не изменён

#### Scenario: Write goal completes
- **WHEN** один или несколько подтверждённых файлов успешно записаны
- **THEN** итог перечисляет каждый фактически изменённый путь и предоставляет ограниченный diff либо команду его получения

#### Scenario: Proposed write is cancelled
- **WHEN** пользователь отклоняет файловый diff
- **THEN** файл не изменяется, а итог не заявляет, что предложение было применено

#### Scenario: Secret file read is denied safely
- **WHEN** пользователь просит прочитать локальный env-файл или другой denylisted путь и project tool возвращает policy denial
- **THEN** workflow возвращает безопасный отказ без generic research error, имени/существования/содержимого цели и сообщает, что workspace не изменён
