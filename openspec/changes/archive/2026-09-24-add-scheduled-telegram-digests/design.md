## Context

См. мотивацию в `proposal.md`. Сейчас `--mcp-server` поднимает Streamable HTTP service, а фабрика создаёт отдельный `EchoServer` для каждой MCP-сессии. Сервер загружает только `.env-mcp`; конфигурация провайдеров находится в `.fox-llm.json`. CalDAV-клиент умеет обнаруживать календарь и создавать событие, но не читать диапазон. SQLite-хранилище сессий синхронное и принадлежит интерактивному процессу.

Фоновая сводка пересекает MCP, планирование времени, SQLite, CalDAV, провайдеры LLM и Telegram. Реализация должна сохранять существующую границу секретов: `.env-mcp` не читается клиентом и его значения никогда не становятся аргументами инструмента или модельным контекстом.

## Goals / Non-Goals

**Goals:**

- Один scheduler на процесс сервера, общий для всех MCP-сессий.
- Выполнение заданий без подключённого CLI с восстановлением после перезапуска.
- Предсказуемый конвейер `calendar -> deterministic digest -> optional LLM rewrite -> Telegram`.
- Наблюдаемые состояния запуска и отсутствие ложного подтверждения доставки.
- Тестируемые границы времени, хранилища и внешних клиентов без реальной сети.

**Non-Goals:**

- Универсальный cron, выполнение shell-команд или произвольных HTTP-заданий.
- Несколько получателей, выбор chat ID моделью и управление Telegram-ботом из чата.
- Полноценная очередь с несколькими процессами worker или распределённая блокировка.
- Использование истории, профиля, памяти или tool-calling интерактивного `Agent` в фоне.
- Гарантия доставки ровно один раз при неопределённом сетевом исходе.
- Автоматическая установка системного сервиса; документация покажет, что процесс должен запускаться отдельно и постоянно.

## Decisions

### 1. MCP-сервер является control plane и владельцем worker

`run_mcp_server` создаёт один `Arc<SchedulerRuntime>` до фабрики MCP-сессий, запускает его worker и передаёт clone handle каждому `FoxMcpServer`. Фабрика больше не создаёт независимое фоновое состояние. При остановке HTTP-сервера cancellation channel завершает worker.

Интерактивный агент только создаёт и управляет заданиями через MCP. В момент расписания worker напрямую запускает внутренний конвейер; он не вызывает собственный MCP endpoint и не требует открытого клиента.

Альтернатива — отдельный бинарник worker — дала бы лучшую изоляцию, но потребовала бы координации двух процессов и отдельной установки. Для локального задания один долгоживущий MCP-процесс проще и достаточно явно показывает архитектуру.

### 2. Отдельное SQLite-хранилище планировщика

Планировщик использует `.fox-scheduler.db`, а не добавляет таблицы в `.fox-sessions.db`. Это отделяет фоновые записи от диалогов и не заставляет MCP-процесс открывать всё хранилище памяти. Файл и его WAL/SHM добавляются в `.gitignore`, на Unix выставляются права `0600`.

Минимальная схема:

```text
scheduler_jobs
  id, name, kind, schedule_type, run_at,
  daily_time, timezone, horizon_hours,
  provider, model, status, next_run_at,
  created_at, updated_at, deleted_at

scheduler_runs
  id, job_id, trigger, scheduled_at,
  started_at, finished_at, status,
  events_json, deterministic_text,
  delivered_text, text_source,
  telegram_message_id, error_kind,
  error_message
```

Удаление логическое: `status = deleted` и `deleted_at` сохраняют аудит запусков. Секреты в обе таблицы не записываются.

Операции `rusqlite` выполняются через узкий `SchedulerStore`. Асинхронный код отправляет блокирующие транзакции в `spawn_blocking`; каждая операция открывает соединение к известному пути, включает foreign keys, WAL и bounded busy timeout. Это избегает удержания синхронного `Connection` через `.await` и не требует делить `SessionStore` между потоками.

Альтернатива — расширить `SessionStore` — уменьшила бы число файлов, но связала бы жизненный цикл демона с интерактивными сессиями и увеличила область миграций.

### 3. Ограниченная модель расписания и вычисление UTC

Храним два типа:

- `once`: абсолютный RFC 3339 `run_at` со смещением;
- `daily`: `HH:MM` и поддерживаемая именованная зона, первоначально `Europe/Moscow`.

`next_run_at` всегда хранится в UTC. Для `Europe/Moscow` используется фиксированное смещение `+03:00`, поэтому новая timezone-зависимость не нужна. JSON Schema ограничивает `timezone` поддерживаемым enum; расширение на другие IANA-зоны потребует отдельного решения о DST.

Worker просыпается по ближайшему `next_run_at`, но также имеет небольшой контрольный tick, чтобы увидеть задания, созданные после вычисления sleep. MCP-мутации сигнализируют worker через `Notify`.

При старте незавершённые `running`-записи становятся `interrupted`. Просроченное ежедневное задание получает один компенсирующий запуск, после чего `next_run_at` переносится на ближайшее будущее локальное время. Одноразовое выполняется один раз. Полный catch-up намеренно исключён, чтобы после долгого простоя не отправлять пачку устаревших сообщений.

### 4. Claim выполняется транзакционно до внешних эффектов

Для due job `BEGIN IMMEDIATE` повторно проверяет статус и `next_run_at`, создаёт `scheduler_runs` и сразу переносит/очищает `next_run_at`. Ровно один локальный worker получит run ID. Следующий срок не начинает копию, если у задания остался незавершённый запуск; он фиксируется как пропущенный или переносится вперёд.

Этот подход защищает от нескольких MCP-сессий и повторного tick внутри одного процесса. Он не является распределённой блокировкой для двух одновременно запущенных экземпляров сервера, что остаётся операционным ограничением.

### 5. MCP API специализирован под календарные сводки

Сервер объявляет:

- `create_calendar_digest_schedule`;
- `list_calendar_digest_schedules`;
- `pause_calendar_digest_schedule`;
- `resume_calendar_digest_schedule`;
- `delete_calendar_digest_schedule`;
- `run_calendar_digest_now`;
- `get_calendar_digest_history`.

Создание принимает имя, tagged schedule, `horizon_hours` (по умолчанию 24, ограниченный диапазон), необязательный provider и использует модель этого provider из локальной конфигурации. В задании фиксируются provider и model, но не API key. Если provider не указан, используется `last_provider`; отсутствие однозначной настройки отклоняет создание. Все мутации имеют `read_only_hint = false`, поэтому существующий контур подтверждения применяется без исключений. List/history объявляются read-only.

`run_calendar_digest_now` создаёт отдельный run с trigger `manual` и не меняет плановый `next_run_at`.

### 6. Чтение календаря использует CalDAV calendar-query

`CalDavClient::list_events(from, to)` переиспользует discovery и однозначный выбор календаря. Он отправляет `REPORT` с `calendar-query`, фильтром `VEVENT` и UTC time-range. Ответ разбирается в нормализованные `CalendarDigestEvent`; поддерживаются временные и all-day значения, строки iCalendar предварительно разворачиваются, события сортируются.

Системная ошибка XML/CalDAV завершает сбор. Повреждённый отдельный VEVENT пропускается с безопасным предупреждением без печати сырого тела. Пустой успешный ответ остаётся отличим от ошибки.

Альтернатива — добавить отдельный календарный SDK — упростила бы полную поддержку recurrence, но заметно расширила бы зависимости. MVP использует уже существующие HTTP/XML и небольшую provider-specific нормализацию; fixture-тесты фиксируют реально поддерживаемые варианты.

### 7. Фоновый генератор не является интерактивным Agent

`DigestGenerator` сначала строит детерминированный русский текст из нормализованных событий. Затем он вызывает существующий provider request path с отдельными `AgentSettings`, фиксированной инструкцией, нулевой историей кроме одного входного сообщения и `RequestOptions::default()` без tools/results. Ответ принимается только если содержит непустой текст и не содержит tool calls; иначе используется fallback.

Конфигурация и API key берутся из `.fox-llm.json`, загруженной MCP-сервером при старте. Изменение provider-настроек требует перезапуска сервера; это предсказуемее, чем читать файл с секретом перед каждым запуском. В базу сохраняются только provider/model. Ошибка или отсутствие ключа не останавливает доставку детерминированного текста.

Переиспользование `Agent::ask` отвергнуто: оно привнесло бы память, сжатие, tool loop и интерактивные подтверждения, которые не имеют безопасной семантики в фоне.

### 8. Telegram — фиксированный delivery adapter

`.env-mcp` получает только явно разрешённые переменные `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; существующий dotenv loader расширяется точным allowlist, а не произвольным префиксом. MCP-инструменты не принимают destination.

`TelegramClient` отправляет `sendMessage` через `reqwest` и разбирает минимальный безопасный ответ. HTTP success с Telegram `ok=true` означает `delivered`; явный HTTP/API отказ — `failed`; транспортная ошибка после начала запроса считается `unknown`. Для `unknown` автоматического retry нет, потому что Telegram Bot API не предоставляет используемого здесь idempotency key и повтор может создать дубликат. Пользователь может подтвердить ручной запуск после проверки.

Ответы и логи редактируются до сохранения: token, chat ID, Authorization-подобные значения и сырые тела внешних ответов не включаются. `telegram_message_id` допустим как безопасный идентификатор результата.

### 9. Конвейер сохраняет стадии и не выдумывает данные

Исполнение проходит состояния `collecting -> generating -> delivering -> delivered|failed|unknown`. После чтения сохраняются нормализованные события и fallback. После LLM сохраняется фактически отправляемый текст и `text_source`. Ошибка CalDAV завершает run до генерации и доставки. Ошибка LLM переключает только источник текста на fallback.

Такой порядок позволяет истории показать, где произошёл сбой, и гарантирует, что доставленная сводка всегда основана на успешно прочитанном календаре.

### 10. Внешние границы инъецируются для тестов

Планировщик получает абстракцию часов, календарный reader, digest generator и notifier. Тесты используют временную SQLite-базу, управляемые часы и записывающие fake-клиенты. HTTP fixture-тесты отдельно покрывают CalDAV XML/iCalendar и ответы Telegram. Это позволяет проверить recovery и exactly-once claim без ожидания реального времени и сети.

## Risks / Trade-offs

- [Запущены два экземпляра MCP-сервера с одной базой] -> Транзакционный claim уменьшает риск дубля, но документируется поддержка только одного процесса-владельца.
- [Telegram принял сообщение, но ответ потерян] -> Статус `unknown`, отсутствие автоматического retry и ручная проверка вместо ложного успеха.
- [LLM выдаёт неподходящий или потенциально инструктивный текст из названий событий] -> Фиксированный prompt, отсутствие tools, ограниченный размер входа и готовый детерминированный fallback; календарные поля рассматриваются как данные.
- [CalDAV recurrence и варианты iCalendar сложнее минимального parser] -> Запрос server-side time range, corpus fixture-тестов и безопасный пропуск только отдельных повреждённых событий; расширение parser выносится отдельно.
- [MCP-сервер остановлен в момент расписания] -> Персистентный `next_run_at`, один recovery run и явная история; непрерывность процесса остаётся обязанностью запускающего окружения.
- [Сводка или события содержат приватные данные] -> Только фиксированный локальный чат, права файлов `0600`, отсутствие секретов в БД/логах и запрет произвольного destination.
- [Рост журнала] -> History API ограничивает выборку; политика автоматической очистки не входит в MVP и может быть добавлена позднее.

## Migration Plan

1. При старте MCP-сервера создать `.fox-scheduler.db` и таблицы идемпотентной миграцией; существующая `.fox-sessions.db` не меняется.
2. При отсутствии Telegram или provider-настроек сервер продолжает обслуживать старые инструменты, но создание/запуск сводки возвращает безопасную ошибку или использует fallback там, где календарь и Telegram доступны.
3. Новые MCP-инструменты остаются выключенными, пока пользователь не включит их через существующий allowlist `/mcp`.
4. После настройки `.env-mcp` перезапустить MCP-сервер и проверить `run_calendar_digest_now`, затем создать ежедневное расписание.
5. Для отката остановить новый сервер и вернуть предыдущую версию. Отдельная scheduler-база не влияет на сессии; её можно сохранить для повторного развёртывания. Удаление базы не выполняется автоматически.
