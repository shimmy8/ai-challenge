## Purpose

Позволяет сохранять, подтверждать и выполнять по расписанию ограниченные последовательные pipeline из инструментов любых зарегистрированных MCP-серверов.

## ADDED Requirements

### Requirement: A scheduled job contains a generic pipeline
Система SHALL сохранять задание как имя, расписание и неизменяемый линейный MCP-pipeline без полей, специфичных для календаря, GitHub, Telegram либо другого домена. Pipeline MUST содержать от одного до восьми шагов с уникальными идентификаторами, квалифицированными именами инструментов и JSON-аргументами.

#### Scenario: A cross-server job is created
- **WHEN** пользователь подтверждает корректное расписание и pipeline из доступных инструментов разных серверов
- **THEN** система сохраняет активное задание и возвращает его идентификатор и следующий момент запуска

#### Scenario: A nested orchestration call is proposed
- **WHEN** pipeline задания содержит инструмент управления заданиями или встроенный инструмент запуска pipeline
- **THEN** система отклоняет задание до сохранения и не допускает рекурсивную оркестрацию

### Requirement: Job creation authorizes an immutable future action
Перед сохранением система MUST показать расписание, упорядоченные шаги, квалифицированные имена инструментов, статические аргументы и места динамических ссылок. Одно явное подтверждение SHALL разрешать будущие запуски только этого неизменяемого pipeline; изменение расписания, шага, инструмента или аргумента MUST требовать нового подтверждения.

#### Scenario: User approves recurring side effects
- **WHEN** пользователь подтверждает pipeline, завершающийся изменяющим состояние инструментом
- **THEN** плановые запуски выполняют ровно сохранённую структуру без интерактивного подтверждения каждого повторения

#### Scenario: Job definition changes
- **WHEN** предлагается изменить подтверждённое расписание или pipeline
- **THEN** система не изменяет существующее задание без нового предварительного просмотра и подтверждения

### Requirement: Runtime data flows through bounded references
Фоновый исполнитель SHALL предоставлять безопасный runtime-контекст запуска и рекурсивно разрешать ссылки на него и результаты только предыдущих шагов. Минимальный runtime-контекст MUST содержать `run.id`, `run.trigger` и абсолютное `run.scheduled_at`; неизвестные, циклические и направленные вперёд ссылки MUST завершать запуск ошибкой до вызова затронутого инструмента.

#### Scenario: Scheduled time drives a source query
- **WHEN** аргумент первого шага ссылается на `run.scheduled_at`
- **THEN** инструмент получает фактическое сохранённое время текущего запуска

#### Scenario: Later step consumes output
- **WHEN** аргумент шага ссылается на структурированный output успешно завершённого предыдущего шага
- **THEN** точное JSON-значение подставляется и повторно проверяется по входной схеме целевого инструмента

### Requirement: Jobs fail closed when their environment changes
Перед каждым запуском система MUST заново разрешить маршруты и схемы всех шагов. Отключённый, исчезнувший, переименованный или недоступный инструмент MUST завершать запуск ошибкой без подмены другим инструментом; последующие шаги SHALL быть отмечены как skipped.

#### Scenario: Tool was disabled after approval
- **WHEN** инструмент сохранённого pipeline отключён до очередного запуска
- **THEN** запуск завершается ошибкой до вызова инструмента и не выполняет последующие шаги

#### Scenario: A server is temporarily unavailable
- **WHEN** сервер одного из шагов недоступен во время запуска
- **THEN** запуск фиксируется как неуспешный, а другие задания, не зависящие от сервера, продолжают выполняться

### Requirement: Job lifecycle and execution history are generic
Orchestrator SHALL предоставлять инструменты создания, просмотра, приостановки, возобновления, удаления и немедленного запуска заданий, а также чтения истории. История MUST содержать trigger, общий статус и упорядоченную безопасную трассировку шагов со статусами, но MUST NOT содержать секреты или необработанные реквизиты внешних сервисов.

#### Scenario: Generic job is run manually
- **WHEN** пользователь подтверждает немедленный запуск активного или приостановленного задания
- **THEN** система создаёт отдельный manual run, не изменяет плановый `next_run_at` и сохраняет трассировку

#### Scenario: A middle step fails
- **WHEN** промежуточный инструмент возвращает ошибку или превышает тайм-аут
- **THEN** запуск имеет статус failed, выполненные шаги остаются в истории, а последующие отмечаются как skipped
