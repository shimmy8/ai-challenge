## Context

`fox-llm` уже поддерживает локальный `Ollama` через Responses API с жёстко заданным адресом `127.0.0.1:11434` и моделью `qwen3.5:4b`. Это существующее поведение должно сохраниться. Для Дня 30 добавляется отдельный `Ollama Remote`: inference выполняется на Raspberry Pi 5 с 8 ГБ, тогда как MacBook выступает только клиентом в той же подсети. См. `proposal.md` и delta-спецификации для пользовательского поведения.

Ollama предоставляет ARM64-сборку, native chat API и OpenAI-совместимый API. Сам backend не обеспечивает требуемый внешний rate limit и по умолчанию слушает loopback, поэтому сетевой доступ и ограничения разделяются между Ollama и локальным gateway.

## Goals / Non-Goals

**Goals:**

- Получить воспроизводимое развёртывание компактной чат-модели на Raspberry Pi.
- Оставить inference и содержимое диалога внутри локальной сети.
- Сохранить локальный `Ollama` без изменений и дать удалённому сервису отдельные provider identity, endpoint, модель и состояние сессии.
- Проверить только обязательные свойства задания короткими функциональными сценариями.

**Non-Goals:**

- Публичный интернет-доступ, домен, TLS или VPN.
- Полноценное нагрузочное, длительное или сравнительное performance-тестирование.
- Сбор и публикация RAM, температуры, throttling или состояния systemd.
- Автоматический выбор модели, кластеризация, GPU-ускорение или несколько одновременно загруженных моделей.
- API-ключ Ollama: границей доступа остаются gateway и локальная подсеть.

## Decisions

### 1. Ollama and `qwen3:1.7b` run on Raspberry Pi

На Pi устанавливается нативная ARM64-сборка Ollama и Q4-вариант `qwen3:1.7b` размером около 1,4 ГБ. Контекст ограничивается 4096 токенами, модель одна, а обычные чат-запросы используют non-thinking режим, чтобы не расходовать CPU на скрытое рассуждение.

Альтернативы: `qwen3:0.6b` легче, но слишком сильно жертвует качеством чата; `gemma3:1b` остаётся диагностическим fallback; модели 3–4B помещаются в память, но не нужны для доказательства работоспособности сервиса и увеличивают задержку на CPU.

### 2. Ollama stays on loopback; Nginx exposes the LAN endpoint

Ollama сохраняет стандартный bind `127.0.0.1:11434`. Nginx слушает отдельный порт на фиксированном LAN-адресе Pi, проксирует `/api/` и `/v1/`, отключает response buffering для потоковых ответов, задаёт достаточный upstream timeout и разрешает только выбранную локальную подсеть.

Nginx применяет простой per-client rate limit с малым burst и возвращает `429` при превышении. Конкретные адрес Pi и CIDR передаются при установке или хранятся только в локальной конфигурации; в Git остаются документированные placeholders.

Альтернатива — `OLLAMA_HOST=0.0.0.0:11434` — проще, но открывает backend без слоя ограничений. Tailscale, TLS и API key не нужны для согласованной домашней подсети и остаются возможным будущим усилением.

### 3. Context is bounded at the model deployment layer

Ollama получает `OLLAMA_CONTEXT_LENGTH=4096`, а развёртываемый alias модели фиксирует соответствующий `num_ctx`. Проверка контекста подтверждает эффективное значение и наблюдаемое поведение запроса у границы, не превращаясь в benchmark. Gateway дополнительно ограничивает размер HTTP body как защиту от заведомо чрезмерных запросов, но этот байтовый предел не выдаётся за токенный лимит.

Точное вычисление токенов в Nginx отклонено: оно потребовало бы отдельного tokenizer-aware сервиса и существенно расширило бы учебную задачу.

### 4. `Ollama Remote` is a separate provider identity

В `Provider` добавляется отдельный вариант `OllamaRemote` со стабильным сериализованным идентификатором `ollama_remote` и пользовательским названием `Ollama Remote`. Локальный `Ollama` сохраняет текущие константы endpoint и модель `qwen3.5:4b`; его конфигурация и старые сессии не мигрируют на сетевой адрес.

Для `Ollama Remote` создаётся собственная `ProviderConfig`: модель по умолчанию `qwen3:1.7b`, endpoint отсутствует до явной настройки, API-ключ не требуется. При первом выборе CLI запрашивает адрес; последующая команда просмотра/изменения endpoint доступна только для remote-провайдера. Валидация разрешает `http` и `https`, требует host и запрещает credentials, query и fragment.

Оба Ollama-варианта используют общий Responses API adapter и одинаковый parser, но разрешение URL различается: локальный провайдер использует неизменные константы, remote-провайдер строит Responses API и models URL из своей проверенной базы. Ошибки содержат имя активного варианта и никогда не переключают запрос на другой provider.

Конфигурация, `AgentSettings`, сессии и метрики сохраняют `OllamaRemote` отдельно. При загрузке старой конфигурации добавляется новая remote-запись с пустым endpoint, не меняя ни одного существующего provider config.

Альтернатива — добавить endpoint в текущий `Ollama` — требует миграции его семантики и позволяет случайно направить ожидаемо локальный запрос в сеть. Отдельная identity немного расширяет матрицу тестов, но делает выбор и историю однозначными.

### 5. Evidence uses narrow functional checks

Скрипт проверки принимает base URL аргументом или через безопасную переменную окружения и выполняет: сетевой smoke request, две связанные реплики чата, 5–10 последовательных коротких запросов, контролируемое превышение rate limit и проверку лимита контекста.

Лог следует существующему человекочитаемому формату проекта `[command][event]` с полями `key=value`, а не JSONL. Для каждого кейса скрипт пишет `case_start`, отдельные многострочные секции `prompt` и `response`, затем `case_done` с `http_status`, `elapsed_ms`, `passed` и безопасным `error`. Один и тот же вывод показывается в терминале и сохраняется в `reports/day30/verification.log` для отчёта и видео.

В лог разрешены только фиксированные синтетические prompt и полученные на них полные ответы модели. Скрипт не пишет base URL, IP Raspberry Pi, HTTP-заголовки, credentials или сообщения из пользовательских сессий `fox-llm`; ошибки проходят безопасную нормализацию перед выводом.

Отчёт `reports/day30/README.md` описывает конфигурацию, команды и фактический результат. Отдельный короткий сценарий видео покрывает те же пункты без дополнительных наблюдений за оборудованием.

## Risks / Trade-offs

- [Модель 1.7B отвечает хуже крупных моделей] -> Использовать короткие проверяемые чат-сценарии и явно не заявлять production-качество.
- [CPU inference на Pi даёт заметную задержку] -> Использовать non-thinking режим, короткие ответы и последовательную stability-проверку.
- [Доверенное устройство в разрешённой подсети может обращаться к API] -> Ограничить CIDR в gateway; для доступа вне доверенной LAN потребуется отдельное изменение с VPN или аутентификацией.
- [Байтовый лимит gateway не равен токенному] -> Проверять `num_ctx` отдельно и документировать оба ограничения без смешения терминов.
- [Два Ollama-провайдера увеличивают число веток конфигурации и тестов] -> Переиспользовать общий HTTP adapter, а различия изолировать в endpoint resolution, отображении и persistence-тестах.
- [Новая enum identity должна переживать сериализацию] -> Задать явное стабильное имя `ollama_remote` и покрыть legacy/new session round-trip тестами.
- [Произвольный prompt может записать личные данные в учебный лог] -> Проверочный скрипт использует только встроенные синтетические строки и не принимает содержимое пользовательской сессии.

## Migration Plan

1. Добавить `OllamaRemote` и его пустую по умолчанию endpoint-конфигурацию, проверив, что локальный `Ollama` и legacy-сессии не изменились.
2. Добавить CLI-настройку remote endpoint, общий HTTP adapter и отдельные persistence/error paths.
3. Подготовить parameterized deployment assets и проверить их на Raspberry Pi без реальных адресов в Git.
4. Установить Ollama и модель на Pi, затем включить loopback backend и LAN gateway.
5. С MacBook выбрать `Ollama Remote`, выполнить функциональные проверки и заполнить отчёт фактическими результатами.
6. При откате переключить `fox-llm` на прежний локальный или облачный провайдер, отключить gateway и остановить Pi deployment; локальный `Ollama`, пользовательские сессии и облачные настройки не изменяются.
