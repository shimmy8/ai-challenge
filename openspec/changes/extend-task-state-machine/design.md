## Context

См. мотивацию в `proposal.md` и поведенческий контракт в `specs/task-lifecycle/spec.md`.

Сейчас `Task` содержит строковый `todo` и фазу. Задача сохраняется независимо от сессий, поэтому фазу и TODO уже можно восстановить без истории диалога, но свободный текст не различает факты, работу и проверки и не хранит прогресс отдельных пунктов. Проект уже применяет компактное TOON-представление для истории сообщений, поэтому тот же подход можно использовать без новой зависимости.

Изменение затрагивает модель TODO, кодирование SQLite, фазовые инструкции, обработку ответа обоих провайдеров, отображение и тесты. Пользовательские сообщения CLI остаются на русском языке.

## Goals / Non-Goals

**Goals:**

- Сделать фазу и TODO достаточными для продолжения задачи в новой сессии.
- Минимизировать число токенов, повторно передаваемых модели с рабочей памятью.
- Автоматически сохранять подтверждённый самим агентом прогресс пунктов без дополнительных действий пользователя.
- Сохранить исключительное право пользователя переводить задачу между фазами.

**Non-Goals:**

- Добавлять явное состояние или команды паузы и продолжения.
- Переносить историю сообщений между сессиями задачи.
- Автоматически переводить фазу после завершения checklist.
- Поддерживать зависимости, исполнителей, сроки или вложенность подзадач.
- Считать служебную отметку агента гарантией внешнего факта вне выполненной им работы.

## Decisions

### 1. TODO становится типизированной структурой

В памяти TODO представлен структурой с тремя секциями:

- `facts: Vec<String>` — краткие факты, решения и ограничения;
- `execution: Vec<TodoItem>` — работа, необходимая для получения результата;
- `validation: Vec<TodoItem>` — проверки, доказывающие готовность результата.

`TodoItem` содержит стабильный положительный `id`, булев `done` и непустой ограниченный по длине `text`. Идентификаторы уникальны внутри своей секции и не переиспользуются после создания. Порядок элементов стабилен.

Альтернатива — хранить Markdown-чекбоксы в одной строке. Она проще для ручного редактирования, но требует неоднозначного парсинга, не даёт устойчивых ссылок на пункты и расходует больше токенов на повторяющиеся маркеры и заголовки.

### 2. Для хранения и prompt используется компактный TOON

Существующий SQLite-столбец `tasks.todo TEXT` сохраняется. В нём хранится каноническая форма с короткими именами секций и числовым флагом `x`:

```text
f[2]:
  "Rust 2021"
  "SQLite обязателен"
e[2]{id,x,text}:
  1,1,"Добавить модель TODO"
  2,0,"Подключить сохранение"
v[1]{id,x,text}:
  1,0,"Запустить cargo test"
```

`f`, `e`, `v` означают facts, execution и validation; `x` принимает `0` или `1`. Строки кодируются как JSON string literals, что сохраняет переносы, запятые и Unicode без отдельного механизма экранирования. Один канонический encoder/decoder используется для SQLite и системного prompt, поэтому повторная сериализация не расходится.

Альтернатива — JSON. Она отвергнута для основного состояния из-за повторения ключей у каждого пункта. TOON сохраняет табличную структуру и уменьшает prompt при длинных списках.

### 3. Legacy TODO декодируется без изменения схемы

Decoder сначала проверяет канонические заголовки TOON. Любое прежнее значение `todo`, не имеющее такого заголовка, трактуется как один факт; execution и validation создаются пустыми. При следующем обновлении задача записывается в каноническом формате.

Это обеспечивает ленивую миграцию без `ALTER TABLE`, не меняет внешние ключи сессий и не требует переписывать все строки при запуске. Пустой или повреждённый новый TOON возвращает информативную ошибку и не заменяется молча.

### 4. Агент передаёт компактный delta в последней строке ответа

Фазовые инструкции разрешают агенту добавить в конец ответа необязательную строку:

```text
TASK_UPDATE:{"f":["факт"],"e":["пункт"],"v":["проверка"],"ed":[2],"vd":[1]}
```

Пустые ключи опускаются. `f`, `e`, `v` добавляют значения, а `ed` и `vd` содержат стабильные ID завершённых пунктов. JSON применяется только для небольшого delta: он надёжно разбирается `serde_json`, а короткие ключи уменьшают токены. Основное состояние остаётся TOON.

После успешного ответа система:

1. отделяет только последнюю строку с каноническим префиксом `TASK_UPDATE:` или совместимым разделителем-пробелом после `TASK_UPDATE`;
2. удаляет её из отображаемого пользователю текста и истории сообщений;
3. разбирает и валидирует delta;
4. применяет разрешённые фазой операции;
5. сохраняет обновлённый TODO и обновляет `ActiveMemory` до следующего запроса.

Канонический формат в prompt использует двоеточие и числовые ID. Для устойчивости к
типичным отклонениям ответа parser также принимает `TASK_UPDATE {...}` и числовые ID
в JSON-строках. Нечисловые строки, неизвестные поля и все фазово недопустимые операции
остаются ошибками и не применяются.

Если модель полностью опускает префикс, parser принимает bare JSON только в последней
строке и только когда объект содержит хотя бы один зарезервированный ключ task-delta:
`f`, `e`, `v`, `ed` или `vd`. После распознавания действуют `deny_unknown_fields` и
фазовая валидация. JSON без этих ключей остаётся частью пользовательского ответа.

На `planning` разрешены `f`, `e` и `v`; на `execution` — только `ed`; на `validation` — только `vd`; на `done` изменения запрещены. Система сама назначает ID новым пунктам, поэтому модель не может создать коллизию. Дубликаты фактов и пунктов не добавляются после нормализации пробелов.

Альтернатива — отдельный LLM-запрос для извлечения прогресса. Она отвергнута из-за дополнительной задержки и расхода токенов. Альтернатива — сохранять весь TODO, возвращённый моделью. Она отвергнута из-за риска потерять существующие пункты или изменить чужие отметки.

### 5. Основной ответ важнее служебного обновления

Отсутствующий или некорректный `TASK_UPDATE` не превращает успешный ответ провайдера в ошибку. Пользователь получает очищенный основной текст, TODO остаётся прежним, а CLI показывает короткое предупреждение. Изменение с неизвестным ID, запрещённым фазе ключом или попыткой смены фазы отклоняется полностью, чтобы не сохранять частичный неоднозначный прогресс.

Обновление считается подтверждением агента только если основной запрос завершился успешно. При ошибке SQLite новый TODO не попадает в runtime-память; CLI сообщает, что ответ получен, но прогресс не сохранён.

### 6. Фазовые инструкции используют checklist, но не управляют переходами

- `planning`: собирать минимальные факты, создавать пункты получения результата и отдельные пункты его проверки; не выполнять их.
- `execution`: выбирать незавершённый execution-пункт, выполнять его и добавлять ID в `ed` только после фактического завершения.
- `validation`: выполнять незавершённый validation-пункт и добавлять ID в `vd` только после полученного результата проверки.
- `done`: не менять TODO и не предлагать дальнейшую работу.

Агент предлагает `/task next`, когда в соответствующей секции нет незавершённых пунктов, но система не переводит фазу автоматически. Перед подтверждением `/task next` CLI показывает число оставшихся пунктов; пользователь может продолжить переход даже при незавершённых пунктах, что сохраняет действующую модель ручного контроля.

После подтверждённого перехода в `execution` или `validation` CLI немедленно
передаёт агенту короткое фазовое user-сообщение: начать первый применимый
незавершённый пункт новой секции и сохранить результат через `TASK_UPDATE`.
Сообщение проходит обычный путь запроса, поэтому сохраняются история, метрики,
обработка delta и ошибки провайдера. Переход в терминальную фазу `done` не вызывает
LLM-запрос.

Перед каждым запросом в рабочей фазе приложение детерминированно выбирает первый
пункт соответствующей секции с `x=0`. Системный prompt отдельно фиксирует
«Текущий шаг» (`e#ID` или `v#ID`) и «Ожидаемое действие» с единственным допустимым
ID для `ed`/`vd`. После сохранения delta следующий prompt вычисляет новый пункт из
обновлённого `ActiveMemory`. Если незавершённых пунктов нет, prompt запрещает
повторять завершённые ID и предлагает пользователю `/task next`.

После атомарного сохранения delta приложение сравнивает готовность этапа до и после
обновления. При переходе от незавершённого checklist к завершённому CLI сам выводит
следующую фазу и команду `/task next`; это не зависит от текста ответа модели и не
меняет фазу автоматически. Повторные idempotent-обновления завершённой секции не
создают дублирующую подсказку.

Если сохранённый delta сдвинул текущий ID и в той же секции остался пункт, CLI
запускает ещё один обычный request-cycle с короткой внутренней командой продолжить
фазу. Каждый ответ отдельно отображается, учитывается в метриках и сохраняется в
сессии. Цикл продолжается только при доказанном изменении текущего ID. Отсутствующий,
пустой, повторный или ошибочный delta, ошибка SQLite либо провайдера останавливают
автопродолжение. Последний пункт завершает цикл предложением `/task next`; фазу
по-прежнему меняет только пользователь.

### 7. Результаты шагов хранятся на уровне задачи

Отдельная таблица `task_step_results` с ключом `(task_id, phase, item_id)` хранит очищенный полный ответ агента и короткий итог. Таблица создаётся без переписывания существующих задач. При новом завершении пункта запись результата и обновление `tasks.todo` выполняются в одной транзакции; повторная отметка не перезаписывает прежний результат. Краткий итог агент может передать ключом `s` в `TASK_UPDATE`; если его нет, CLI строит ограниченный по длине итог из ответа. Ответ целиком остаётся в БД, но не дублируется в TODO.

При загрузке задачи результаты читаются вместе с TODO и фазой. Системный prompt получает короткие итоги завершённых шагов, а в `validation` — полные результаты `execution` для проверки артефакта. `/task show` и `/memory` показывают сохранённые результаты. Старые задачи без записей в новой таблице продолжают загружаться; восстановить ответы из прошлых сессий автоматически нельзя.

## Risks / Trade-offs

- [Модель ошибочно объявит пункт выполненным] → разрешать отметки только в секции текущей фазы, принимать только существующие ID и явно инструктировать модель отмечать пункт после завершённой работы.
- [Короткое «продолжай» повторит предыдущий ответ] → вычислять текущий пункт приложением и явно закреплять его ID, текст и ожидаемую отметку в каждом системном prompt.
- [Модель не предложит переход после последнего пункта] → определять завершение checklist после сохранения delta и выводить `/task next` силами CLI.
- [Автопродолжение зациклится или потратит лишние токены] → запускать следующий запрос только при смене вычисленного текущего ID; на любом отсутствии прогресса немедленно останавливаться.
- [Служебная строка попадёт в пользовательский текст] → распознавать только точный префикс последней строки и покрыть очистку ответов обоих провайдеров тестами.
- [Модель вернёт delta без префикса] → распознавать bare JSON только по зарезервированным ключам последней строки, не перехватывая обычные JSON-ответы.
- [Некорректный delta оставит прогресс несохранённым] → сохранить основной ответ, оставить TODO без изменений и показать предупреждение; пользователь сможет повторить шаг.
- [TOON-парсер станет отдельным форматом проекта] → сделать encoder/decoder симметричными, строгими и полностью покрытыми round-trip и corruption-тестами.
- [Большой TODO всё равно увеличит prompt] → ограничить число и длину фактов и пунктов, дедуплицировать добавления и использовать короткие заголовки/табличные строки.
- [Legacy-текст нельзя надёжно разделить на задачи] → сохранять его целиком как факт и позволить planning-агенту сформировать списки без потери исходного текста.

## Migration Plan

1. Добавить типы структурированного TODO и симметричный TOON encoder/decoder.
2. На чтении распознавать прежний свободный текст и преобразовывать его в единственный факт без изменения фазы.
3. Перевести создание, чтение и обновление задач на типизированный TODO, сохранив столбец `tasks.todo` и `sessions.task_id`.
4. Добавить фазовый `TASK_UPDATE`, очистку пользовательского ответа и атомарное сохранение допустимого delta.
5. Проверить legacy-базу, round-trip всех символов, смену сессии и продолжение каждой фазы.
6. При откате старый бинарный файл прочитает TOON как обычный текстовый TODO; данные останутся доступны, хотя структурные операции будут недоступны.
