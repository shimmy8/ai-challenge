# support-web-application Specification

## Purpose

Предоставить запускаемый одной командой локальный веб-стенд, в котором пользователь создаёт обращение поддержки и ведёт связанный с ним диалог с AI-ассистентом через JSON API.

## Requirements

### Requirement: Support-режим запускает API и веб-интерфейс одним процессом
Система SHALL предоставлять отдельный startup mode `support`, который запускает на одном явно заданном loopback-адресе JSON API и встроенный веб-интерфейс. Запуск support-режима MUST NOT запускать интерактивный CLI и MUST NOT изменять его сохранённую конфигурацию, сессии или память.

#### Scenario: Успешный запуск
- **WHEN** пользователь запускает `fox-llm support --addr 127.0.0.1:<port>` с доступными конфигурацией модели, support-индексом и тикетной базой
- **THEN** процесс начинает обслуживать веб-интерфейс и JSON API на указанном адресе и сообщает локальный URL

#### Scenario: Невалидный адрес
- **WHEN** пользователь передаёт отсутствующий, занятый или не-loopback адрес
- **THEN** процесс завершается понятной ошибкой до запуска HTTP-сервера

#### Scenario: Интерактивный режим не изменился
- **WHEN** пользователь запускает `fox-llm` без команды `support`
- **THEN** приложение запускает прежний интерактивный CLI без чтения support-базы и support-индекса

### Requirement: JSON API создаёт тикет и обслуживает связанный диалог
API SHALL принимать `application/json`, создавать тикет из имени и email пользователя, темы и первоначального описания, возвращать стабильный идентификатор тикета и позволять отправлять последующие сообщения только в контексте этого идентификатора. Успешный запрос создания тикета SHALL считаться явным разрешением пользователя сохранить ровно переданные и провалидированные поля.

#### Scenario: Создание тикета
- **WHEN** клиент отправляет валидные имя, email, тему и непустое описание в `POST /api/tickets`
- **THEN** API создаёт открытый тикет, использует первоначальное сообщение как первый вопрос ассистенту и возвращает `201` с тикетом, сообщениями, outcome и citations

#### Scenario: Невалидный тикет
- **WHEN** обязательное поле пусто, email невалиден либо значение превышает установленный лимит
- **THEN** API возвращает `400` с машинным кодом и безопасным русским описанием ошибки и ничего не сохраняет

#### Scenario: Продолжение диалога
- **WHEN** клиент отправляет непустое сообщение в `POST /api/tickets/{ticket_id}/messages`
- **THEN** API сохраняет пользовательское сообщение, формирует ответ с контекстом этого тикета, сохраняет ответ ассистента и возвращает оба актуальных сообщения, outcome и citations

#### Scenario: Тикет не найден
- **WHEN** клиент отправляет сообщение для неизвестного `ticket_id`
- **THEN** API возвращает `404`, не вызывает embedding- или generation-провайдера и не создаёт сообщение

### Requirement: API возвращает однозначные результаты частичных сбоев
API SHALL различать создание или сохранение данных и последующий сбой AI-ответа. Если пользовательское сообщение уже сохранено, ответ об ошибке MUST содержать тикет и идентификатор сообщения и MUST NOT утверждать, что операция полностью отменена.

#### Scenario: Generation завершилась ошибкой после сохранения сообщения
- **WHEN** сообщение пользователя сохранено, но retrieval или generation завершается ошибкой
- **THEN** API возвращает безопасную ошибку вместе с `ticket_id`, идентификатором сохранённого сообщения и признаком отсутствия ответа ассистента

#### Scenario: Новый тикет создан, но первый AI-ответ недоступен
- **WHEN** `POST /api/tickets` успешно создал тикет и первоначальное сообщение, но retrieval или generation завершился ошибкой
- **THEN** API возвращает `201` с созданным тикетом, `assistant_message: null` и безопасным описанием частичного сбоя

#### Scenario: Ошибка до сохранения
- **WHEN** валидация или получение тикета завершается до записи сообщения
- **THEN** API сообщает, что сообщение не сохранено, и не создаёт частичных записей

### Requirement: Веб-интерфейс покрывает основной пользовательский сценарий
Встроенная страница SHALL позволять создать тикет, увидеть его идентификатор и историю, отправлять последующие сообщения и различать пользовательские ответы, ответы ассистента, источники и ошибки. Интерфейс SHALL использовать тот же JSON API и не иметь отдельного привилегированного доступа к данным.

#### Scenario: Диалог из браузера
- **WHEN** пользователь открывает корневую страницу и создаёт валидный тикет с описанием проблемы
- **THEN** интерфейс без перезагрузки показывает созданный тикет, первоначальное сообщение, первый ответ ассистента и использованные источники, после чего позволяет продолжить диалог

#### Scenario: Ошибка отображается без потери истории
- **WHEN** очередной AI-ответ завершается ошибкой после сохранения сообщения
- **THEN** интерфейс сохраняет видимую историю тикета и показывает отдельное сообщение об ошибке с возможностью повторить вопрос

### Requirement: HTTP-граница безопасна для учебного локального стенда
Support-сервис SHALL по умолчанию слушать только loopback, принимать тела ограниченного размера, экранировать пользовательский текст в HTML и не возвращать API keys, embedding vectors, полные служебные prompts, внутренние пути или данные других тикетов.

#### Scenario: Пользовательский HTML передан как текст
- **WHEN** поле тикета или сообщение содержит HTML или script-разметку
- **THEN** веб-интерфейс отображает её как текст и не исполняет пользовательский код

#### Scenario: Запрошен другой тикет
- **WHEN** обработчик формирует ответ для одного `ticket_id`
- **THEN** в payload и model context отсутствуют сообщения и пользовательские данные других тикетов
