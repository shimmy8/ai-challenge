# linkding-support-rag Specification

## Purpose

Обеспечить отдельную проверяемую базу знаний по linkding и формировать ответы поддержки, одновременно grounded в документации и персонализированные безопасным контекстом выбранного тикета.

## Requirements

### Requirement: Документация linkding образует отдельный воспроизводимый корпус
Система SHALL индексировать только локально зафиксированный разрешённый набор Markdown-документации и собственного FAQ по linkding в отдельный явно заданный support-индекс. Support-индекс MUST NOT включать проектные отчёты, OpenSpec, исходный код `fox-llm`, секреты, локальные env-файлы или содержимое тикетов.

#### Scenario: Индексация support-корпуса
- **WHEN** пользователь запускает индексирование с корнем базы знаний linkding и отдельным support index path
- **THEN** опубликованный индекс содержит только разрешённые документы linkding с относительными source, section и стабильными chunk identifiers

#### Scenario: Общий индекс не смешивается с support-индексом
- **WHEN** одновременно существуют `.fox-index.db` и support-индекс linkding
- **THEN** support-запрос читает только support-индекс, а интерактивный `/rag on` продолжает читать прежний общий индекс

#### Scenario: Происхождение документации зафиксировано
- **WHEN** разработчик проверяет корпус Дня 33
- **THEN** отчёт указывает upstream-проект, зафиксированную версию или commit, выбранные документы и отдельно обозначает созданный в проекте FAQ

### Requirement: Retrieval учитывает вопрос и ограниченный контекст тикета
Для каждого сообщения support-сервис SHALL строить поисковый запрос из текущего вопроса и ограниченного снимка выбранного тикета: темы, первоначального описания и последних пользовательских сообщений. Контекст тикета SHALL передаваться как недоверенные данные, MUST NOT включать данные других тикетов и MUST NOT заменять исходный вопрос в сохраняемой истории.

#### Scenario: Короткое уточнение использует тикет
- **WHEN** пользователь спрашивает «а почему после переноса?», а тема или история текущего тикета содержит адрес сервера linkding
- **THEN** retrieval разрешает контекст уточнения через текущий тикет и ищет релевантную документацию

#### Scenario: Данные другого тикета не влияют на поиск
- **WHEN** другой тикет содержит похожую проблему или дополнительные credentials
- **THEN** его поля и сообщения отсутствуют в rewrite, retrieval и generation текущего запроса

#### Scenario: Rewrite потерял технический идентификатор
- **WHEN** текущий вопрос содержит URL, версию, HTTP-код или выделенный технический идентификатор, который исчез в rewrite
- **THEN** запрос отклоняется до generation без молчаливой подмены исходного вопроса

### Requirement: Ответ разделяет факты тикета и знания продукта
Generation prompt SHALL явно разделять системные инструкции, недоверенный снимок тикета, исходный вопрос и пронумерованные фрагменты документации. Фактические утверждения о поведении linkding SHALL подтверждаться выбранными фрагментами; персональные утверждения SHALL происходить только из текущего тикета и MUST NOT оформляться как цитаты документации.

#### Scenario: Ответ объединяет два вида контекста
- **WHEN** тикет сообщает о смене URL после переноса, а документация описывает настройку browser extension
- **THEN** ответ связывает наблюдение из тикета с документированным действием и цитирует только документацию linkding

#### Scenario: Тикет противоречит документации
- **WHEN** пользовательское сообщение утверждает поведение продукта, не подтверждаемое документацией
- **THEN** ассистент обозначает это как сообщение пользователя, не представляет его документированным фактом и не создаёт ложную цитату

#### Scenario: В документации недостаточно данных
- **WHEN** retrieval не находит фрагментов выше порога
- **THEN** сервис возвращает детерминированный outcome `no_relevant_context`, не вызывает generation и не придумывает решение по данным тикета

### Requirement: Grounded-ответ имеет проверяемую атрибуцию
Каждый успешный AI-ответ SHALL пройти проверку source metadata, ссылок и дословных цитат относительно фактически переданных support-чанков. API SHALL возвращать очищенный ответ и структурированный список citations; служебный attribution-блок MUST NOT попадать в веб-интерфейс или историю тикета.

#### Scenario: Валидный grounded-ответ
- **WHEN** модель возвращает ответ с корректными ссылками и цитатами из переданных фрагментов
- **THEN** сервис сохраняет очищенный ответ ассистента и возвращает соответствующие citations в API

#### Scenario: Модель выдумала источник
- **WHEN** source, section, chunk identifier или цитата не совпадает с переданным support-контекстом
- **THEN** сервис выполняет не более одного repair-запроса, а при повторном нарушении не сохраняет и не показывает ответ как успешный

### Requirement: Ошибки support-RAG не имеют негрунтованного fallback
При отсутствии, повреждении или несовместимости support-индекса либо embedding-конфигурации сервис SHALL завершить текущий ответ явной безопасной ошибкой. Сервис MUST NOT использовать общий индекс, обычный ответ модели или внешние знания как скрытый fallback.

#### Scenario: Support-индекс отсутствует
- **WHEN** пользователь отправляет сообщение, но отдельный индекс linkding отсутствует
- **THEN** пользовательское сообщение сохраняется, AI-ответ не создаётся, а API предлагает построить support-индекс

#### Scenario: Embedding-пространство несовместимо
- **WHEN** model или dimensions текущего embedding provider не совпадают с support-индексом
- **THEN** сервис требует переиндексацию без раскрытия credentials, vectors или полных текстов чанков
