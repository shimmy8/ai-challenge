# День 21. Индексация документов для RAG

## Корпус

Индексатор использует Markdown-документы из двух источников по умолчанию:

- `reports/`;
- `openspec/specs/`.

На момент проверки в корпусе 38 файлов и 34216 слов. Файлы обнаруживаются
рекурсивно, канонизируются и сортируются; дубликаты путей исключаются.

## Конфигурация embeddings

Настройки embeddings изолированы от агентской конфигурации и читаются только
командой `index` из `.fox-embeddings.json` в корне проекта. Безопасный шаблон
находится в `fox-embeddings.example.json`. Локальный файл исключён из Git и не
должен попадать в отчёты или логи.

```bash
cp fox-embeddings.example.json .fox-embeddings.json
chmod 600 .fox-embeddings.json
```

После копирования нужно вручную указать endpoint, model, dimensions, batch size
и, если он требуется провайдером, API key. Поддерживается OpenAI-compatible API,
поэтому для перехода на совместимый локальный сервис достаточно изменить этот
файл; агентский flow и `.fox-llm.json` не меняются.

## Воспроизведение

Запуск обеих стратегий с параметрами по умолчанию:

```bash
cargo run -- index \
  --comparison-output reports/day21/chunking-comparison.json
```

Явный эквивалент:

```bash
cargo run -- index \
  --source reports \
  --source openspec/specs \
  --strategy all \
  --index-path .fox-index.db \
  --chunk-size 1200 \
  --chunk-overlap 200 \
  --comparison-output reports/day21/chunking-comparison.json
```

Результат сохраняется в `.fox-index.db`. Таблицы `documents`, `chunks` и
`embeddings` содержат локальный индекс, а `index_runs` — историю успешных
запусков и sanitized JSON сравнения. Повторный запуск переиспользует embeddings
по ключу `(content_hash, model, dimensions)`.

Во время работы команда построчно показывает в `stderr` обнаружение документов,
chunking, cache hits/misses, начало и завершение каждой embedding-партии,
публикацию SQLite и запись сравнения. Итоговая таблица остаётся в `stdout`.
Каждый embedding-запрос ограничен timeout 60 секунд; progress и ошибки не
содержат тексты чанков, content hashes, заголовки авторизации или credentials.

## Стратегии

- `fixed` делит текст по числу Unicode-символов, предпочитая границы абзацев и
  строк и сохраняя overlap.
- `structural` использует Markdown-заголовки и сохраняет иерархический путь
  раздела; слишком большой раздел делится тем же ограничителем размера.

Обе стратегии сохраняют `source`, `title`, `section`, `chunk_id`, порядковый
номер и `content_hash`. Векторы хранятся как little-endian `f32` BLOB.

## Фактическое сравнение

Живой запуск выполнен через OpenAI-compatible endpoint с моделью
`text-embedding-3-small` и размерностью 1536. Обе стратегии обработали одинаковые
38 документов. Денежная стоимость не вычисляется.

| Метрика | fixed | structural |
| --- | ---: | ---: |
| Чанки | 292 | 662 |
| Минимум, символов | 370 | 11 |
| Максимум, символов | 1200 | 1200 |
| Среднее, символов | 1011,7 | 383,3 |
| Медиана, символов | 1052,0 | 265,5 |
| Section coverage | 100% | 100% |
| Новые embeddings | 292 | 629 |
| Переиспользованные embeddings | 0 | 7 |
| API tokens | 117 004 | 96 259 |
| Длительность | 15,14 с | 20,82 с |

Суммарное потребление составило 213 263 API-токена. Числа новых и
переиспользованных embeddings относятся к уникальным текстам: поэтому для
structural их сумма меньше числа чанков — одинаковые тексты дедуплицируются по
`content_hash`.

Structural создал в 2,27 раза больше чанков. Его средний размер на 62,1%, а
медианный — на 74,8% меньше, чем у fixed. Это ожидаемый эффект сохранения границ
Markdown-разделов: фрагменты получаются точнее привязаны к секциям, но многие из
них очень короткие — минимум 11 символов. Несмотря на большее число чанков,
structural использовал на 17,7% меньше API-токенов, поскольку не создаёт overlap
между соседними смысловыми разделами. Обработка заняла на 37,5% больше времени,
что соответствует большему числу vectors и последовательных batch-запросов.

Для последующего retrieval structural выглядит предпочтительнее как базовая
стратегия благодаря сохранению семантических границ. Перед production-применением
стоит добавить минимальный размер секции или объединение очень коротких соседних
разделов, чтобы уменьшить число малополезных чанков без смешивания крупных тем.

Sanitized-результат сохранён в `reports/day21/chunking-comparison.json`; он не
содержит vectors, тексты чанков, embedding-конфигурацию или credentials.

