# День 25. Мини-чат с RAG и памятью задачи

## Итог реализации

Интерактивный CLI сохраняет исходные пары сообщений в SQLite, а при включённом
RAG строит query rewrite из текущего вопроса, четырёх последних пользовательских
реплик и компактного состояния активной задачи. В retrieval не попадают ответы
ассистента, summary, sticky facts, профиль, долговременные факты, результаты
шагов и MCP-инструменты.

Цель диалога задаётся названием и исходным описанием задачи. Уточнения,
ограничения и определения терминов сохраняются существующим проверяемым
`TASK_UPDATE.f` и начинают влиять на следующий ход после атомарной записи.
Формат SQLite и TOON не менялся.

```text
текущий вопрос
      +
4 последние user-реплики (до 2000 символов)
      +
task title/facts (до 2000 символов)
      |
      v
изолированный query rewrite --> enhanced retrieval
                                     |
                                     v
                         grounded generation
                                     |
                                     v
                    validator источников и цитат
                                     |
                                     v
                    история + task delta + отчёт
```

Grounded-ответ принимается только после проверки metadata и дословных цитат.
Если контекст не найден, generation не запускается, но сохранённый локальный
ответ всё равно содержит раздел `Источники` с явным сообщением об отсутствии
релевантных источников.

## Воспроизводимый прогон

Файл [`scenarios.json`](scenarios.json) содержит два изолированных сценария по
10 пользовательских ходов:

| Сценарий | Цель | Проверяемые поздние зависимости | Ходов |
|---|---|---|---:|
| `design-task-aware-rag-chat` | Спроектировать CLI-чат с памятью и источниками | термин grounded-ответ, ограничения CLI и SQLite | 10 |
| `verify-rag-index-and-memory` | Проверить retrieval и изоляцию состояния | `candidate_k=20`, `final_k=5`, `min_similarity=0.40`, два независимых сценария | 10 |

Запуск:

```bash
cargo run -- rag-chat-eval \
  --scenarios reports/day25/scenarios.json \
  --output reports/day25/results.json
```

Runner проверяет каждый ход отдельно: outcome, обязательные фрагменты ответа,
сохранённые части task title/facts, ожидаемые пути проверенных источников и
наличие раздела `Источники`. Сценарий получает `passed: true` только при успехе
всех десяти ходов. Между сценариями создаются разные агенты и временные
SQLite-базы; внутри сценария история и задача сохраняются.

`results.json` создаётся только фактическим live-прогоном и не формируется
вручную. Для запуска нужны локально настроенные chat- и embedding-провайдеры и
опубликованный совместимый structural-индекс.

## Результат live-прогона

Прогон выполнен 2 октября 2026 года через OpenAI `gpt-5.6-sol` с параметрами
`candidate_k=20`, `final_k=5`, `min_similarity=0.40` и бюджетом контекста 6000
символов. Оба сценария выполнили все 10 ходов, каждый ход завершился исходом
`answered`. Строгий итог: `passed: false`, 0/2 пройденных сценариев и 10/20
полностью пройденных ходов.

Обозначения проверок: `A` — обязательные фрагменты ответа, `G` — заголовок цели,
`M` — факты задачи, `S` — ожидаемые source paths, `I` — видимая секция
`Источники`. Строчная буква означает провал конкретной проверки.

Цель диалога не потеряна: `task_title_ok` и секция `Источники` прошли на всех
20 ходах. Ожидаемые источники прошли на 16/20 ходах, точные фрагменты task facts
— на 12/20, обязательные фрагменты ответа — на 18/20. Значительная часть
провалов facts вызвана семантически близкой переформулировкой: например,
«интерфейс только CLI» был сохранён как «интерфейс приложения ограничен CLI»,
а «не делить состояние» — как «без общего состояния». Строгая substring-проверка
правильно не засчитала эти варианты.

Четыре провала источников показывают, что retrieval находил содержательно
связанные документы, но не всегда включал каждый заранее ожидаемый путь. Это
не скрывается агрегатом и требует отдельной настройки fixture/индекса либо
более детерминированной фиксации task facts перед тем, как считать eval зелёным.
Полный машинный результат с ответами, безопасными metadata источников и снимками
памяти находится в [`results.json`](results.json).

## Безопасность отчёта

JSON содержит вопросы, ответы, task title/facts, безопасные `source`, `section`,
`chunk_id`, token usage, длительность и результаты проверок. Он не содержит
API keys, authorization headers, embeddings, content hashes, полные тексты
retrieval-чанков, embedding-конфигурацию или служебные prompt.
