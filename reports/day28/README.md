## Что проверяется

Эксперимент проверяет ответы RAG-пайплайна с локальной моделью Ollama. Для
ориентировочного сравнения также используется сохранённый облачный прогон Дня
22 на `gpt-5.6-sol` с теми же контрольными вопросами. Локальный анализ использует
только явно выбранную интерактивную сессию и соответствующие ей строки метрик.
Исторический `rag-eval` рассматривается отдельно и не выдаётся за одновременный
контрольный A/B-прогон: после Дня 22 изменились индекс, retrieval/reranking и
контракт RAG-ответа.

## Граница локальности

SQLite-поиск по векторам выполняется локально. При выбранном Ollama query
rewrite, основной grounded-ответ и единственная возможная repair-попытка также
выполняются локальной моделью `qwen3.5:4b` и не переключаются на OpenAI или
Claude. Query embeddings создаются существующим embedding-провайдером из
локальной конфигурации; если его endpoint внешний, весь пайплайн нельзя считать
полностью offline. Содержимое локальной конфигурации и credentials в отчёт не
попадают.

Поток одного запроса:

1. Ollama переписывает вопрос в поисковый запрос.
2. Существующий embedding-провайдер строит embeddings исходного и переписанного
   запросов.
3. SQLite локально выбирает и ранжирует structural-чанки.
4. Ollama формирует ответ по найденному контексту и при нарушении контракта
   выполняет не более одной repair-попытки.
5. CLI проверяет citations, отображает источники, сохраняет сессию и записывает
   метрики запуска.

## Условия интерактивного прогона

Запуск:

```text
cargo run -- --dump-metrics
```

Перед первым вопросом:

1. Через `/provider` выбрать Ollama.
2. Через `/model` выбрать `qwen3.5:4b`.
3. Через `/mode` выбрать вариант без пользовательского режима.
4. Выполнить `/profile off`, `/task off` и `/new`.
5. Выполнить `/rag on` и убедиться через `/rag status`, что RAG включён.
6. Не задавать посторонних вопросов до завершения основной последовательности.

Для необязательного облачного сравнения следует начать вторую чистую сессию,
выбрать уже настроенного облачного провайдера и повторить те же вопросы в том же
порядке. Новые credentials для эксперимента не запрашиваются.

### Стабильность и локальная нагрузка

Operational stability после добавления fallback высокая: все шесть ходов
сохранены, provider errors отсутствуют. Нативная стабильность structured output
у `qwen3.5:4b` низкая: ни generation, ни repair ни разу не выполнили строгий
контракт. У generation встречались `invalid_tags` и `invalid_header`, каждый
repair завершился `invalid_tags`. Поэтому каждый пользовательский вопрос вызвал
две локальные генерации, после которых ответ восстанавливался приложением.

Пользователь отметил сильный нагрев MacBook во время видеозаписи. Аппаратные
датчики не снимались, поэтому температура недоступна; фиксируется качественное
наблюдение, а не числовой замер. Нагрузка согласуется с шестью длительными
двойными генерациями за девять минут. Для следующего прогона разумно установить
температуру модели `0.0` и сначала проверить один-два вопроса. Более важное
техническое улучшение — не выполнять заведомо неуспешный второй LLM repair для
малой локальной модели, а сразу строить проверяемую атрибуцию из context markers;
это сократит число локальных generation-вызовов примерно вдвое.

В доступных данных облачный baseline значительно быстрее и не испытывает
локальной тепловой нагрузки. По качеству текущий локальный прогон формально выше,
но единственное различие связано с улучшившимся retrieval. Поэтому корректный
итог: `qwen3.5:4b` способна использовать найденный контекст, однако текущая
локальная конфигурация заметно медленнее, сильнее нагружает MacBook и нестабильна
по формату; превосходство одной модели по смысловому качеству этим сравнением не
доказано.

## Проверки реализации

Focused-тесты подтверждают локальные настройки для rewrite, generation и
repair, отключённые MCP tools, проверку citations, рендеринг источников,
сохранение исходного вопроса, token accounting, no-context путь и единственную
repair-попытку. Первый интерактивный вопрос выявил совместимость формата:
`qwen3.5:4b` добавила служебный `RETRY_UPDATE`, ошиблась в счётчике строк
`citations[N]` и не расставила все числовые маркеры. Repair-path теперь удаляет
только этот служебный блок и нормализует избыточные элементы формата, после чего
по-прежнему строго проверяет metadata и дословное вхождение каждой цитаты.
Повторный запуск показал более серьёзно повреждённую TOON-строку при сохранённых
валидных ссылках `[1] [2]`. Для этого случая добавлен безопасный fallback:
приложение принимает существующие context markers, а metadata и короткие
дословные цитаты строит из локально retrieved chunks; неизвестные ссылки
отклоняются.
На втором контрольном вопросе repair оборвался до citations, хотя исходный
полный ответ содержал валидные `[1] [2]`. Теперь при невосстановимом repair
применяется тот же безопасный marker fallback к исходному draft: это сохраняет
реальное качество ответа локальной модели для последующей оценки вместо
превращения слабого ответа в системную ошибку.
Диагностический `rag-eval` дополнительно выявил ссылки на валидные contexts в
порядке `[1] [3] [2]` и квадратный служебный тег. Fallback теперь принимает
существующие context IDs в порядке первого использования, детерминированно
перенумеровывает их в citation IDs и удаляет повреждённый служебный блок;
неизвестные context IDs по-прежнему отклоняются.
