# День 15. Контролируемые переходы состояний

## Что реализовано

Задача проходит только `planning -> execution -> validation -> done`. Команда
`/task next` показывает исходную и целевую фазы и требует подтверждения.
Переход дополнительно проверяется при записи в SQLite:

- `planning -> execution`: в плане есть хотя бы один пункт выполнения и один
  пункт проверки;
- `execution -> validation`: секция выполнения не пуста и все её пункты
  завершены;
- `validation -> done`: секция проверки не пуста и все её пункты завершены;
- из `done` перехода нет.

Задача хранит `plan_version` и `approved_plan_version`. Новая задача получает
версию `0` без утверждения. Сохранённое изменение фактов или пунктов плана в
`planning` увеличивает версию один раз; пустое и повторное обновление её не
меняет. Подтверждение `/task next` утверждает показанную версию одновременно
с переходом в `execution`. Если версия изменилась после показа плана, переход
отклоняется с предложением повторить команду. Агент получает обе версии и
текущую фазу в рабочем контексте, но не меняет фазу сам.

При открытии существующей базы приложение добавляет недостающие столбцы версии
к таблице задач. Старые задачи не получают задним числом утверждение плана;
проверка ниже выполняется на новой задаче в обычной `.fox-sessions.db`.

## Автоматическая проверка

После реализации выполнены:

| Команда | Результат |
| --- | --- |
| `cargo fmt --all` | Успешно |
| `cargo clippy --all-targets --all-features -- -D warnings` | Успешно, предупреждений нет |
| `cargo test` | 77 тестов пройдено |

Тесты покрывают пустой план, незавершённые секции, терминальную фазу,
устаревшее подтверждение, отмену, версионирование изменений, откат при ошибке
записи и восстановление задачи после открытия базы без прежней истории диалога.
Они используют локальную SQLite и подменяемые ответы; реальный ответ модели
проверяется отдельно вручную.

## Пример ручной проверки

Запустить CLI из каталога проекта, используя обычную базу:

```sh
cd /Users/shimmy8/study/ai-challenge
cargo run
```

CLI может попросить выбрать провайдера или ввести ключ. Не включайте ключ или
личные ответы в отчёт. Уже сохранённые задачи для проверки не выбирайте.

1. Выполнить `/task new`, назвать задачу «SQL по заказам» и описать её:
   «Подготовить запрос SQLite, который считает общую сумму заказов по каждому
   клиенту. Схему таблицы и результат `EXPLAIN QUERY PLAN` я предоставлю
   отдельно». Подтвердить создание. `/task show` должен показывать `planning`,
   версию `0` и отсутствие утверждённой версии.
2. Сразу выполнить `/task next`. Ожидается отказ «план не содержит пунктов
   выполнения»; фаза и версия по `/task show` остаются прежними.
3. Отправить агенту: «Составь план, пока не выполняй его. В `execution` добавь
   шаги: дождаться схемы таблицы `orders`, затем написать SQL-запрос. В
   `validation` добавь шаг: дождаться вывода `EXPLAIN QUERY PLAN` и проверить
   запрос по нему. Не отмечай шаги завершёнными без соответствующих данных».
   В `/task show` должны появиться оба списка и версия плана больше `0`;
   утверждения ещё нет.
4. Выполнить `/task next` и ответить «нет» на подтверждение. `/task show`
   должен по-прежнему показывать `planning` без утверждения. Повторить
   `/task next`, сверить показанные факты, пункты и версию и подтвердить.
   Ожидается `execution`, а утверждённая версия должна совпасть с показанной.
5. Пока схема не предоставлена, выполнить `/task next`. Ожидается отказ с
   числом незавершённых пунктов выполнения; фаза остаётся `execution`.
   Затем сообщить схему: `orders(id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL, amount_cents INTEGER NOT NULL)`.
   Агент должен составить запрос с
   `GROUP BY customer_id` и `SUM(amount_cents)` и отметить пункты выполнения.
   CLI может автоматически продолжать следующий пункт той же фазы.
6. После завершения выполнения подтвердить `/task next`. Ожидается
   `validation`. До передачи результата `EXPLAIN QUERY PLAN` выполнить
   `/task next`: ожидается отказ с числом незавершённых пунктов проверки,
   фаза остаётся `validation`.
7. Отдельно выполнить `EXPLAIN QUERY PLAN` для полученного запроса в SQLite и
   передать его вывод агенту. После завершения проверки подтвердить
   `/task next`. Ожидается `done`.
   Ещё один `/task next` должен сообщить, что задача уже завершена, без
   дополнительного запроса к модели.

После того как агент вернёт SQL-запрос, выполнить в отдельном терминале команду
ниже. Она создаёт временную таблицу в памяти и печатает план запроса; реальную
базу изменять не нужно. Если агент предложил другой SQL, заменить часть после
`EXPLAIN QUERY PLAN` его запросом:

```sh
sqlite3 :memory: 'CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL, amount_cents INTEGER NOT NULL); EXPLAIN QUERY PLAN SELECT customer_id, SUM(amount_cents) AS total_cents FROM orders GROUP BY customer_id;'
```

Для приведённого запроса локальный SQLite вывел:

```text
QUERY PLAN
|--SCAN orders
`--USE TEMP B-TREE FOR GROUP BY
```

Скопировать этот вывод в FOX LLM, например: «Вот результат `EXPLAIN QUERY
PLAN` для предложенного запроса: ... Проверь запрос по нему». Результат плана
может отличаться при другой схеме, индексах или версии SQLite; агенту нужно
передавать фактический вывод команды для его запроса.

Автоматическое выполнение пунктов зависит от ответа модели. Если агент
пометит шаг завершённым без требуемых данных, зафиксировать это в наблюдениях:
ограничение перехода опирается на сохранённые отметки TODO. Детерминированная
проверка запрета перехода включена в `cargo test task_transition`.

## Наблюдения пользователя после ручного прогона

### Последняя сохранённая сессия в SQLite

Проверена самая поздняя по `updated_at` сессия #9 (19 сентября 2026 года,
13:26:20 UTC), связанная с задачей #5 «SQL по заказам». В задаче сохранены
фаза `done`, версия плана `1` и утверждённая версия `1`. Оба пункта выполнения
и оба пункта валидации отмечены завершёнными; для каждого сохранён результат.

- В начале `execution` агент запросил схему `orders`. После ввода полной схемы
  `orders(id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL, amount_cents INTEGER NOT NULL)`
  пункт `e#1` был завершён. Затем агент автоматически перешёл к `e#2` и
  сохранил запрос:

  ```sql
  SELECT customer_id, SUM(amount_cents) AS total_amount_cents
  FROM orders
  GROUP BY customer_id;
  ```

- В начале `validation` агент запросил план выполнения. После ввода
  `EXPLAIN QUERY PLAN` с `SCAN orders` и
  `USE TEMP B-TREE FOR GROUP BY` он завершил `v#1`, автоматически продолжил
  `v#2` и сохранил проверку по этому выводу. Сохранённая фаза `done`
  подтверждает завершение последовательности переходов для этой задачи.
- Вывод плана согласуется с чтением таблицы `orders` и группировкой. Проверки
  сумм на тестовых строках в истории нет, поэтому числовой результат запроса
  этим прогоном не подтверждён.

Команды CLI и предупреждения не входят в сохранённую историю диалога.
Поэтому из этой сессии нельзя восстановить попытки недопустимых переходов,
отмену подтверждения или повторный `/task next` после `done`; эти случаи
проверены автоматическими тестами выше.
