# Промпт для запуска эксперимента дня 9

Ты работаешь в корне проекта `fox-llm`. Проведи воспроизводимый эксперимент,
сравнивающий качество ответов и расход токенов с включённым и выключенным
сжатием истории. Сам код приложения не изменяй. Запусти проект, выполни два
одинаковых диалога, проанализируй результаты и сохрани готовый отчёт в
`reports/day9/report.md`.

## Подготовка

1. Выполни `cargo test`. Если тесты не проходят, останови эксперимент и опиши
   ошибку в `reports/day9/report.md`.
2. Запиши исходное количество строк метрик:

   ```bash
   wc -l < fox-metrics.log
   ```

   Если файла ещё нет, считай исходное количество равным нулю.
3. Запусти приложение с записью метрик:

   ```bash
   cargo run -- --dump-metrics
   ```

4. Оба прогона должны использовать одного провайдера, одну модель, один режим и
   одну температуру. Перед началом зафиксируй эти значения. По возможности
   установи температуру `0`, если выбранная модель её поддерживает. Если нет,
   используй одно и то же доступное значение и укажи это ограничение в отчёте.
   Используй режим без дополнительных инструкций.

Не раскрывай API-ключи и не включай содержимое `.fox-llm.json` в отчёт.

## Прогон A: без сжатия

В работающем CLI введи:

```text
/summary 0
/new
```

Убедись, что статусбар показывает `Сжатие: выкл.`. Затем последовательно, по
одному, отправь все 29 сообщений из раздела «Тестовый диалог». Дождись ответа
на каждое сообщение перед отправкой следующего. Сохрани ответы на контрольные
вопросы 25–29 для анализа. После ответа на сообщение 29 запиши текущее число
строк в `fox-metrics.log`; это граница прогона A.

## Прогон B: со сжатием

В том же CLI введи:

```text
/summary 6
/new
```

Убедись, что статусбар показывает `Сжатие: 6 сообщ.`. Провайдер, модель, режим
и температура должны совпадать с прогоном A. Повтори те же 29 сообщений в том
же порядке, снова сохранив ответы 25–29. После последнего ответа выйди через
`/quit` и запиши финальное количество строк метрик.

Если отдельный запрос сжатия завершился ошибкой, зафиксируй ошибку и повтори
то же пользовательское сообщение один раз. Не считай неуспешную попытку
отдельным сообщением теста.

18. `Изменение: срок первой версии перенесён с 15 декабря на 20 января. Ответь только «Обновлено».`
19. `Изменение: совместное планирование исключили из первой версии, а вместо него добавили офлайн-доступ к маршруту. Ответь только «Обновлено».`
20. `Изменение: дизайнером теперь работает Светлана вместо Ирины. Ответь только «Обновлено».`
21. `Предложи три варианта приветствия для главного экрана.`
22. `Какие ошибки могут возникнуть при экспорте PDF?`
23. `Назови пять событий для продуктовой аналитики.`
24. `Какие поля нужны в форме создания поездки?`
25. `Как называется проект, какова его аудитория и основной рынок?`
26. `Назови актуальный бюджет, срок выпуска и состав команды. Не упоминай отменённые значения.`

29. `Составь итоговый паспорт проекта в виде таблицы. Используй только актуальные решения.`

## Как прочитать метрики

`fox-metrics.log` — JSON Lines: одна JSON-запись на каждый успешный основной
ответ. Команды `/summary` и `/new` строк не создают. Для каждого прогона должно
появиться ровно 29 записей. Используй записанные номера строк, чтобы отделить
новые данные эксперимента от старого содержимого файла.

Поля записи:

- `request_input_tokens` и `request_output_tokens` — токены только основного
  запроса, соответствующего этой строке;
- `session_input_tokens` и `session_output_tokens` — накопительный расход
  текущей сессии;
- `elapsed_ms` — длительность обработки пользовательского сообщения;
- `provider` и `model` — контроль одинаковых настроек.

Запросы, которыми приложение создаёт summary, не получают отдельных строк в
логе, но их токены входят в `session_input_tokens` и `session_output_tokens`.
Поэтому общий расход каждого прогона бери из `session_input_tokens` и
`session_output_tokens` его последней, 29-й записи. Не суммируй сессионные поля
по всем строкам: они уже накопительные. При желании извлеки диапазоны через
`sed -n 'START,ENDp' fox-metrics.log`; для вычислений можно использовать `jq`
или небольшой скрипт, не печатающий конфигурацию и ключи.

Для каждого прогона вычисли:

- итоговые входные, выходные и общие токены сессии;
- входные токены последнего основного запроса;
- среднее и медиану `request_input_tokens`;
- среднее время ответа;
- абсолютную и процентную разницу токенов между прогонами:
  `(без сжатия - со сжатием) / без сжатия * 100%`.

Если в диапазоне не 29 строк либо менялись модель или провайдер, не скрывай
это: объясни отклонение и не представляй сравнение как строгое.

## Оценка качества

Оцени ответы на вопросы 25–29 отдельно для каждого прогона. Каждый из следующих
12 фактов даёт 1 балл только при корректном актуальном значении:

1. название «Север»;
2. приложение для планирования путешествий по России;
3. аудитория 25–40 лет;
4. рынок — Россия;
5. актуальный бюджет — 1 200 000 рублей, без 900 000 как действующего;
6. срок — 20 января, без 15 декабря как действующего;
7. команда: Марина, Олег и Светлана, без Ирины как действующего дизайнера;
8. функции: маршруты, список вещей, экспорт PDF и офлайн-доступ;
9. совместное планирование явно отмечено как исключённое;
10. технологии: Rust, PostgreSQL и React;
11. подписка 299 рублей в месяц и отсутствие позиционирования как сервиса
    покупки билетов;
12. метрика успеха: 40% создают вторую поездку в течение 60 дней.

Дополнительно посчитай число явных противоречий и выдуманных фактов. Приведи
краткие примеры ошибок или пропусков. Не оценивай литературный стиль: цель —
проверить сохранность и актуальность контекста.

## Итоговый файл

Создай `reports/day9/report.md`. Включи в него:

1. дату теста, провайдера, модель, температуру, режим и значения сжатия;
2. методику и подтверждение, что оба прогона получили одинаковые 29 сообщений;
3. таблицу качества: баллы из 12, противоречия и выдуманные факты;
4. таблицу токенов и времени для двух прогонов;
5. абсолютную и процентную разницу расхода;
6. примеры наиболее показательных ответов или ошибок;
7. вывод о компромиссе между качеством и экономией токенов;
8. ограничения эксперимента: единственный прогон, возможная недетерминированность
   модели и влияние токенов служебного запроса summary.

Все числа бери из фактических логов, ответы — из фактического запуска. Ничего
не выдумывай. Если запуск невозможен из-за отсутствия ключа, сети или доступа к
API, сохрани в `reports/day9/report.md` описание блокера и точные шаги, которые
осталось выполнить, вместо фиктивных результатов.
