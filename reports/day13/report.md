# День 13. Состояние задачи

## Цель

Сделать состояние задачи самодостаточным после смены сессии: агент должен
получить фазу, известные факты, оставшуюся работу и проверки без повторного
описания со стороны пользователя.

## Модель

Фаза остаётся строгим пользовательским автоматом:

```text
planning -> execution -> validation -> done
```

Пользователь подтверждает только `/task next`. Агент не меняет фазу, но после
успешного ответа автоматически обновляет соответствующую часть TODO:

- `planning` добавляет факты, execution-пункты и validation-пункты;
- `execution` отмечает выполненные execution-ID;
- `validation` отмечает выполненные validation-ID;
- `done` не изменяет TODO.

После подтверждённого перехода в `execution` или `validation` CLI автоматически
запускает первый применимый пункт новой фазы через обычный request pipeline.
Терминальный переход в `done` не вызывает LLM.

Служебное обновление передаётся последней строкой ответа, например
`TASK_UPDATE:{"ed":[2]}`. CLI удаляет её из видимого ответа и истории,
проверяет фазу и ID, затем сохраняет обновлённый TODO. Ошибочный или
отсутствующий delta не повреждает рабочую память и не скрывает основной ответ.

## Формат хранения

В существующем SQLite-поле `tasks.todo` используется компактный TOON:

```text
f[2]:
  "Rust 2021"
  "SQLite обязателен"
e[2]{id,x,text}:
  1,1,"Добавить модель TODO"
  2,0,"Подключить сохранение"
v[1]{id,x,text}:
  1,0,"Запустить cargo test"
```

`f`, `e`, `v` обозначают факты, выполнение и валидацию, `x=1` — завершение.
Строки используют JSON-экранирование, а ID стабильны внутри секции.

### Сравнение размера

Для одинакового состояния из двух фактов, двух execution-пунктов и одной
validation-проверки:

| Представление | Символов |
|---|---:|
| Компактный JSON | 228 |
| TOON | 163 |

TOON короче на 65 символов, или на 28,5%. Точное число токенов зависит от
токенизатора модели, поэтому воспроизводимый эксперимент фиксирует символы;
сокращение достигается отсутствием повторяющихся ключей `id`, `done` и `text`.

## Продолжение после смены сессии

Проверенный сценарий:

1. В `planning` сохранены факт, два пункта выполнения и проверка.
2. Пользователь подтвердил переход в `execution`.
3. Агент отметил первый execution-пункт через `ed:[1]`.
4. SQLite закрыта и открыта повторно, загружена сессия без сообщений истории.
5. Восстановились фаза `execution`, оба пункта и отметка первого пункта.
6. Системный prompt содержит TOON и направляет агента к следующему
   незавершённому пункту `#2`.

На каждом запросе рабочей фазы prompt дополнительно содержит отдельные поля
`Текущий шаг` и `Ожидаемое действие` с точным ID. После отметки `#1` следующий
запрос, включая короткое «продолжай», получает `#2`; завершённые ID повторно не
предлагаются.

После сохранения последнего ID секции CLI сам сообщает о завершении этапа и
предлагает `/task next`. Фаза не меняется автоматически, а повторное обновление
уже завершённой секции не дублирует подсказку.

Если после отметки остаётся следующий пункт той же секции, CLI автоматически
запускает его через обычный request pipeline. Ручное «продолжай» внутри фазы не
требуется; ошибка или отсутствие смены текущего ID останавливает автоцикл.

Legacy-текстовый TODO при чтении становится одним фактом с пустыми списками и
записывается в каноническом формате после первого автоматического обновления.

Результаты шагов теперь хранятся в отдельной таблице `task_step_results`, связанной
с задачей, а не сессией. Для каждого завершённого пункта сохраняются полный
очищенный ответ и краткий итог; запись результата и отметка TODO атомарны.
Повторная отметка не заменяет прежний результат. После повторного открытия SQLite
новая сессия видит краткие итоги, а `validation` получает полный результат
`execution` без загрузки старой истории. Ранее завершённые пункты без записей
результата остаются доступными, но прошлые ответы автоматически не извлекаются
из истории сессий.

### Ручной сценарий: результат задачи после перезапуска

Проверка должна прерывать работу **между `execution` и `validation`**, чтобы
валидация получила артефакт из записи задачи, а не из истории старого диалога.

1. Запустить `cargo run` и выполнить `/task new`. Название задачи:
   `Проверка результата после перезапуска`. В качестве исходного описания ввести:

   > Подготовить готовый русскоязычный справочник для начинающего
   > Rust-разработчика о резервном копировании SQLite, не более 180 слов.
   > Включить безопасное создание копии через `.backup`, восстановление после
   > остановки приложения и предупреждение о копировании работающей базы
   > обычным `cp`. В planning создай один пункт выполнения — написать полный
   > текст справочника — и два пункта валидации: проверить содержание и
   > посчитать слова.

2. Отправить агенту `Составь TODO для этой задачи.` и выполнить `/task show`.
   Ожидаются один execution-пункт и два validation-пункта. Записать ID задачи.
3. Выполнить `/task next` и подтвердить переход в `execution`. CLI автоматически
   запустит пункт; агент должен выдать **полный текст справочника** и завершить
   execution-пункт. В `/task show` проверить, что в `Результаты` сохранён именно
   этот текст для `e#1`, а не только отметка или краткий итог.
4. Выйти через `/quit` и заново запустить `cargo run`. Выполнить `/new`, затем
   `/task use <ID задачи>`. **Не загружать** прежнюю сессию через `/sessions`.
5. Выполнить `/task show`. Ожидаются фаза `execution`, завершённый `e#1` и тот
   же полный текст справочника. Это проверяет хранение результата независимо
   от истории сессии.
6. Выполнить `/task next` и подтвердить `validation`. Агент должен автоматически
   проверить содержание и объём сохранённого справочника без повторной отправки
   текста пользователем. После работы `/task show` должен показать результаты
   проверок `v#1` и `v#2`.

Если после перезапуска полный справочник отсутствует в `/task show` или агент
просит прислать его повторно для валидации, проверка не пройдена.

### Фактический прогон после очистки БД (19.09.2026)

На момент анализа в `.fox-sessions.db` остались одна задача `#1` (`task test`),
две связанные с ней сессии `#1` и `#2` и три записи `task_step_results`.
Задача находится в `done`: единственный пункт `execution` и оба пункта
`validation` имеют `x=1`.

- Сессия `#1` содержит планирование и ответ `execution`. Для `e#1` в
  `task_step_results` отдельно сохранены краткий итог и полный текст
  справочника (1067 символов).
- Сессия `#2` начинается с внутренней инструкции для `validation` и содержит
  автоматическое продолжение ко второму пункту. В её `history_toon` нет текста
  справочника или фрагмента Rust-кода из `e#1`; результаты `v#1` и `v#2`
  сохранены в таблице задачи. Это подтверждает разрыв истории между сессиями;
  согласно текущему коду, полный `e#1` передаётся валидатору из записи задачи.
- Оба пункта валидации объявили лимит в 180 слов соблюдённым, но назвали
  **139 слов**. Независимый пробельный подсчёт сохранённого `e#1` через
  `wc -w` даёт **118 слов**. Вывод о соблюдении лимита верен, точное число —
  нет. Кроме того, `v#1` уже проверял объём, поэтому `v#2` фактически
  продублировал часть первой проверки.

Вывод: сохранение полного результата на уровне задачи и продолжение в новой
сессии сработали в этом прогоне. Точность содержательной валидации нельзя
считать доказанной только по отметкам `x=1`; для числовых критериев нужна
детерминированная проверка или независимое сравнение.

Сопутствующая проблема окружения на момент анализа: в локальной
`.fox-llm.json` у провайдера OpenAI поле `temperature` равно `null`, из-за чего
текущий CLI не проходит загрузку конфигурации (`expected f64`). Конфигурация
не изменялась в ходе анализа; эта ошибка отделена от состояния задачи в SQLite.

## Проверки

На момент подготовки отчёта реализованы тесты для:

- строгой последовательности фаз;
- выделения стабильных ID, ограничений и дедупликации;
- TOON round-trip, Unicode, кавычек, запятых и повреждённого ввода;
- legacy TODO и повторного открытия SQLite;
- фазовых ограничений `TASK_UPDATE` и неизвестных ID;
- очистки служебной строки и сохранения основного ответа;
- автоматического обновления SQLite и runtime-памяти;
- полного lifecycle и продолжения без истории предыдущей сессии.

Финальная проверка выполняется командами:

```text
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```
