# Руководство по репозиторию

## Структура проекта и организация модулей

В этом репозитории находится `fox-llm` — CLI-клиент на Rust для OpenAI и Claude. `src/main.rs` содержит только декларации модулей и точку входа; основной код распределён по ответственности:

- `app.rs` — инициализация и интерактивный цикл приложения;
- `agent.rs` — `Agent`, `AgentPool` и стратегии управления контекстом;
- `config.rs` — конфигурация провайдеров, режимы ответа и миграция legacy-формата;
- `providers.rs` — HTTP-интеграции OpenAI/Claude, ответы и список моделей;
- `sessions.rs` — SQLite-хранилище сессий, миграции и TOON-кодирование;
- `cli.rs` — команды, rustyline, интерактивные prompt'ы и отображение статуса;
- `metrics.rs` — флаг `--dump-metrics` и JSONL-лог метрик;
- `memory.rs` — профили персонализации, долговременные факты, задачи, TODO и фазы `planning -> execution -> validation -> done`;
- `mcp/` — MCP-интеграция: `mod.rs` управляет runtime и allowlist, `server.rs` регистрирует HTTP-инструменты, `calendar.rs` реализует CalDAV-клиент Яндекс Календаря, `tools.rs` содержит provider-neutral типы tool-calling и подтверждения;
- `model.rs` — общие типы предметной области;
- `tests.rs` — регрессионные юнит- и асинхронные тесты.

При изменениях сохраняйте код в модуле, которому принадлежит ответственность, и оставляйте `main.rs` тонким. Отчёты об экспериментах и полученные результаты сохраняйте в `reports/dayN/`. Общие режимы ответов определены в `fox-modes.json`.

Не коммитьте сгенерированные и локальные данные: `target/`, `.fox-llm.json`, `.fox-sessions.db*`, `fox-metrics.log`, `mcp.log` и `.env-mcp` исключены из Git, поскольку содержат результаты сборки, учётные данные, сессии или метрики выполнения.

## Команды сборки, тестирования и разработки

- `cargo run` запускает интерактивный CLI-клиент.
- `cargo run -- --dump-metrics` запускает клиент и записывает метрики запросов в `fox-metrics.log`.
- `cargo build` собирает отладочную версию и выявляет базовые ошибки интеграции.
- `cargo test` запускает юнит-тесты и асинхронные тесты.
- `cargo fmt --all -- --check` проверяет стандартное форматирование Rust; `cargo fmt --all` применяет его.
- `cargo clippy --all-targets --all-features -- -D warnings` запускает линтер и считает предупреждения ошибками.

Перед отправкой изменений на проверку запустите форматирование, Clippy и тесты.

При ручной проверке памяти используйте `/profile`, `/remember`, `/forget`,
`/task` и `/memory`. `/remember` сохраняет только явно переданный
долговременный факт; сессии, задачи и профили эта команда не изменяет.
Переход задачи к следующей фазе выполняется только после подтверждения
пользователя через `/task next`; агент не меняет фазу автоматически.

## Стиль кода и соглашения об именовании

Следуйте соглашениям Rust 2021 и стандартным настройкам rustfmt с отступом в четыре пробела. Используйте `snake_case` для функций, переменных, модулей и тестов, `PascalCase` для структур и перечислений, `SCREAMING_SNAKE_CASE` для констант. Для информативных ошибок предпочитайте `Result` вместе с `anyhow::Context`, а в рабочем коде используйте `?` вместо необоснованного `unwrap()`. Изолируйте логику отдельных провайдеров в специализированных функциях, таких как `send_openai` и `send_claude`. Пользовательские сообщения CLI сейчас написаны на русском языке; придерживайтесь этого языка в новых сообщениях.

## Требования к тестированию

Добавляйте узконаправленные тесты в `src/tests.rs`, группируя их по ответственному модулю; при дальнейшем выделении тестов допускается локальный `#[cfg(test)]`-модуль рядом с реализацией. Называйте тесты по наблюдаемому поведению, например `sqlite_store_saves_and_loads_session`. Для асинхронного поведения используйте `#[tokio::test]`, а для изоляции файловой системы и баз данных — `tempfile`. Проверяйте успешный разбор и сохранение данных, ошибочный ввод и пути миграции. Числового требования к покрытию нет, но каждое изменение поведения должно сопровождаться регрессионным тестом.

Для изменений памяти дополнительно проверяйте изоляцию слоёв, восстановление
`profile_id` и `task_id`, последовательность фаз без пропусков, формирование
системного prompt при каждой стратегии сжатия, передачу профиля обоим
провайдерам, сохранение долговременных фактов после `/new` и ANSI-цвет
индикатора текущей фазы и заголовков полей профиля. SQLite-тесты выполняйте на
временной базе и обязательно покрывайте миграцию с legacy-схемы без профилей,
задач и таблицы `memory_entries`. Отдельно проверяйте, что `/remember` и
`/forget` не изменяют сессии, задачи или профиль.

## Требования к коммитам и Pull Request

В истории используются короткие тематические заголовки, например `day10: добавить стратегии управления контекстом` и `week 1, day 1: add interactive multi-provider LLM CLI`. Следуйте этому шаблону: один логически завершённый набор изменений на коммит, краткий заголовок в повелительной форме и при необходимости префикс дня или области. В Pull Request опишите видимое пользователю изменение, перечислите команды проверки и добавьте ссылку на связанную задачу или день испытания. Если меняется взаимодействие с CLI, приложите вывод терминала или снимки экрана. Никогда не добавляйте API-ключи, базы данных сессий или содержимое личных диалогов.

Локальный `.env-mcp` содержит секреты CalDAV и предназначен только для запуска
процесса MCP-сервера. Агентам запрещено читать, индексировать, анализировать,
цитировать или выводить содержимое `.env-mcp` и любых локальных env-файлов с
секретами. Для документации и разработки используйте только `.env-mcp.example`;
значения переменных никогда не запрашивайте и не включайте в отчёты, логи,
тестовые фикстуры или коммиты.
